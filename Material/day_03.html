3.1. The Mechanical Reality: Next-Token Prediction

Despite appearances of conscious thought, a Large Language Model (LLM) is fundamentally a statistical next-token prediction engine. When you input a prompt, the model does not consult an internal philosophical compass or "reason" about right versus wrong. Instead, it evaluates the mathematical probability distribution across its entire vocabulary of tokens and selects the most probable next token given everything that came before.

This process is autoregressive: once token $N+1$ is selected, it is appended to the input sequence, and the entire enlarged sequence is fed back into the transformer to predict token $N+2$. The model repeats this prediction cycle hundreds or thousands of times until it produces an explicit <|endoftext|> stop token or reaches its maximum output limit.

Real World Example: Think of the predictive keyboard on your smartphone. As you type "I am on my...", the phone suggests "way" (70%), "break" (15%), or "phone" (5%). An LLM operates on the exact same fundamental principle, but scaled up from a few dozen rules to hundreds of billions of numerical weights trained across trillions of words from the public internet, books, and codebases.

3.2. Tokens vs. Words: The Anatomy of Subword Tokenization

Computers cannot read characters or words directly. Before text enters a neural network, it is sliced into discrete units called tokens. Modern LLMs use an algorithm known as Byte Pair Encoding (BPE). BPE iteratively merges frequently occurring character pairs into reusable subword units.

Under standing LL Ms

Token IDs: [14246, 2382, 30438, 3217]
Figure 3.0-1: Byte Pair Encoding (BPE) Tokenization into Subwords
Figure Parameters Explained:
  • Subword Chunking: Common words (like "the" or "run") are single tokens. Uncommon or compound words are split (e.g., "Understanding" $\rightarrow$ "Under" + "standing").
  • Whitespace Sensitivity: Notice the leading space in " LL". In BPE tokenizers, spaces are part of the token itself (represented as Ġ or hex).
  • Token IDs: Each subword maps to a fixed integer ID within the model's vocabulary table (e.g., OpenAI's cl100k_base has 100,277 distinct tokens).

Because tokens are subwords, a rule of thumb for English text is that 100 tokens $\approx$ 75 words. However, for non-Latin languages (e.g., Hindi, Japanese, Arabic) or complex programming languages, tokenization fragmentation increases significantly, often consuming 2x to 4x more tokens for the exact same conceptual meaning.

3.3. Embeddings: Giving Geometry to Meaning

Once text is converted into token IDs, how does the model know that "cat" is related to "kitten", or that "Paris" relates to "France" the same way "Tokyo" relates to "Japan"? The answer lies in dense vector embeddings.

Token IDs vs. Embeddings

These two ideas look similar but mean very different things, and it's easy to mix them up as a beginner:

  • Token ID — a plain integer that identifies a token in the model's vocabulary table. It carries no meaning by itself; it's just an index.
  • Embedding — a dense vector of floating-point numbers that the model looks up (and refines during training) for each token ID. This vector is what actually carries learned meaning.
"cat" → 1234  (token ID — just an integer)
1234 → [0.12, -0.45, 0.83, ...]  (embedding — a vector carrying meaning)

Here is the full pipeline from raw text to something the Transformer can actually compute with:

Text → Tokens → Token IDs → Embedding Vectors → Transformer → Contextual Representations

An embedding places a token ID into a high-dimensional continuous space — real models commonly use hundreds or even thousands of dimensions. Tokens with similar semantic meaning or grammatical function tend to end up close to one another in that space, once the model has been trained.

Vector("King") - Vector("Man") + Vector("Woman") ≈ Vector("Queen")
(a classic illustrative example — not a guarantee that holds exactly in every modern embedding model)
"king" and "queen" sit relatively close together in embedding space
"king" and "airplane" sit much farther apart
Figure 3.0-2: Semantic Relationships in High-Dimensional Embedding Space
Figure Parameters Explained:
  • Geometric Relationships: Relationships like gender, tense, capital cities, and synonyms can be reflected as geometric directions across dimensions. Some embedding spaces show this clearly; others only approximately.
  • Cosine Similarity: Measures the cosine of the angle between two multi-dimensional vectors. A score of 1.0 represents identical direction, while 0.0 represents complete orthogonality (no correlation). What counts as "close" depends on the specific embedding model and dataset — there is no single universal cutoff score.

# Program 3.0-2: Vector Cosine Similarity Implementation
import numpy as np

# Simplified 4-dimensional embeddings demonstrating semantic clustering
embeddings = {
    "king":       np.array([0.91, 0.82, 0.74, 0.05]),
    "queen":      np.array([0.88, 0.85, 0.71, 0.08]),
    "apple":      np.array([0.12, 0.04, 0.08, 0.95]),
    "banana":     np.array([0.15, 0.02, 0.11, 0.92]),
    "car":        np.array([0.05, 0.89, 0.12, 0.02])
}

def cosine_similarity(v1: np.ndarray, v2: np.ndarray) -> float:
    dot_product = np.dot(v1, v2)
    norm_v1 = np.linalg.norm(v1)
    norm_v2 = np.linalg.norm(v2)
    return dot_product / (norm_v1 * norm_v2)

print("Semantic Similarity Comparisons:")
print(f"  king vs queen:   {cosine_similarity(embeddings['king'], embeddings['queen']):.4f} (High Royalty Match)")
print(f"  apple vs banana: {cosine_similarity(embeddings['apple'], embeddings['banana']):.4f} (High Fruit Match)")
print(f"  king vs apple:   {cosine_similarity(embeddings['king'], embeddings['apple']):.4f} (Unrelated Concepts)")

3.4. Context Windows & The Attention Bottleneck

Every language model is bound by a Context Window (e.g., 8k, 32k, 128k, or 1M tokens). The context window is the maximum number of tokens the model can "see" at any single moment, including both your input prompt and the output it is currently generating.

Inside the transformer, the Self-Attention Mechanism allows every token in the context window to attend to (look at) every other token and weigh how relevant each one is — this is how the model figures out that "it" in a sentence refers to "the cat" mentioned three words earlier. However, this comes with computational trade-offs:

  • $O(N^2)$ Complexity: Standard naive attention scales quadratically with sequence length $N$. Doubling the context window quadruples the memory and computation required for the attention matrix.
  • Lost in the Middle Phenomenon: Research has shown that models tend to retrieve information located at the very beginning or the very end of a context window more reliably than information placed in the middle of very long prompts.
Coming later: When we study production LLM serving, we will explore KV caches, GPU memory, batching, and inference optimization — the engineering side of making attention fast and affordable at scale.

3.5. What Is Prompt Engineering?

A prompt is the text you send to an LLM: your instructions, any background information, and your question or task. Prompt engineering is the practice of designing that input deliberately — choosing the wording, structure, and information you provide — so the model produces the response you actually need.

It helps to be precise about what prompt engineering is not: it does not change the model's learned weights — those were fixed during training, as you saw in the sections above. What you are changing is the input — the instructions, context, and constraints supplied to the model at inference time. Two different prompts sent to the exact same model can produce dramatically different results, because you are steering the same underlying prediction engine toward a more specific target.

User Request
↓
Prompt
↓
LLM
↓
Response
Figure 3.0-5: Prompt Engineering Shapes What Happens Between Request and Response

Why does this matter so much? Because the same underlying model can look "smart" or "useless" depending entirely on how it's asked. Compare these two prompts:

Bad Prompt:
"Explain AI."
Improved Prompt:
"Explain artificial intelligence to a software developer who has no machine-learning background. Use one practical example and keep the explanation under 300 words."

The second prompt is better for three concrete reasons:

  • Audience: "a software developer with no ML background" tells the model what to assume the reader already knows.
  • Scope: "one practical example" and "under 300 words" give the model a clear boundary, instead of leaving length and depth to guesswork.
  • Removed ambiguity: "Explain AI" could mean a one-line definition, a history lesson, or a technical deep dive — the model has to guess which one you want, and it will often guess wrong.

3.6. How Prompting Works With an LLM

In the sections above, you learned what happens inside an LLM, from raw text to next-token prediction. Prompting sits right at the front of that pipeline: your prompt is simply the text that gets tokenized and fed in.

Figure 3.0-6: Your Prompt Enters the Same Pipeline Described Above
Prompt engineering does not retrain the LLM. The model's learned weights remain unchanged during ordinary prompting. We are changing the information and instructions supplied to the model at inference time — not the model itself.

That's the whole idea in one sentence: since the weights are fixed, everything you can influence has to travel through the prompt. This is exactly why the wording, structure, and completeness of your prompt matter so much.

3.7. Anatomy of a Good Prompt — RCTNO

Rather than writing prompts from scratch every time, it helps to use a repeatable structure. A well-structured prompt generally includes five components, remembered with the acronym RCTNO: Role, Context, Task, coNstraints, and Output.

STRUCTURED PROMPT
↓
ROLE
CONTEXT
TASK
↓
CONSTRAINTS
↓
OUTPUT
Figure 3.0-7: The RCTNO Structured Prompt Framework

Let's walk through each component: what it means, why it matters, and how a weaker version compares to a stronger one.

R — Role

Definition: The perspective or persona you want the model to adopt when answering.

Why it matters: A role narrows the model's vocabulary, tone, and assumptions. "Explain like a security auditor" produces a very different answer than "explain like a marketing writer," even for the exact same question.

Bad: "Review this code."

Better: "You are a senior Python code reviewer focused on security and readability. Review this code."

C — Context

Definition: The background information the model needs — documents, data, prior conversation, or business rules.

Why it matters: Without relevant context, the model can only draw on general patterns learned in training — exactly the situation that leads to guessing (you'll see this formalized as "grounding" in Day 4's Hallucinations & Grounding section).

Bad: "What's our refund policy?"

Better: "Using the refund policy text below, answer the question. [policy text] What's our refund policy for damaged items?"

T — Task

Definition: The specific action you want performed, stated as a clear instruction.

Why it matters: A vague task leaves the model to guess what "done" looks like — Section 3.8 covers this in depth.

Bad: "Sales data."

Better: "Identify the three products with the largest month-over-month sales decline."

N — Constraints

Definition: The rules the model should follow while completing the task — length limits, tone, what to include or exclude, what it must not assume.

Why it matters: Without constraints, a technically correct answer can still be unusable — too long, too speculative, or in the wrong tone for its audience.

Bad: (no constraints given) — the model may write a full page when you needed three sentences.

Better: "Answer in exactly 3 bullet points. Do not include information that isn't in the source text."

O — Output

Definition: The format the response should take — plain text, bullet points, a table, JSON, and so on (Section 3.10 goes deeper).

Why it matters: Software downstream of the model usually needs a predictable shape, not just correct content.

Bad: (format unspecified) — the shape of the answer changes every time you run it.

Better: "Return the result as a JSON object with fields: summary, priority, recommended_action."

Not every prompt needs all five components spelled out — a quick one-off question may only need a Task. But for anything that needs to be reliable, reusable, or consumed by other software, filling in all five is the difference between a prompt that "usually works" and one you can depend on.

3.8. Writing Clear Instructions

The Task component deserves a closer look on its own, because vague instructions are the single most common cause of disappointing LLM output. A clear instruction usually:

  • starts with a clear action verb (summarize, classify, extract, compare, rewrite — not just "look at" or "help with")
  • specifies exactly what the task is
  • defines the scope (how much, which part, what time range)
  • identifies the target audience
  • specifies success criteria — what a good answer looks like
  • avoids vague requests that could reasonably mean five different things

Weak: "Analyze this sales data."

Better: "Analyze the sales data and identify the three products with the largest month-over-month decline. Explain the likely trend for each product."

Here's the same pattern applied across three common workplace tasks:

Data Analysis

Weak: "Analyze this report."

Better: "Review this quarterly report and list the top 3 metrics that changed the most, with a one-sentence explanation for each."

Code Review

Weak: "Check this code."

Better: "Review this Python function for security issues and unhandled edge cases. List each issue with the line number and a suggested fix."

Document Summarization

Weak: "Summarize this report."

Better: "Summarize this incident report for an engineering manager in 5 bullet points, focused on root cause and remediation steps."

3.9. Context, Constraints & Boundaries

Four related but distinct ideas are easy to blur together. Keeping them separate makes prompts much easier to write and debug:

  • Instruction — what should the model do?
  • Context — what information does the model need to do it?
  • Constraint — what rules should it follow while doing it?
  • Boundary — what should it NOT assume, invent, or do?
Instruction:
Summarize the company leave policy.
Context:
[Company Leave Policy]
Constraints:
Use only information contained in the policy.
Missing information:
If the answer is not present, say: "Not specified in the provided policy."
Output:
Return 5 concise bullet points.
Figure 3.0-8: A Fully Specified, Grounded Prompt

Notice that context should be relevant and sufficient — not simply large. Pasting an entire 40-page handbook when only one section applies wastes tokens, can crowd out other important instructions, and doesn't automatically make the answer better (recall the context-window discussion in Section 3.4 above).

3.10. Output Formatting

You can tell an LLM exactly how its response should be structured — this becomes essential once you start building software, and later agents, around LLM output.

Plain text: "Explain the result."

Bullet points: "Return the result as 5 bullet points."

Table: "Return the comparison as a table."

JSON: "Return the result as JSON with the fields shown below."

{ "summary": "...", "priority": "...", "recommended_action": "..." }
LLM
↓
Structured Output
↓
Application / Python
↓
Database / API / Agent
Figure 3.0-9: Structured Output Is What Lets Software Consume an LLM's Response

Predictable output matters because software downstream of the model — a database write, an API call, another function — usually needs to parse the response automatically. A response that's sometimes a paragraph, sometimes a list, and sometimes a table will break that code. Asking explicitly for a format turns "usually parseable" into "reliably parseable."

3.11. Zero-Shot Prompting

Zero-shot prompting means asking the model to perform a task without providing demonstration examples.
Classify this customer complaint as: Billing, Technical, or Shipping. Complaint: "My package has not arrived yet."

Use zero-shot when:

  • the task is straightforward
  • your instructions are sufficient on their own
  • the expected output behavior is fairly standard

3.12. Few-Shot Prompting

Few-shot prompting provides examples of the desired input-output behavior before asking the model to process a new input.

Few-shot prompting is especially useful when:

  • you need custom classification labels the model wouldn't guess on its own
  • you need a specific output format
  • you need to match a particular style or tone
  • the task behavior is unusual or non-obvious
  • you want to demonstrate edge-case behavior, like what to do when data is missing
Few-shot prompting does NOT update or retrain the model's weights. The examples condition the model's behavior for this one request, at inference time — the model's weights simply aren't touched. Close the session, and the model "forgets" your examples entirely. We'll formalize this training/inference distinction in Day 4.

Topic Quiz (10 Questions)

1. What is an LLM fundamentally doing when generating text?
  • Querying an internal SQL database of factual human knowledge.
  • Predicting the probability distribution of the next token given prior tokens.
  • Executing compiled Python bytecode in a sandboxed runtime.
  • Translating user prompts into formal symbolic logic proofs.
2. What is a token?
  • Always an entire complete English word.
  • Always a single character.
  • A subword unit — a chunk of text the model reads and generates as one piece.
  • An encrypted cryptographic hash representing an API user session.
3. What is the difference between a token ID and an embedding?
  • They are two names for exactly the same thing.
  • A token ID is just an integer index; an embedding is a dense vector that carries learned meaning.
  • A token ID is a vector of floats, while an embedding is a plain integer.
  • Token IDs are used only during training, and embeddings are used only during inference.
4. Why does the context window matter?
  • It determines how many API keys a user can register.
  • It's the maximum amount of text (input plus output) the model can consider at once — anything beyond it is not visible to the model.
  • It controls how much the model is allowed to charge per token.
  • It sets the model's release date.
5. What is prompt engineering?
  • Writing Python code that trains a new neural network from scratch.
  • Deliberately designing the instructions, context, and structure of the input given to an LLM to get a better result.
  • Installing and configuring GPU drivers for model inference.
  • A synonym for building a chatbot user interface.
6. Does writing a good prompt update the model's weights?
  • Yes, every prompt slightly retrains the model.
  • No — ordinary prompting only changes the input at inference time; the model's learned weights stay the same.
  • Yes, but only when the prompt exceeds 500 tokens.
  • Only system prompts update weights; user prompts do not.
7. What is structured prompting?
  • Writing a prompt using only valid JSON syntax.
  • Organizing a prompt into clear components — such as role, context, task, constraints, and output — instead of one vague block of text.
  • A technique that only works with programming-related questions.
  • Sending the same prompt to multiple models at once.
8. What is the role of context in a prompt?
  • It sets the model's temperature value.
  • It supplies the background information the model needs to answer accurately, instead of relying on general training patterns.
  • It has no measurable effect on the response.
  • It determines how many tokens the response will cost.
9. What is zero-shot prompting?
  • Sending an empty prompt to test the model's default behavior.
  • Asking the model to perform a task without providing any demonstration examples.
  • A prompting technique that requires fine-tuning first.
  • Running the same prompt zero times before deploying it.
10. What is few-shot prompting?
  • Fine-tuning the model on a small dataset of a few hundred examples.
  • Providing a small number of input-output examples in the prompt before asking the model to handle a new input.
  • Limiting the model to a "few" possible output tokens.
  • Asking the same question multiple times and averaging the answers.
