Topic 2

C Programming Best Practices

Writing C for embedded systems is fundamentally different from general-purpose desktop or backend programming. On a PC or server, a segfault halts a single process while the OS kernel recovers gracefully. In an embedded automotive braking controller, cardiac pacemaker, or drone flight stabilizer, a single uncaught pointer fault or arithmetic overflow can trigger catastrophic physical failure.

Disciplined embedded C programming is governed by three foundational pillars: determinism (execution timing and memory allocation must be strictly bounded), type safety (every variable's exact bit-width and sign representation must be explicit), and defensive const-correctness (memory intent must be enforced at compile time to conserve SRAM and place read-only assets into non-volatile Flash).

2.1 The Embedded Philosophy: Determinism and Resource Constraints

In desktop computing, software often trades CPU cycles and memory overhead for developer convenience. In embedded engineering, resources are severely constrained: a typical 32-bit ARM Cortex-M0+ or M4 may possess only 32 KB of SRAM and 128 KB of on-chip Flash.

To achieve deterministic, bug-free operation, embedded software engineering adheres to several strict guidelines:

  • No Dynamic Heap Allocation (malloc / free): Dynamic heap causes memory fragmentation over time, non-deterministic execution spikes, and the risk of catastrophic heap-stack collisions. All memory must be statically or stack allocated.
  • Bounded Loop Iterations: Every loop (whether waiting for a hardware flag or parsing an incoming packet) must feature a deterministic timeout counter. An unbounded while (!ready); loop will hang the CPU indefinitely if a hardware wire disconnects.
  • Explicit Integer Widths: Native C types (short, int, long) change size across CPU architectures. Using fixed-width types from <stdint.h> is strictly mandatory.

2.2 Mandatory Use of Fixed-Width Types (<stdint.h>)

The standard C specification intentionally allows the bit-width of primitive data types to be implementation-defined to allow compilers to match the host machine word. Table 2.1 illustrates the hazards of native types across common embedded architectures:

Type Category Native C Type 8-bit AVR / 16-bit MSP430 32-bit Cortex-M Mandatory <stdint.h> Replacement
8-bit Unsigned unsigned char 8 bits (0 to 255) 8 bits (0 to 255) uint8_t
16-bit Signed int / short 16 bits (-32,768 to 32,767) 32 bits (-2.14B to +2.14B) int16_t
32-bit Unsigned unsigned long 32 bits 32 bits or 64 bits uint32_t
Boolean int (0 or 1) 16 bits (wastes 15 bits) 32 bits (wastes 31 bits) bool (<stdbool.h>)
Real World Example: In 1996, the maiden flight of the Ariane 5 rocket (Flight 501) resulted in complete vehicle disintegration 37 seconds after launch. The root cause was an uncaught integer overflow: a 64-bit floating point velocity value was cast into a 16-bit signed integer. The resulting overflow caused the primary and backup inertial guidance computers to halt simultaneously. Rigorous range checking and explicit integer typing prevent such catastrophes.

2.3 Const-Correctness: Placing Read-Only Data in Flash

Microcontrollers feature separate physical memories for program code/constants (Flash / ROM) and read-write runtime data (SRAM). By default, non-const global variables consume precious SRAM. By decorating read-only tables, lookup calibrations, and string literals with const, the linker places them into the .rodata (Read-Only Data) section within Flash, preserving SRAM for runtime stacks and communication buffers.

Figure 2.1: Microcontroller Physical Memory Distribution for Code, Constants, and Variables
Memory Placement Rules Explained:
  • uint8_t table[256]; → Allocated in SRAM (.data or .bss). Wastes 256 bytes of volatile RAM.
  • const uint8_t table[256]; → Placed directly into Flash (.rodata). Zero SRAM consumed!
  • void write(const uint8_t *buf, size_t len); → Function guarantees it will never mutate the caller's buffer.

2.4 Eliminating Side Effects and Unspecified Evaluation Order

One of the most dangerous traps in C is relying on an unspecified sequence of operations within an expression. According to the ISO C standard, the order of evaluation of function arguments and sub-expressions between sequence points is unspecified.

For example, the expression process(get_next(), get_next()); does not guarantee which call executes first. If get_next() reads from a hardware FIFO, data bytes will be processed in unpredictable order depending on compiler optimization flags!

2.5 Hands-On Code Implementations

The following production-grade implementation demonstrates the core best practices: explicit fixed-width integers, defensive parameter validation, const-correct buffer handling, bounded timeout loops, and complete elimination of heap allocation. 

/**
 * Program 2.1: Deterministic Sensor Data Acquisition Engine
 * File: sensor_engine.c
 * Target: Embedded C Best Practices Demonstration
 */

#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

/* Return status codes representing exhaustive operational states */
typedef enum {
    SENSOR_OK            = 0,
    SENSOR_ERR_NULL_PTR  = -1,
    SENSOR_ERR_BAD_PARAM = -2,
    SENSOR_ERR_TIMEOUT   = -3,
    SENSOR_ERR_OVERFLOW  = -4
} SensorStatus_t;

/* Sensor reading structure with explicit units and signedness */
typedef struct {
    int16_t  temperature_celsius_x10;  /*!< Range: -400 to +1250 (-40.0C to +125.0C) */
    uint16_t pressure_hpa;              /*!< Range: 300 to 1100 hPa */
    uint8_t  humidity_percent;          /*!< Range: 0 to 100% */
    uint32_t timestamp_ms;              /*!< Milliseconds since system startup */
} SensorSample_t;

/* Constant calibration table stored permanently in Flash (.rodata) */
static const int16_t TEMPERATURE_CALIBRATION_OFFSETS[4] = {
    -12,  /* Sensor 0 offset: -1.2 deg C */
      5,  /* Sensor 1 offset: +0.5 deg C */
      0,  /* Sensor 2 offset:  0.0 deg C */
     -3   /* Sensor 3 offset: -0.3 deg C */
};

#define SENSOR_TIMEOUT_CYCLES  (50000UL)
#define MAX_SENSORS            (4U)

/**
 * @brief Reads raw sensor telemetry with strict bounds and deterministic timeout.
 * @param[in]  sensor_id  Index of sensor (0 to 3)
 * @param[out] sample_out Pointer to destination sample struct
 * @return SensorStatus_t Status code
 */
SensorStatus_t sensor_read_sample(const uint8_t sensor_id, SensorSample_t * const sample_out) {
    /* 1. Defensive parameter validation */
    if (sample_out == NULL) {
        return SENSOR_ERR_NULL_PTR;
    }
    if (sensor_id >= MAX_SENSORS) {
        return SENSOR_ERR_BAD_PARAM;
    }

    /* 2. Deterministic, bounded hardware polling loop */
    uint32_t timeout_counter = SENSOR_TIMEOUT_CYCLES;
    volatile uint32_t mock_hw_ready = 1U; /* Simulated ready flag */

    while ((mock_hw_ready == 0U) && (timeout_counter > 0U)) {
        timeout_counter--;
    }

    if (timeout_counter == 0U) {
        return SENSOR_ERR_TIMEOUT;
    }

    /* 3. Acquire raw data and apply Flash-based calibration */
    const int16_t raw_temp = 250; /* 25.0 deg C */
    const int16_t calibrated_temp = (int16_t)(raw_temp + TEMPERATURE_CALIBRATION_OFFSETS[sensor_id]);

    sample_out->temperature_celsius_x10 = calibrated_temp;
    sample_out->pressure_hpa = 1013U;
    sample_out->humidity_percent = 45U;
    sample_out->timestamp_ms = 12450UL;

    return SENSOR_OK;
}

2.6 Buggy vs. Modern Safe Code Comparison

Consider a function intended to compute the average of an array of 16-bit ADC samples. The legacy version commits several common errors: missing pointer validation, using native int types, risking 16-bit accumulator overflow, and modifying global variables without thread safety.

View Buggy/Legacy Code

This snippet has 4 distinct vulnerabilities: no null-check, 16-bit accumulator overflow, divide-by-zero risk, and missing const qualifier on input array: 

/* BUGGY / UNSAFE: Accumulator overflow, no bounds validation */
int calculate_average(int *samples, int count) {
    int sum = 0; /* On 16-bit systems, sum overflows past 32,767 after just 8 readings! */
    int i;
    
    for (i = 0; i < count; i++) {
        sum += samples[i]; /* Undefined Behavior on signed overflow */
    }
    
    return sum / count; /* If count is 0, triggers hardware Divide-by-Zero fault! */
}
Program 2.2-A: Buggy Accumulator with Integer Overflow Hazard

Here is the production-grade safe refactoring using fixed-width integers, a 64-bit accumulator to guarantee overflow immunity, const-correct buffer pointers, and defensive zero-length validation: 

/* SAFE / PRODUCTION-GRADE: 64-bit accumulator, const buffer, verified length */
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

bool calculate_average_u16(const uint16_t * const samples, 
                           const size_t count, 
                           uint16_t * const avg_out) 
{
    /* Validate pointers and guard against division by zero */
    if ((samples == NULL) || (avg_out == NULL) || (count == 0U)) {
        return false;
    }

    /* Use 64-bit unsigned accumulator to eliminate any possibility of overflow */
    uint64_t accumulator = 0ULL;
    for (size_t i = 0U; i < count; ++i) {
        accumulator += (uint64_t)samples[i];
    }

    /* Compute average and cast back into 16-bit output */
    *avg_out = (uint16_t)(accumulator / (uint64_t)count);
    return true;
}

Topic Quiz (10 Questions)

Test your mastery of embedded C best practices, const-correctness, and deterministic design.

1. Why is dynamic memory allocation (malloc/free) strictly prohibited in safety-critical embedded firmware?
  • malloc() is only supported in C++, not C.
  • Heap fragmentation can lead to non-deterministic allocation failure and unpredictable execution timing.
  • Flash memory cannot read data allocated on the heap.
  • The C11 standard officially deprecated malloc().
Heap allocation causes non-deterministic fragmentation over long runtimes, risking unexpected allocation failures in critical functions.
2. When decorating a global lookup table with the 'const' keyword, where does the linker place the data in microcontroller memory?
  • In the .bss segment of SRAM
  • On the runtime call stack
  • In the .rodata segment of non-volatile Flash memory
  • In the CPU general-purpose register file
Linker scripts route const-qualified variables into .rodata residing in Flash/ROM, preserving precious SRAM for read-write operations.
3. What is the fundamental problem with the declaration: 'unsigned int sensor_val;' in portable firmware?
  • It cannot store odd numbers.
  • The width of 'unsigned int' is architecture-dependent: 16 bits on 8/16-bit MCUs and 32 bits on Cortex-M.
  • It is not recognized by GCC.
  • It generates an unaligned memory trap on ARM.
The C standard does not fix the exact bit-width of native integer types. Developers must use uint16_t or uint32_t for portable certainty.
4. What does the declaration 'const uint8_t * const ptr;' signify in C?
  • A mutable pointer to a mutable byte
  • A mutable pointer to a constant byte
  • A constant pointer to a constant byte (neither the address nor the data can be modified)
  • A volatile register pointer
Reading from right to left: 'const ptr' means the pointer address is constant; '* const uint8_t' means the pointed-to data byte is constant.
5. Why is an unbounded loop like 'while ((STATUS_REG & 0x01) == 0);' dangerous in production firmware?
  • Bitwise AND is not supported inside while loop conditions.
  • If the hardware peripheral fails or the line is severed, the firmware hangs forever without recovery.
  • It triggers an automatic bus fault.
  • It resets the microcontroller's SysTick timer.
Every hardware polling loop must feature a bounded iteration or tick timeout to prevent infinite CPU lockup during peripheral hardware faults.
6. What happens if two calls with side effects are used as arguments: 'foo(get_val(), get_val());'?
  • The compiler always evaluates from left to right.
  • The compiler always evaluates from right to left.
  • The order of evaluation of function arguments is unspecified by the C standard and depends on compiler implementation.
  • The code fails to compile with a syntax error.
The ISO C standard explicitly states argument evaluation order is unspecified; relying on evaluation order introduces compiler-dependent bugs.
7. Which header introduced in C99 provides the standard 'bool', 'true', and 'false' macros?
  • <stdint.h>
  • <stdbool.h>
  • <stddef.h>
  • <stdlib.h>
<stdbool.h> defines bool (expanding to the _Bool keyword), true (1), and false (0).
8. What is the danger of using macros with arguments without enclosing each parameter in parentheses (e.g. #define SQUARE(x) x * x)?
  • The macro will only accept integer arguments.
  • Operator precedence issues: SQUARE(2 + 3) expands to 2 + 3 * 2 + 3 = 11 instead of 25.
  • The macro will be stored in Flash memory.
  • GCC disables macro expansion when optimization is turned on.
Macros perform raw text substitution. Without parentheses, operator precedence will corrupt arithmetic evaluations.
9. What is the purpose of the C99 'restrict' keyword on pointer arguments?
  • It restricts the pointer to null-terminated strings.
  • It prevents the pointer from accessing SRAM.
  • It hints to the compiler that the pointer does not alias any other pointer, enabling aggressive register caching and SIMD optimization.
  • It restricts access to kernel privilege mode.
'restrict' promises that the memory referenced by the pointer is accessed only through that pointer, allowing the compiler to optimize without reloading aliased memory.
10. Why should functions that return error codes be decorated with [[nodiscard]] (in C23) or __attribute__((warn_unused_result)) (in GCC)?
  • To force the function to execute in the SysTick ISR.
  • To generate a compile-time warning or error if the caller ignores the return status, ensuring errors are never silently ignored.
  • To reduce Flash consumption by 10%.
  • To enable automatic hardware reset on error.
Forcing callers to inspect return codes prevents critical hardware failure states from being silently bypassed during execution.

Hands-On Assignments

Apply these 5 hands-on assignments to enforce best practices and clean code patterns.

Assignment 1: Flash vs. SRAM Footprint Audit

Task: Create a lookup table of 1024 16-bit sine wave values. First, declare it as a mutable global: uint16_t sin_lut[1024];. Compile and run size to note the .data / .bss size. Next, add const to the declaration and recompile. Verify how many bytes migrated from SRAM to Flash.

Assignment 2: Hardening an ADC Driver Interface

Task: Take a legacy function prototype: int read_adc(int channel, int *val);. Refactor this interface following embedded best practices: use fixed-width integer types, enforce const-correctness, return a typed enum status code, and add defensive null-pointer and channel-range validations.

Assignment 3: Eliminating Macro Hazards with Inline Functions

Task: Write a preprocessor macro #define CLAMP(x, min, max) .... Demonstrate a double-evaluation bug when invoking CLAMP(i++, 0, 10). Then replace the macro with a type-safe C99 static inline int32_t clamp_i32(int32_t x, int32_t min, int32_t max) function and prove that side-effects are eliminated.

Assignment 4: Safe Ring Buffer Index Arithmetic

Task: Implement head and tail index advancement for a circular ring buffer of size 32. Show why using power-of-two sizing with a bitwise mask (index = (index + 1) & 31U) is superior to using the modulo operator (index = (index + 1) % 32) in terms of instruction cycle count on Cortex-M0+.

Assignment 5: Bounded Polling Loop Timeout Guard

Task: Write a mock I2C wait function that polls a simulated busy bit. Incorporate a timeout counter. Simulate both a successful peripheral acknowledgment and a disconnected line fault. Verify that the function exits deterministically within a known cycle threshold without hanging the main superloop.
