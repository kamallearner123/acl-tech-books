Topic 9

Make & CMake Basics

As firmware projects scale beyond a single source file to encompass RTOS kernels, vendor HAL drivers, communication stacks, and unit test suites, manual command-line compilation becomes impossible. Build automation is the discipline of expressing dependency graphs between source files, headers, and compiled artifacts, guaranteeing that only modified files are recompiled.

In the embedded industry, two tools dominate build automation: GNU Make (the ubiquitous classic workhorse relying on explicit dependency rules and pattern matching) and CMake (the modern meta-build generator creating portable, out-of-tree Ninja/Make build systems with first-class cross-compilation toolchain support).

9.1 Anatomy of a GNU Makefile

Every Makefile rule adheres to a strict syntax structure: 

target: prerequisites
	recipe (MUST be indented with a real TAB character, not spaces!)

To eliminate repetitive boilerplate, Make provides powerful automatic variables:

  • $@: Represents the target filename being generated.
  • $<: Represents the first prerequisite (the primary source file).
  • $^: Represents all prerequisites in a space-delimited list.
  • .PHONY: Declares targets (like clean or flash) that do not represent physical files on disk.

9.2 Automatic Header Dependency Tracking (-MMD -MP)

A notorious bug in naive Makefiles is failing to track header file modifications. If you edit config.h, Make will not recompile main.c unless config.h was explicitly listed as a prerequisite!

The professional solution instructs GCC to automatically generate dependency files (.d) during compilation using the flags:
CFLAGS += -MMD -MP
These generated dependency files are then included directly into the Makefile via -include $(DEPS).

9.3 Modern Embedded CMake Architecture

While Make directly executes shell commands, CMake is a meta-build system that parses a CMakeLists.txt specification and generates native build scripts for tools like Ninja or GNU Make.

9.4 Hands-On Code Implementations

The following production-grade Makefile demonstrates pattern rules, out-of-tree build directory management, automatic header dependency tracking, and binary flashing targets: 

# ==============================================================================
# Production Embedded Makefile for ARM Cortex-M4
# Features: Automatic dependency generation, out-of-tree builds, binary sizing
# ==============================================================================

TARGET    := firmware
BUILD_DIR := build
SRC_DIR   := src

# Toolchain definitions
CROSS_COMPILE ?= arm-none-eabi-
CC            := $(CROSS_COMPILE)gcc
OBJCOPY       := $(CROSS_COMPILE)objcopy
SIZE          := $(CROSS_COMPILE)size

# Source discovery
SRCS := $(wildcard $(SRC_DIR)/*.c)
OBJS := $(SRCS:$(SRC_DIR)/%.c=$(BUILD_DIR)/%.o)
DEPS := $(OBJS:.o=.d)

# Target CPU architecture flags
MCU_FLAGS := -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16

# Strict warning and dependency generation flags
CFLAGS := $(MCU_FLAGS) -std=c11 -Os -Wall -Wextra -Werror -Wpedantic
CFLAGS += -MMD -MP
CFLAGS += -ffunction-sections -fdata-sections

# Linker flags
LDSCRIPT := linker/stm32f401.ld
LDFLAGS  := $(MCU_FLAGS) -T$(LDSCRIPT) -Wl,-Map=$(BUILD_DIR)/$(TARGET).map
LDFLAGS  += -Wl,--gc-sections --specs=nano.specs

.PHONY: all clean flash size

all: $(BUILD_DIR)/$(TARGET).elf $(BUILD_DIR)/$(TARGET).bin size

# Link executable ELF
$(BUILD_DIR)/$(TARGET).elf: $(OBJS) | $(BUILD_DIR)
	@echo "LINK $@"
	@$(CC) $(OBJS) $(LDFLAGS) -o $@

# Generate raw binary for flashing
$(BUILD_DIR)/$(TARGET).bin: $(BUILD_DIR)/$(TARGET).elf
	@echo "OBJCOPY $@"
	@$(OBJCOPY) -O binary $< $@

# Pattern rule: Compile C sources into relocatable objects
$(BUILD_DIR)/%.o: $(SRC_DIR)/%.c | $(BUILD_DIR)
	@echo "CC $<"
	@$(CC) $(CFLAGS) -c $< -o $@

$(BUILD_DIR):
	@mkdir -p $@

size: $(BUILD_DIR)/$(TARGET).elf
	@$(SIZE) -B $<

clean:
	@echo "CLEAN"
	@rm -rf $(BUILD_DIR)

# Include generated header dependencies
-include $(DEPS)
Program 9.1: Production Embedded Makefile with Header Dependency Tracking

9.5 Buggy vs. Modern Safe Code Comparison

A naive Makefile without header dependency generation causes stale builds: modifications to header structs or `#define` constants are silently ignored during incremental builds.

View Buggy/Legacy Code

This naive rule only checks timestamps on %.c. If config.h changes, Make reports "Nothing to be done", resulting in firmware with desynchronized structures: 

# BUGGY: Does NOT track changes in .h header files!
%.o: %.c
	gcc $(CFLAGS) -c $< -o $@
Program 9.2-A: Naive Rule Missing Header Dependencies

By instructing GCC to emit .d dependency files via -MMD -MP, Make tracks all nested `#include` hierarchies automatically: 

# SAFE: Automatic header dependency generation
CFLAGS += -MMD -MP

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# Include all generated dependency rules
-include $(OBJS:.o=.d)

Topic Quiz (10 Questions)

Test your mastery of GNU Make rules, automatic variables, and CMake toolchains.

1. In a GNU Makefile recipe, what character is strictly required at the beginning of each command line?
  • Four spaces
  • A Tab character ('\t')
  • A semicolon
  • An octothorpe (#)
GNU Make's syntax parser strictly requires a true Tab character to identify recipe commands; spaces will produce a 'missing separator' syntax error.
2. What does the automatic variable '$@' represent inside a Makefile rule?
  • The first prerequisite
  • The name of the target file being generated
  • All prerequisites
  • The active compiler
$@ expands to the exact filename of the target matching the rule.
3. What does the automatic variable '$<' represent inside a Makefile rule?
  • The target file
  • The first prerequisite (typically the primary source file)
  • The current directory
  • The linker script
$< expands to the first prerequisite in the rule's dependency list.
4. Why should targets like 'clean' and 'all' be declared as .PHONY in a Makefile?
  • To run them in parallel.
  • To ensure the recipe executes even if a physical file named 'clean' or 'all' exists on the filesystem.
  • To suppress compiler warnings.
  • To enable GDB debugging.
.PHONY informs Make that the target does not produce an eponymous file on disk, preventing timestamp check conflicts.
5. Which GCC flags enable automatic generation of header dependency files (.d) during compilation?
  • -Wall -Wextra
  • -MMD -MP
  • -O2 -g
  • -S -c
-MMD generates Make dependency files (.d) excluding system headers, while -MP adds dummy phony targets for headers to prevent deleted-header errors.
6. What is the role of a CMake Toolchain File (e.g. arm-none-eabi.cmake)?
  • It replaces the linker script.
  • It configures CMAKE_SYSTEM_NAME, CMAKE_C_COMPILER, and target flags before CMake performs system environment checks.
  • It installs Python.
  • It burns the microcontroller bootloader.
A toolchain file tells CMake that it is cross-compiling for a bare-metal architecture and specifies the cross-compiler executable paths.
7. What is an 'out-of-tree' build in CMake or Make?
  • Compiling code on a laptop outdoors.
  • Generating all intermediate object files (.o), binaries, and artifacts in a separate build directory (e.g. build/) keeping source directories clean.
  • Compiling without using header files.
  • Linking without an ELF format.
Out-of-tree builds isolate all build artifacts inside a dedicated build folder, preventing clutter and simplifying cleanup (rm -rf build).
8. In a pattern rule '%.o: %.c', what does the '%' character signify?
  • The modulo operator.
  • A stem wildcard that matches any string across target and prerequisite filenames.
  • A comment line.
  • An environment variable.
The '%' in pattern rules acts as a stem wildcard, matching foo.o to foo.c across all compilation units.
9. What CMake command adds include directories to a specific compiled library or executable target?
  • include_directories()
  • target_include_directories()
  • add_subdirectory()
  • set_property()
Modern CMake favors target_include_directories() over global include_directories() to enforce clean modular encapsulation.
10. Why is the '-j' flag passed to 'make' (e.g. make -j8)?
  • To enable JSON output.
  • To execute compilation recipes in parallel across multiple CPU cores, accelerating build times.
  • To jump to the first error.
  • To enable JTAG debugging.
-j spawns multiple parallel jobs matching the number of host CPU cores, speeding up large multi-file builds dramatically.

Hands-On Assignments

Execute these 5 laboratory assignments to master build automation with Make and CMake.

Assignment 1: Incremental Build Dependency Verification

Task: Create a project with main.c, gpio.c, and gpio.h. Author a Makefile with -MMD -MP. Build the project. Run touch gpio.h and run make. Verify that Make detects the header timestamp change and rebuilds only the files that include gpio.h.

Assignment 2: Automated Size Guard Rule in Make

Task: Add a post-build target to your Makefile that evaluates the size of firmware.bin using a shell script. If the binary exceeds 64 KB (65,536 bytes), halt the build with an error message: "ERROR: Firmware exceeded maximum 64KB Flash allocation!".

Assignment 3: Multi-Target Debug vs. Release Builds

Task: Enhance your Makefile to accept a configuration variable: make BUILD=debug versus make BUILD=release. When building for debug, set -O0 -g3 -DDEBUG and output to build/debug/. When building for release, set -Os -DNDEBUG and output to build/release/.

Assignment 4: Modern CMake Cross-Compilation Project

Task: Create a CMakeLists.txt and an arm-none-eabi.cmake toolchain file for your embedded project. Configure CMake using Ninja (cmake -B build -GNinja --toolchain arm-none-eabi.cmake). Build the project and benchmark build times compared to GNU Make.

Assignment 5: Automated Flashing Target via OpenOCD

Task: Add a flash target to your Makefile that invokes OpenOCD in headless mode: openocd -f interface/stlink.cfg -f target/stm32f4x.cfg -c "program $(TARGET).bin 0x08000000 reset exit". Test flashing your board by executing make flash.
