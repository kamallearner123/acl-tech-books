Topic 16

Defensive Programming in Embedded C

In desktop application programming, an unhandled exception or null-pointer dereference results in an OS process crash and a core dump. In an embedded system, there is no underlying operating system to clean up resources: a crashed core leaves motor H-bridges energized, surgical lasers firing, or flight control surfaces locked in place.

Defensive Programming is the systematic engineering practice of designing software to remain reliable and secure despite unexpected hardware faults, corrupted communications, electromagnetic interference (EMI), and programming bugs in peer modules. It operates on a foundational axiom: Anything that can fail, will fail; the firmware must anticipate every failure, detect it immediately, and transition into a verified fail-safe state.

16.1 Boundary Validation & Pointer Sanitization

Every public API function accepting pointers or numerical arguments must validate its parameters prior to performing any hardware operations or memory writes: 

#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

typedef enum {
    DRIVER_STATUS_OK = 0,
    DRIVER_STATUS_NULL_PTR,
    DRIVER_STATUS_INVALID_PARAM,
    DRIVER_STATUS_BUFFER_OVERFLOW,
    DRIVER_STATUS_HARDWARE_TIMEOUT
} DriverStatus_t;

DriverStatus_t telemetry_packet_serialize(
    const uint8_t * const p_src_data,
    const size_t          src_len_bytes,
    uint8_t * const       p_dst_buffer,
    const size_t          dst_capacity_bytes,
    size_t * const        p_written_bytes)
{
    /* 1. Pointer Sanitization: Check all input and output pointers */
    if ((p_src_data == NULL) || (p_dst_buffer == NULL) || (p_written_bytes == NULL)) {
        return DRIVER_STATUS_NULL_PTR;
    }

    /* 2. Range & Bounds Validation */
    if (src_len_bytes == 0U) {
        return DRIVER_STATUS_INVALID_PARAM;
    }

    /* Reserve 4 bytes for preamble and 2 bytes for CRC16 */
    const size_t required_bytes = src_len_bytes + 6U;
    if (required_bytes > dst_capacity_bytes) {
        *p_written_bytes = 0U;
        return DRIVER_STATUS_BUFFER_OVERFLOW;
    }

    /* 3. Safe Execution */
    p_dst_buffer[0] = 0xAAU;
    p_dst_buffer[1] = 0x55U;
    p_dst_buffer[2] = (uint8_t)(src_len_bytes >> 8);
    p_dst_buffer[3] = (uint8_t)(src_len_bytes & 0xFFU);

    for (size_t i = 0; i < src_len_bytes; ++i) {
        p_dst_buffer[4U + i] = p_src_data[i];
    }

    /* Append CRC checksum */
    uint16_t crc = crc16_calculate(&p_dst_buffer[4], src_len_bytes);
    p_dst_buffer[4U + src_len_bytes]      = (uint8_t)(crc >> 8);
    p_dst_buffer[4U + src_len_bytes + 1U] = (uint8_t)(crc & 0xFFU);

    *p_written_bytes = required_bytes;
    return DRIVER_STATUS_OK;
}
Program 16.1: Defensively Hardened Serialization Function

The Cardinal Rule of Buffer Parameters

In defensive C, never pass a buffer pointer without also passing its maximum allocated capacity. Functions like strcpy(), sprintf(), and gets() that assume the destination buffer is large enough are banned by MISRA-C and modern security standards. Always pass capacity and verify bounds before every byte write.

16.2 Stuck-Hardware Fallbacks & Bounded Loops

A ubiquitous design flaw in amateur firmware is unbounded polling of hardware status registers: 

/* FATAL BUG: Unbounded spin-loop! */
void i2c_write_byte_fragile(uint8_t data) {
    I2C1->DR = data;
    while (!(I2C1->SR1 & I2C_SR1_TXE)); /* HANGS FOREVER IF BUS IS SHORTED! */
}

If an external I2C sensor experiences an ESD strike, loose solder joint, or drops power, the TXE flag may never assert. The CPU will freeze inside the while loop indefinitely, resulting in a locked medical ventilator or drone flight controller.

The Bounded Timeout Pattern

Every loop waiting for hardware confirmation must include an explicit countdown or SysTick timestamp timeout: 

#define I2C_TIMEOUT_MAX_CYCLES  (100000UL)

DriverStatus_t i2c_write_byte_defensive(const uint8_t data) {
    uint32_t timeout_counter = I2C_TIMEOUT_MAX_CYCLES;

    I2C1->DR = data;

    while (!(I2C1->SR1 & I2C_SR1_TXE)) {
        if (--timeout_counter == 0U) {
            /* Hardware failure detected! Recover peripheral and abort */
            i2c_bus_hardware_reset();
            return DRIVER_STATUS_HARDWARE_TIMEOUT;
        }
    }

    return DRIVER_STATUS_OK;
}

16.3 Fail-Safe States & Actuator Quenching

When an unrecoverable fault is detected (sensor timeout, CRC checksum mismatch, brownout warning), defensive code must enforce immediate actuator quenching:

void safety_system_trigger_emergency_stop(const ErrorCode_t fault_code) {

    TIM1->BDTR &= ~TIM_BDTR_MOE; /* Main Output Enable OFF in Cortex-M timer */

    led_strobe_error_pattern(fault_code);

16.4 Stack Watermarking & Canary Words

Stack overflow is among the most silent and destructive failure modes in embedded C. Because microcontrollers lack Memory Management Units (MMUs) with paging and segmentation, a stack growing downwards collides silently with global .data and .bss sections.

A standard defensive technique is Stack Watermarking: during startup, the entire unused stack area is painted with a distinctive byte pattern (e.g., 0xA5A5A5A5). Periodically, a background diagnostic task inspects the memory from the base of the stack upwards to calculate the exact maximum historical stack consumption: 

extern uint32_t _stack_bottom; /* Defined in linker script */
extern uint32_t _stack_top;

#define STACK_WATERMARK_PATTERN (0xA5A5A5A5UL)

void stack_paint_canary(void) {
    uint32_t *p_curr = &_stack_bottom;
    /* Paint up to current stack pointer minus safety margin */
    uint32_t *p_sp = (uint32_t *)__get_MSP();

    while (p_curr < p_sp) {
        *p_curr++ = STACK_WATERMARK_PATTERN;
    }
}

size_t stack_get_free_bytes(void) {
    const uint32_t *p_curr = &_stack_bottom;
    size_t unused_words = 0;

    while (*p_curr == STACK_WATERMARK_PATTERN) {
        unused_words++;
        p_curr++;
    }

    return unused_words * sizeof(uint32_t);
}

16.5 Code Comparison: Blind vs. Defensively Engineered Firmware

Compare a naive parser that trusts external inputs with a defensively designed parser capable of repelling malformed network packets.

Compare Implementations: Packet Parser

❌ Blind & Fragile (Crash Magnet)

/* Trusts caller completely */
void process_packet(uint8_t *buffer) {
    uint8_t len = buffer[0];
    uint8_t payload[32];

    /* Buffer Overflow Vulnerability!
       If len > 32, stack is corrupted */
    for (int i = 0; i < len; i++) {
        payload[i] = buffer[1 + i];
    }
    execute_command(payload[0]);
}

Flaws: No null pointer check, no total buffer length parameter, unbounded array copy resulting in stack smashing if len > 32.

✔ Defensively Hardened

#define MAX_PAYLOAD_BYTES (32U)

DriverStatus_t process_packet(
    const uint8_t * const p_buf,
    const size_t          buf_len) 
{
    if ((p_buf == NULL) || (buf_len < 2U)) {
        return DRIVER_STATUS_INVALID_PARAM;
    }
    const uint8_t payload_len = p_buf[0];

    /* Strict Bounds Validation */
    if ((payload_len > MAX_PAYLOAD_BYTES) || 
        (buf_len < (size_t)(payload_len + 1U))) {
        return DRIVER_STATUS_BUFFER_OVERFLOW;
    }

    uint8_t payload[MAX_PAYLOAD_BYTES];
    for (size_t i = 0; i < payload_len; ++i) {
        payload[i] = p_buf[1U + i];
    }
    return execute_command(payload[0]);
}

Safety: Total length validation, payload clamp check, const correctness, status code return.

16.6 Interactive Knowledge Check

Test your comprehension of defensive programming techniques and failure mitigation.

1. Why is an unbounded spin loop like while (!(SPI1->SR & SPI_SR_RXNE)); considered dangerous in production firmware?
  • Because the compiler converts while loops to recursive function calls.
  • If an electrical fault or disconnected slave causes the flag to never assert, the CPU hangs forever.
  • Because SPI flags can only be read once per power cycle.
  • It disables all hardware interrupts automatically.
Explanation: Unbounded loops assume hardware works perfectly. Any physical wire disconnect or ESD latchup stalls the firmware permanently unless guarded by a bounded timeout.
2. What is "actuator quenching" in safety-critical firmware?
  • Cooling high-power MOSFETs with liquid nitrogen.
  • Immediately cutting drive signals (disabling PWM, de-energizing relays) upon detecting a fault to enter a safe passive state.
  • Increasing the actuator frequency to maximum speed during an error.
  • Writing configuration parameters to Flash memory.
Explanation: Actuator quenching ensures physical hardware (motors, heaters, valves) cannot cause harm when software loses valid sensor feedback or enters a fault state.
3. What is the defensive technique of "stack watermarking"?
  • Writing the programmer's name into the vector table.
  • Filling the unused stack space with a known pattern (e.g. 0xA5A5A5A5) at boot to measure maximum stack depth during operation.
  • Using hardware parity bits on stack registers.
  • Compressing stack frames using Huffman coding.
Explanation: By inspecting how much of the magic watermark pattern was overwritten during execution, developers can accurately calculate stack usage margins and prevent collisions.
4. What parameter must ALWAYS accompany a raw buffer pointer passed into a function?
  • A checksum of the function's bytecode.
  • The maximum capacity/length of the allocated buffer in bytes.
  • The memory bus clock frequency.
  • A pointer to the parent process ID.
Explanation: Without an explicit capacity parameter, a receiving function cannot verify whether writing data will overflow the buffer boundary.
5. Why is strcpy(dst, src) strictly banned under MISRA-C and defensive embedded standards?
  • It performs no bounds checking, causing unbounded buffer overflows if src exceeds dst.
  • It is only implemented in C++ compilers.
  • It consumes 4 KB of Flash memory per call.
  • It forces the CPU into Thumb mode.
Explanation: strcpy() copies until encountering a null byte with zero regard for destination capacity. Safer alternatives or custom bounded loop copies are required.
6. What is the purpose of checking if ((uintptr_t)ptr % 4 != 0) before casting a byte pointer to a 32-bit integer pointer on ARM Cortex-M0?
  • To verify the pointer is in ROM.
  • To avoid an unaligned memory access HardFault, which occurs on architectures that do not support unaligned 32-bit loads.
  • To enable floating-point hardware.
  • To check if the pointer is null.
Explanation: ARM Cortex-M0 and Cortex-M0+ cores lack hardware unaligned memory access support. Dereferencing an unaligned 32-bit address immediately triggers a UsageFault/HardFault.
7. How should a defensive function handle a null pointer argument?
  • Print an ASCII joke to the UART console.
  • Immediately return an explicit error code (e.g. STATUS_NULL_PTR) without dereferencing the pointer.
  • Assign the pointer to address 0x00000000.
  • Enter an infinite busy-wait loop.
Explanation: Checking for NULL at the top of the function and returning an error code prevents dereferencing an invalid address.
8. What does "graceful degradation" mean in embedded architecture?
  • Slowly decreasing the MCU voltage until the chip turns off.
  • Maintaining partial system functionality (e.g. basic safety monitoring) when non-critical components or sensors fail, rather than shutting down entirely.
  • Allowing flash memory to degrade without wear leveling.
  • Gradually dimming status LEDs.
Explanation: If a secondary sensor (e.g., ambient humidity) fails, graceful degradation keeps the primary motor control and thermal safety loops running safely rather than locking up.
9. What is a "Windowed Watchdog" (WWDG) and how does it improve defensive reliability over a standard watchdog?
  • It displays watchdog status in a graphical OLED window.
  • It triggers a reset not only if refreshed too late, but also if refreshed too early, detecting runaway loops that kick the watchdog prematurely.
  • It only operates during daytime windows.
  • It disables all flash writes during brownouts.
Explanation: A WWDG enforces both an upper and lower time limit for refresh. If buggy code gets stuck in a tight loop that repeatedly calls the feed function too quickly, the WWDG resets the MCU.
10. In a defensive C codebase, what should be done with unused switch cases?
  • Omit the default: label to save ROM space.
  • Always include a default: case that handles invalid states, logs an anomaly, and places the system in a safe fallback state.
  • Comment them out with preprocessor macros.
  • Jump directly to the vector table.
Explanation: Cosmic rays, electrical noise, or pointer corruptions can flip bits in an enum variable. A defensive default: block traps illegal states and prevents undefined execution paths.

16.7 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to build resilient firmware immune to hardware faults and data corruption.

Assignment 1: Bounded Hardware Timeout Wrapper

Task: Create a generic macro or inline function: WAIT_FOR_FLAG_TIMEOUT(reg, flag, timeout_us, status). Test it by deliberately disconnecting the MISO line on an SPI bus. Verify that the system reports a timeout status within 50 μs and does not freeze.

Assignment 2: Memory Alignment & Bounds Sanitizer

Task: Implement a defensive memory copy function: safe_mem_copy(uint32_t *p_dst, const uint32_t *p_src, size_t count_words). Verify that it checks for null pointers, verifies 4-byte address alignment on both buffers, and detects overlapping buffer memory regions.

Assignment 3: Stack Canary & High-Watermark Monitor

Task: Implement the stack watermark engine from Program 16.4 in your startup code. Write a recursive test function that consumes stack space incrementally. Verify that a background task detects when free stack falls below 128 bytes and triggers an orderly safety shutdown.

Assignment 4: Windowed Watchdog (WWDG) Timing Calibration

Task: Configure a hardware Windowed Watchdog with a lower refresh limit of 20 ms and an upper limit of 50 ms. Write a cooperative loop task that kicks the watchdog at 30 ms intervals. Intentionally trigger an early kick (at 5 ms) and verify that the MCU resets immediately.

Assignment 5: Fail-Safe Quench Interlock

Task: Build a simulated motor speed controller. Inject three distinct faults: (1) ADC disconnect, (2) Temperature over 85 °C, and (3) UART communication loss for > 500 ms. Verify that every fault cleanly executes the safety_system_trigger_emergency_stop() sequence within 2 milliseconds.
