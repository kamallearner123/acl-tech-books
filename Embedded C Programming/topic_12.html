Topic 12

Polling vs Interrupts

Every embedded peripheral interaction boils down to a fundamental architectural choice: should the processor repeatedly query the hardware status register (Polling), or should the hardware alert the processor asynchronously when an event occurs (Interrupts)?

While polling is conceptually simple and requires zero vector table configuration, it wastes millions of CPU cycles in busy-wait loops and burns battery power. Interrupts unlock high CPU utilization and microsecond reaction times, but introduce the hazards of asynchronous preemption: race conditions, shared memory corruption, priority inversion, and stack blowouts.

12.1 Comparative Analysis Matrix

Selecting between polling and interrupts requires evaluating latency, throughput, power consumption, and code complexity:

Evaluation Metric Polling (Busy-Wait) Interrupt-Driven Architecture
CPU Utilization 100% busy-wait during transactions; wastes CPU cycles. Near 0% idle; CPU computes background tasks or sleeps.
Response Latency Variable and high; depends on main loop execution period. Deterministic and immediate (~12 clock cycles on ARM Cortex-M).
Power Consumption High; core runs active clock cycles continuously. Ultra-low; CPU sleeps in WFI until an interrupt awakens it.
Software Complexity Trivial; linear code execution, no race conditions. Higher; requires volatile qualifiers, critical sections, and NVIC tuning.

12.2 Hardware Interrupt Mechanics & NVIC

On ARM Cortex-M microcontrollers, interrupt handling is governed by the Nested Vectored Interrupt Controller (NVIC). When a hardware peripheral asserts an interrupt line:

  1. Hardware Stacking: The processor automatically pushes 8 core registers onto the active stack: R0, R1, R2, R3, R12, LR, PC, xPSR in just 12 CPU clock cycles.
  2. Vector Fetch: Simultaneously, the NVIC reads the 32-bit ISR function address directly from the Vector Table in Flash memory.
  3. Execution: The CPU jumps directly to the C ISR function.
  4. Unstacking: Upon executing the special return code in LR (EXC_RETURN), hardware automatically pops the registers and restores the interrupted code.

12.3 Critical Sections & Atomic Access

Whenever a variable wider than the CPU data bus (e.g. a 64-bit millisecond counter on a 32-bit ARM, or a 16-bit int on an 8-bit AVR) or a multi-field structure is shared between the main loop and an ISR, a critical section is mandatory.

12.4 Hands-On Code Implementations

The following C implementation demonstrates atomic reading of a 64-bit shared timestamp counter using ARM assembly critical section primitives: 

/**
 * Program 12.1: Atomic 64-Bit Timekeeper with Nested Interrupt Protection
 * File: atomic_timer.c
 */

#include <stdint.h>
#include <stdbool.h>

/* 64-bit system tick counter updated asynchronously in SysTick ISR */
static volatile uint64_t s_system_uptime_ticks = 0ULL;

/**
 * @brief Enter Critical Section: saves previous interrupt mask state and disables IRQs.
 */
static inline uint32_t enter_critical_section(void) {
    uint32_t primask;
    /* Read active PRIMASK interrupt state */
    __asm volatile ("mrs %0, primask" : "=r" (primask));
    /* Disable interrupts */
    __asm volatile ("cpsid i" : : : "memory");
    return primask;
}

/**
 * @brief Exit Critical Section: restores previous interrupt mask state.
 */
static inline void exit_critical_section(uint32_t primask) {
    /* Restore saved PRIMASK */
    __asm volatile ("msr primask, %0" : : "r" (primask) : "memory");
}

/**
 * @brief Thread-safe atomic read of 64-bit uptime counter.
 * @return uint64_t Snapshot of uptime in ticks
 */
uint64_t get_system_uptime_atomic(void) {
    uint32_t mask = enter_critical_section();
    /* Atomic 64-bit copy: completely immune to ISR interleaving */
    uint64_t snapshot = s_system_uptime_ticks;
    exit_critical_section(mask);
    return snapshot;
}

/**
 * @brief 1 kHz Hardware SysTick Timer Interrupt Handler.
 */
void SysTick_Handler(void) {
    /* Incremented asynchronously every 1 millisecond */
    s_system_uptime_ticks++;
}

12.5 Buggy vs. Modern Safe Code Comparison

Directly disabling interrupts globally using __enable_irq() breaks nested calls if an outer function had intentionally disabled interrupts.

View Buggy/Legacy Code

Calling __enable_irq() unconditionally re-enables interrupts even if the outer calling function was inside its own critical section: 

/* BUGGY: Unconditionally enables interrupts, breaking outer critical sections */
void write_shared_data(uint32_t val) {
    __disable_irq();
    g_shared_reg = val;
    __enable_irq(); /* DANGER: Re-enables interrupts even if caller disabled them! */
}
Program 12.2-A: Broken Unconditional Interrupt Re-Enable

The modern pattern captures and restores the original PRIMASK register, cleanly supporting arbitrary critical section nesting: 

/* SAFE / PRODUCTION-GRADE: Nestable PRIMASK state capture */
void write_shared_data_safe(uint32_t val) {
    uint32_t primask = enter_critical_section();
    g_shared_reg = val;
    exit_critical_section(primask); /* Restores previous state cleanly */
}

Topic Quiz (10 Questions)

Test your understanding of polling limitations, interrupt mechanics, and critical sections.

1. What is the primary drawback of using busy-wait polling to wait for a UART character to arrive?
  • UART baud rates drift.
  • The CPU is 100% tied up executing tight loops, burning battery power and preventing other tasks from executing.
  • The compiler emits an error on polling loops.
  • It disables SRAM memory reads.
Polling monopolizes the processor in unproductive spin-loops, preventing sleep modes and wasting power.
2. On an ARM Cortex-M processor, how many core registers are automatically pushed onto the stack by hardware upon interrupt entry?
  • 4 registers
  • 8 registers (R0, R1, R2, R3, R12, LR, PC, xPSR)
  • 16 registers
  • 0 (all stacking is done by software)
Hardware automatically pushes the 8 caller-saved registers in 12 clock cycles, enabling standard C functions to act directly as ISRs without assembly wrappers.
3. What does the Nested Vectored Interrupt Controller (NVIC) enable on ARM Cortex-M processors?
  • Direct execution of Python scripts.
  • Hardware-managed interrupt prioritization, dynamic preemption of lower-priority ISRs, and tail-chaining.
  • Automatic Flash memory wear leveling.
  • Wireless communication over Wi-Fi.
The NVIC handles prioritized preemption and tail-chaining optimization in hardware without software overhead.
4. What is 'tail-chaining' in the ARM Cortex-M interrupt architecture?
  • Daisy chaining multiple microcontroller chips over SPI.
  • An optimization where the processor transitions directly to a pending interrupt without restoring and re-stacking registers, saving 24 clock cycles.
  • A software algorithm for linking lists.
  • A compiler warning.
Tail-chaining avoids redundant unstacking and re-stacking when another interrupt is pending as an ISR finishes, reducing switch latency to just 6 cycles.
5. Why is an atomic read required when reading a 64-bit variable on a 32-bit ARM Cortex-M processor?
  • 64-bit integers are illegal in C99.
  • The CPU requires two separate 32-bit load instructions; an interrupt can fire between the two instructions, resulting in corrupted data.
  • Flash cannot store 64-bit variables.
  • The compiler forces a hard fault.
A 32-bit CPU cannot read 64 bits in a single cycle. An ISR interleaving between the lower and upper word reads reads desynchronized halves.
6. What is the role of the PRIMASK register in ARM Cortex-M CPUs?
  • It stores the processor serial number.
  • A 1-bit register that masks all configurable interrupts when set to 1 (except HardFault and NMI).
  • It controls the PLL clock multiplier.
  • It holds the baud rate divider.
Setting PRIMASK via 'cpsid i' disables all interrupts with configurable priority, creating an atomic critical section.
7. What is 'Interrupt Jitter'?
  • Physical vibration of the PCB.
  • The timing variation between when a hardware interrupt request is asserted and when the first instruction of the ISR actually executes.
  • A bug in the linker script.
  • Fluctuation in supply voltage.
Jitter is caused by critical sections holding interrupts disabled or higher-priority ISRs executing when the event occurs.
8. What happens if an ISR does not clear its peripheral's hardware interrupt pending flag before exiting?
  • The peripheral is permanently powered off.
  • The interrupt controller immediately re-triggers the ISR upon exit, locking the CPU in an infinite interrupt loop and starving the main loop.
  • The compiler reports a warning.
  • The vector table is erased.
If the hardware status bit remains high, the NVIC observes an active interrupt condition and re-invokes the ISR endlessly.
9. What special return value placed in the Link Register (LR) by ARM hardware signals an exception return?
  • 0x00000000
  • EXC_RETURN (e.g. 0xFFFFFFFD or 0xFFFFFFF9)
  • 0xDEADBEEF
  • 0x08000000
When the CPU branches to an EXC_RETURN value (0xFFFFFFFx), hardware automatically initiates exception unstacking and mode restoration.
10. What is priority grouping in the ARM Cortex-M NVIC?
  • Grouping multiple C source files into an archive.
  • Splitting the 8-bit priority register into 'Preemption Priority' (which determines who preempts whom) and 'Subpriority' (which resolves simultaneous pending requests).
  • Sorting variables in SRAM.
  • A feature exclusive to Linux.
Priority grouping allows system architects to partition priority bits between preemption levels and tie-breaker subpriorities.

Hands-On Assignments

Execute these 5 laboratory assignments to master interrupt control, latency analysis, and atomic protection.

Assignment 1: Interrupt Response Latency Benchmarking

Task: Configure a GPIO input interrupt. In the ISR, set an output pin high as the very first line of code. Using an oscilloscope or logic analyzer, measure the time elapsed from the input pin rising edge to the output pin rising edge. Calculate the total latency in nanoseconds and CPU cycles.

Assignment 2: Nestable Critical Section Implementation

Task: Implement the nestable critical section functions enter_critical_section() and exit_critical_section() using inline assembly to save and restore PRIMASK. Write a test case with nested function calls and verify that interrupts remain disabled until the outermost function exits.

Assignment 3: NVIC Priority Preemption Experiment

Task: Configure two hardware timers: Timer 2 with priority 2 and Timer 3 with priority 1. In Timer 2's ISR, toggle a pin and enter a delay loop. Trigger Timer 3 during this delay. Using an oscilloscope, demonstrate that Timer 3 immediately preempts Timer 2 mid-execution.

Assignment 4: Polling vs. Interrupt CPU Utilization Audit

Task: Write a UART receive driver in polling mode. Count how many iterations of a background compute loop execute per second while receiving 100 bytes/sec. Then refactor to an interrupt-driven circular buffer and measure the 10x increase in background iterations.

Assignment 5: Infinite Interrupt Lockup Reproduction

Task: Configure an external GPIO interrupt. In the ISR, deliberately omit the code line that clears the pending flag in EXTI->PR. Run the program and observe in GDB how the processor becomes permanently trapped in the ISR, starving the main loop.
