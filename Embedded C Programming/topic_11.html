Topic 11

Events & Event Handling

Novice firmware is typically written as a sequential script: read sensor, delay 500 ms, toggle LED, transmit UART, repeat. In modern real-time systems, external inputs (button clicks, packet reception, timer expirations, fault conditions) occur asynchronously and unpredictably. A system that blocks waiting for one event misses all other inputs.

The event-driven paradigm fundamentally reorganizes firmware: instead of polling hardware in tight blocking loops, system components react asynchronously to discrete events. Hardware Interrupt Service Routines (ISRs) act as rapid event producers, posting structured event messages into a FIFO queue. The main background superloop acts as an event pump, dispatching events to registered handlers without ever blocking CPU cycles.

11.2 The Producer-Consumer Event Queue Pattern

The heart of reactive firmware is the decoupled Producer-Consumer Queue:

  • Producers (Hardware ISRs & Drivers): Detect physical events (GPIO edge, UART byte received, timer tick). They package an Event_t and push it into the queue in under 2 microseconds, then exit immediately.
  • Consumer (Main Superloop): Runs continuously. Pops events from the queue one at a time and dispatches them to state machines or application logic.

11.3 Hands-On Code Implementations

The following complete, thread-safe module implements an event queue, event signals, and an event pump in pure C: 

/**
 * Program 11.1: Interrupt-Safe Event Queue & Dispatcher Engine
 * File: event_engine.c
 */

#include <stdint.h>
#include <stdbool.h>
#include <stdio.h>

/* Event signal enumeration */
typedef enum {
    EVT_NONE = 0,
    EVT_TIMER_TICK,
    EVT_BUTTON_PRESSED,
    EVT_UART_PACKET_RX,
    EVT_BATTERY_LOW,
    EVT_CRITICAL_FAULT
} EventSignal_t;

/* Event message structure */
typedef struct {
    EventSignal_t signal;
    uint32_t      timestamp_ms;
    uint32_t      parameter;
} Event_t;

#define EVENT_QUEUE_CAPACITY 16U

typedef struct {
    Event_t  queue[EVENT_QUEUE_CAPACITY];
    volatile uint8_t head;
    volatile uint8_t tail;
    volatile uint8_t count;
} EventQueue_t;

static EventQueue_t s_event_queue = { .head = 0, .tail = 0, .count = 0 };

/**
 * @brief Thread-safe push of an event into the queue (Invoked from ISR or main).
 */
bool event_post(EventSignal_t sig, uint32_t param) {
    /* Critical section start: disable interrupts briefly if multi-threaded */
    __asm volatile ("cpsid i" : : : "memory");

    if (s_event_queue.count >= EVENT_QUEUE_CAPACITY) {
        __asm volatile ("cpsie i" : : : "memory");
        return false; /* Queue full */
    }

    s_event_queue.queue[s_event_queue.head].signal = sig;
    s_event_queue.queue[s_event_queue.head].timestamp_ms = 12000UL; /* In real MCU: get_sys_tick() */
    s_event_queue.queue[s_event_queue.head].parameter = param;

    s_event_queue.head = (s_event_queue.head + 1U) % EVENT_QUEUE_CAPACITY;
    s_event_queue.count++;

    __asm volatile ("cpsie i" : : : "memory");
    return true;
}

/**
 * @brief Pops the oldest event from the queue.
 */
bool event_get(Event_t * const evt_out) {
    if ((evt_out == NULL) || (s_event_queue.count == 0U)) {
        return false;
    }

    __asm volatile ("cpsid i" : : : "memory");
    *evt_out = s_event_queue.queue[s_event_queue.tail];
    s_event_queue.tail = (s_event_queue.tail + 1U) % EVENT_QUEUE_CAPACITY;
    s_event_queue.count--;
    __asm volatile ("cpsie i" : : : "memory");

    return true;
}

/* Event Dispatcher Handlers */
void handle_button_event(uint32_t button_id) {
    printf("[DISPATCH] Button %lu pressed! Toggling state.\n", (unsigned long)button_id);
}

void handle_battery_event(uint32_t millivolts) {
    printf("[DISPATCH] WARNING: Battery low (%lu mV)!\n", (unsigned long)millivolts);
}

/**
 * @brief The Central Event Pump: dispatches events to business logic.
 */
void event_pump_dispatch(void) {
    Event_t evt;
    if (event_get(&evt)) {
        switch (evt.signal) {
            case EVT_BUTTON_PRESSED:
                handle_button_event(evt.parameter);
                break;
            case EVT_BATTERY_LOW:
                handle_battery_event(evt.parameter);
                break;
            default:
                break;
        }
    }
}

11.4 Buggy vs. Modern Safe Code Comparison

Polling hardware pins inside a slow superloop causes missed user inputs because human button presses occur between slow polling iterations.

View Buggy/Legacy Code

This linear loop blocks for 500 ms on every iteration. Any button press that begins and ends during the delay is completely lost: 

/* BUGGY: Blocking loop misses asynchronous user inputs */
while (1) {
    /* If button is pressed during this 500ms sleep, it is MISSED! */
    delay_ms(500); 
    
    if (READ_BUTTON_PIN() == 0) {
        toggle_led();
    }
}
Program 11.2-A: Blocking Polling Loop with Missed Events

The event-driven solution captures button presses instantly via an external interrupt (EXTI) and dispatches them in the background without delay loops: 

/* SAFE / EVENT-DRIVEN: Hardware interrupt captures edge, superloop dispatches */
void EXTI0_IRQHandler(void) {
    /* 1. Clear hardware flag */
    EXTI->PR = (1U << 0);
    /* 2. Post event in < 2 microseconds */
    event_post(EVT_BUTTON_PRESSED, 1);
}

void main_loop(void) {
    while (1) {
        event_pump_dispatch(); /* Non-blocking event pump */
        /* CPU enters low-power sleep until next interrupt */
        __asm volatile ("wfi");
    }
}

Topic Quiz (10 Questions)

Test your understanding of event-driven architectures, queues, and reactive execution.

1. What is the fundamental principle of event-driven programming compared to traditional linear programming?
  • Event-driven code uses recursion instead of loops.
  • System execution flow is determined by asynchronous events (sensor edges, timers, packets) rather than a rigid sequential script.
  • It eliminates the need for C header files.
  • It requires an operating system.
Event-driven systems react to events as they arrive, preserving CPU responsiveness and eliminating busy-waiting.
2. In an event-driven microcontroller architecture, who typically acts as the event 'producer'?
  • The compiler
  • Hardware Interrupt Service Routines (ISRs) and peripheral drivers
  • The linker script
  • The terminal screen
ISRs detect hardware occurrences (timer ticks, GPIO edges, UART byte ready) and post events into the event queue.
3. What data structure is universally used to decouple event producers from event consumers?
  • A binary search tree
  • A FIFO (First-In, First-Out) circular ring buffer
  • A dynamic heap linked list
  • A hash map
A statically allocated circular FIFO ring buffer provides O(1) deterministic insertion and retrieval without dynamic memory allocation.
4. Why must an event queue's push operation be protected by a critical section (e.g. disabling interrupts)?
  • To increase CPU clock speed.
  • To prevent race conditions where a higher-priority interrupt preempts the main loop while it is updating queue indices.
  • To erase Flash memory.
  • To enable C++ exceptions.
Updating shared head/tail/count variables non-atomically allows an ISR to interleave, corrupting queue indices and losing events.
5. What happens when an event queue overflows (is full and a new event arrives)?
  • The microcontroller automatically reboots.
  • The queue must drop the event (or oldest event) gracefully and record an error telemetry counter without hanging.
  • Memory is allocated from the heap.
  • The compiler throws a warning.
Robust embedded queues reject additions when full, return false, and increment an overflow counter for diagnostics.
6. What is the role of the 'Event Pump' (or Event Dispatcher)?
  • It cools down the CPU.
  • A loop in the background thread that continuously pops events from the queue and routes them to appropriate handler functions.
  • It flashes the firmware over JTAG.
  • It generates random numbers.
The event pump is the central engine that drains the queue and executes corresponding state machine actions.
7. What low-power ARM instruction is called in the event pump when the event queue is empty?
  • NOP
  • WFI (Wait For Interrupt)
  • BKPT
  • SVC
WFI halts the CPU clock, entering sleep mode until an interrupt occurs, dramatically cutting battery power consumption when idle.
8. Why is keeping ISR execution time under a few microseconds critical in event-driven systems?
  • To prevent the crystal from drifting.
  • To ensure the CPU is immediately available to service subsequent high-priority interrupts without latency jitter.
  • To save RAM space.
  • To avoid triggering compiler optimizations.
Short ISRs package events and defer heavy processing to the main loop, minimizing interrupt latency across all peripherals.
9. What design pattern combines an event queue, a private thread/loop, and a finite state machine?
  • Singleton Pattern
  • Active Object Pattern (Actor Model)
  • Factory Pattern
  • Observer Pattern
The Active Object pattern encapsulates a dedicated event queue and state machine, ensuring message-passing concurrency without shared-memory locks.
10. In C, what is the best way to associate event signals with specific data payloads without wasting memory?
  • Use an array of void pointers with malloc().
  • Use a tagged union inside the event structure, sharing memory across different event data types.
  • Store everything as an ASCII string.
  • Use global variables for each event.
A tagged union allows different event types (e.g. keyboard char vs ADC 32-bit int) to share the same payload byte space efficiently.

Hands-On Assignments

Execute these 5 laboratory assignments to master event-driven architecture and message passing.

Assignment 1: Event Queue Saturation Test

Task: Implement an event queue with a capacity of 8 events. Write a test loop that attempts to post 12 consecutive events without draining the queue. Verify that the queue gracefully rejects the final 4 events, returns false, and increments an overflow_count metric.

Assignment 2: EXTI Push Button Event Producer

Task: Configure a push button on GPIO pin PA0 to generate an external interrupt (EXTI0). In the ISR, clear the pending flag and post an EVT_BUTTON_PRESS event to the event queue. In the main superloop, pop and handle the event by toggling an LED.

Assignment 3: Tagged Union Event Structure

Task: Create an event structure containing a tagged union supporting three payload types: (1) 32-bit ADC voltage, (2) 8-bit keypad character, and (3) an enum error code. Author a dispatcher that uses a switch statement on the signal to decode the correct union field.

Assignment 4: Low-Power WFI Event Pump

Task: In your main loop, drain and handle all pending events in the queue. When the queue is completely empty, invoke __WFI(). Connect an oscilloscope or current probe to measure the board's power consumption drop when waiting in sleep mode.

Assignment 5: Multi-Priority Event Queues

Task: Expand the engine to maintain two separate queues: a High-Priority Queue (for emergency stop faults and over-temperature alerts) and a Normal-Priority Queue (for user UI and routine telemetry). Ensure the event pump always exhausts all high-priority events before servicing normal events.
