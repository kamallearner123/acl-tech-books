⚡ Exactly What Happens When We LOAD the Program (Flashing Phase)

Target: Flash Array @ 0x08000000

When you click "Run" or "Flash" in your toolchain (or execute STM32_Programmer_CLI), the computer does not execute your C code. Instead, the binary is converted into electrical programming pulses to write non-volatile memory bits:

01
Host PC Sends Firmware Packets over USB
The PC flashing utility reads firmware.bin or extracts loadable sections from firmware.elf, packaging 64-byte USB packets to the on-board ST-LINK MCU.
02
ST-LINK Halts the Cortex-M4 CPU Core via SWD
ST-LINK asserts the NRST pin or writes to the Debug Halting Control and Status Register (DHCSR) over the 2-wire Serial Wire Debug lines (SWDIO and SWCLK). The CPU freezes immediately.
03
Flash Memory Controller Unlocks Security Registers
To prevent accidental erasure from runaway code, the STM32 Flash control register (FLASH_CR) is locked by default. ST-LINK writes unlock keys KEY1 = 0x45670123 and KEY2 = 0xCDEF89AB into FLASH_KEYR.
04
Internal Charge Pump Erases Target Flash Sectors
Flash memory cannot overwrite a 0 with a 1; it must first be erased to all 0xFF bytes. An internal charge pump steps up voltage to ~12V to tunnel electrons out of the floating gates of sectors 0 through 3.
05
32-Bit Words Burned Row-by-Row into Flash starting at 0x08000000
Machine instructions are clocked into the Flash Programming Data Register 32 bits at a time. The first two 32-bit words written are the Initial Stack Pointer (_estack) and the Reset_Handler Address!
06
Verification Checksum Read-Back
ST-LINK reads back all programmed flash memory locations and computes a CRC-32 hash to guarantee that zero bit-flip errors occurred during burning.
07
Hardware Reset Pulse Releases MCU to Run
The programmer pulls NRST LOW for 20ms and then releases it HIGH, handing control over to the ARM Cortex-M silicon core. The COM LED stops blinking red and turns solid green.

🚀 Exactly What Happens When We RUN the Program (Execution Phase)

Target: CPU Core • SRAM • Peripherals

Once reset is released, the physical semiconductor takes over autonomously at 84 million cycles per second. Notice how execution flows from hardware vector registers into memory initialization, and finally into GPIO, PIR, and UART peripherals:

01
Power Stabilizes & Hardware Loads Vector Table Words
Internal Power-On Reset (POR) comparator detects VDD > 1.7V. CPU reads address 0x08000000 and loads it into MSP (R13). Then reads 0x08000004 and loads it into PC (R15).
02
Reset_Handler Copies .data from Flash to RAM & Zeros .bss
Before your C code starts, a tight assembly loop copies initial variable values from Flash (LMA) into volatile SRAM (VMA at 0x20000000), and fills the .bss section with zeros.
03
SystemInit() Synthesizes 84 MHz System Clock (PLL)
Switches the CPU clock from the uncalibrated 16 MHz internal RC oscillator (HSI) to the high-accuracy 8 MHz quartz crystal (HSE). The Phase-Locked Loop (PLL) multiplies this to 84 MHz HCLK and sets Flash wait states to 2.
04
main() is Reached: HAL_Init() Configures SysTick (1 ms)
The application entry point begins! HAL_Init() sets NVIC interrupt priority grouping and configures the 24-bit SysTick hardware countdown timer to generate an interrupt every 1.0 millisecond for HAL_Delay().
05
RCC Clock Gating Powers GPIOA, GPIOB, and USART2 Buses
The MCU enables bits in RCC->AHB1ENR and RCC->APB1ENR. Without this step, writing to GPIO or UART registers would cause a bus fault because peripheral clocks are gated off to conserve battery power!
06
GPIO Driver Sinks Current → Green LED LD2 Emits Light
Firmware writes to GPIOA->BSRR bit 5. The silicon P-MOSFET turns ON, driving physical pin PA5 to 3.3V. 8 milliamperes of current flow through the 510-ohm resistor into LED LD2, exciting photons!
07
PIR Motion Sensor Drives PB0 HIGH → Schmitt Trigger Latches
When someone walks in front of the pyroelectric lens, the PIR module drives pin PB0 to 3.3V. The internal Schmitt trigger cleans up noise and sets bit 0 of GPIOB->IDR, which firmware reads or detects via EXTI0.
08
USART2 Serializes ASCII Bytes onto PA2 TX Wire @ 115,200 Baud
HAL_UART_Transmit() writes byte 'M' into USART2->DR. The hardware shift register shifts out 1 Start bit, 8 data bits, and 1 Stop bit at 8.68 µs per bit, streaming text to the ST-LINK USB Virtual COM Port!

Writing the LED Blink Program

Goal: Understand HAL APIs, system clock setup, and GPIO electrical drive.
Scenario 02

⚠️ Real-World Problem

Beginners write while(1) { toggle(); } without initializing clocks or configuring the pin direction register, leaving the LED permanently dead.

👀 What Student Observes

An on-board green LED flashes smoothly every 500 milliseconds in rhythm with physical voltage transitions between 0V and 3.3V on pin PA5.

⚙️ What is Happening Internally

HAL_Init() sets Flash latency and SysTick at 1ms. SystemClock_Config() engages the PLL at 84MHz. MX_GPIO_Init() enables AHB1 clock and sets MODER to Output. HAL_GPIO_TogglePin() flips bit 5 of the Output Data Register (ODR). The physical MOSFET push-pull driver pulls the external pin to VDD (3.3V), sourcing 8mA through the current-limiting resistor to excite the LED diode junction.

int main(void)
{
    HAL_Init();               // Reset peripherals, initialize Flash & SysTick
    SystemClock_Config();     // Configure clock tree (HCLK = 84 MHz)
    MX_GPIO_Init();           // Configure PA5 as push-pull output

    while (1)
    {
        HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5); // Invert pin state
        HAL_Delay(500);                        // Non-blocking SysTick wait (500 ms)
    }
}
int main(void)
{
    // 1. Enable AHB1 clock for GPIOA port
    RCC->AHB1ENR |= (1 << 0);

    // 2. Set Pin 5 as General Purpose Output (MODER[11:10] = 01)
    GPIOA->MODER &= ~(3 << (5 * 2));
    GPIOA->MODER |=  (1 << (5 * 2));

    while (1)
    {
        // 3. Atomically toggle Pin 5 via Output Data Register
        GPIOA->ODR ^= (1 << 5);

        // Approximate busy-wait loop
        for (volatile int i = 0; i < 500000; i++);
    }
}
🔬 Deep-Dive: What Really Happens Inside the GPIO Peripheral

1. The CPU writes a 32-bit word across the AHB1 bus matrix to physical memory address 0x40020014 (GPIOA_ODR).

2. The internal flip-flop latches the updated bit value on the next peripheral clock edge.

3. The latch drives the gate of two complementary MOSFETs (P-MOS on top connected to VDD, N-MOS on bottom connected to VSS).

4. In push-pull mode, turning on the P-MOS establishes a low-impedance (~25Ω) path to 3.3V, causing electrons to flow out of the pin pad.

🧪 Check Your Understanding

What happens if you omit the call to enable the GPIO port clock in the RCC (Reset and Clock Control) register?

A. The LED blinks at half its normal speed
B. Writes to GPIO registers are ignored or trigger a bus fault because peripheral logic is unpowered
C. The compiler reports an unresolved symbol error
D. The pin automatically defaults to an analog input mode
Correct! Microcontrollers use clock-gating to conserve energy. Without activating the AHB1 clock to GPIOA, the entire register block remains dormant.
Common Mistake Using active-high assumptions for all boards. Some boards wire LEDs between VDD and the pin (active-low), meaning writing 0 turns the LED ON!
Practical Takeaway Always consult the board schematic to check pin assignments (e.g., Nucleo-F401RE uses PA5, Nucleo-F103RB uses PA5, Discovery uses PD12-PD15).

Compilation and Assembly

Goal: Witness C statements translate into Cortex-M Thumb machine instructions.
Scenario 04

⚠️ Real-World Problem

Engineers assume a single line of C code executes in one clock cycle, leading to failed timing constraints in high-speed bit-banging.

👀 What Student Observes

One C line like GPIOA->ODR ^= (1 << 5); turns into four distinct assembly instructions: LDR, LDR, EOR, and STR.

⚙️ What is Happening Internally

The compiler translates the Abstract Syntax Tree into ARM Thumb-2 instructions. Because Cortex-M is a Load/Store RISC architecture, the ALU cannot directly manipulate bits in physical peripheral registers. The processor must load the address into a general-purpose register, read the value over the bus, modify the bit in an internal register, and store the result back to memory.

C to Assembly Step-by-Step Translation (Read-Modify-Write)
High-Level C Statement:
GPIOA->ODR ^= (1 << 5);
Invert bit 5 of the GPIOA Output Data Register located at 0x40020014.
Generated Cortex-M Thumb Assembly:
ldr r0, =0x40020000 /* Load GPIOA base address */
ldr r1, [r0, #0x14] /* Read current ODR into r1 */
eor r1, r1, #32 /* XOR bit 5 with 1 (toggle) */
str r1, [r0, #0x14] /* Write back modified value */
Compiler Flags Explained 
# Compile without linking (-c) for Cortex-M4 with Thumb instruction set:
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 -O2 -c main.c -o main.o

# Flags Breakdown:
# -mcpu=cortex-m4       : Target processor architecture
# -mthumb               : Emit 16-bit and 32-bit compact Thumb-2 instructions
# -mfloat-abi=hard      : Use hardware Floating Point Unit registers directly
# -c                    : Stop after compilation/assembly; do NOT run the linker

🧪 Check Your Understanding

Why does a Cortex-M processor require both an LDR (Load) and an STR (Store) instruction to toggle an I/O bit in ODR?

A. ARM Cortex-M is a Load/Store architecture; arithmetic and bitwise logic only operate on internal CPU registers
B. The memory bus cannot handle 32-bit operations
C. The peripheral bus requires two clock cycles to wake up
D. The compiler intentionally slows down execution to prevent bus saturation
Correct! Unlike CISC architectures like x86 that have direct memory-modifying instructions, ARM requires loading data into CPU registers (R0-R12) before ALU manipulation.
Common Mistake Forgetting -mthumb when invoking GCC manually, causing the toolchain to emit 32-bit ARM instructions that Cortex-M microcontrollers cannot decode, triggering an immediate HardFault!
Practical Takeaway For atomic pin changes that don't suffer from interrupt race conditions during read-modify-write, use the BSRR (Bit Set/Reset Register) instead of ODR!

Object Files and Unresolved References

Goal: Understand symbol tables, export bindings, and why .o files cannot run alone.
Scenario 05

⚠️ Real-World Problem

A student encounters the dreaded error: undefined reference to 'HAL_Init' and fruitlessly searches for syntax errors in their C code.

👀 What Student Observes

main.c compiles cleanly into main.o, but the build halts with an unresolved reference error during the final linking step.

⚙️ What is Happening Internally

An object file (.o) is an isolated module of machine code. When main.c calls HAL_Init(), the compiler does not know where in flash memory that function will physically reside. It emits a branch placeholder instruction with address 0x00000000 and creates a record in the Relocation Symbol Table marking HAL_Init as UND (Undefined).

Linker and Linker Script

Goal: Master physical address placement for Flash, RAM, .text, .data, and .bss.
Scenario 06

⚠️ Real-World Problem

Firmware builds fine but crashes immediately on boot because code was placed into volatile RAM or RAM variables were mapped past physical memory bounds.

👀 What Student Observes

The linker script (.ld) assigns every byte an exact 32-bit physical address starting at 0x08000000 for Flash and 0x20000000 for SRAM.

⚙️ What is Happening Internally

The GNU Linker takes all .o files, resolves symbol addresses, and organizes them according to the rules in stm32.ld. It places .isr_vector at the flash origin, appends .text (code) and .rodata (constants), assigns .data a Load Memory Address (LMA) in Flash and Virtual Memory Address (VMA) in RAM, and allocates space for .bss, Stack, and Heap in RAM.

🧪 Check Your Understanding

Why does the .data section have two addresses (an LMA in Flash and a VMA in RAM)?

A. It prevents hackers from accessing variable values
B. RAM loses its contents when power is turned off; initial values must be stored in permanent Flash and copied into RAM at boot
C. The ARM core requires duplicate copies for error parity check
D. Flash memory cannot be read at runtime
Correct! Global variables like int count = 42; must retain '42' after power loss (stored in Flash LMA), but need write access at runtime (executed from RAM VMA).
Common Mistake Assuming the Stack starts at 0x20000000. On ARM Cortex-M, the stack is full-descending: it starts at the top of RAM (e.g., 0x20018000) and grows downward!
Practical Takeaway Examine the map file (-Wl,-Map=firmware.map) after every build to monitor flash and RAM utilization.

What Happens When Power is Switched On?

Goal: Master the Cortex-M hardware reset sequence, MSP loading, and Reset_Handler.
Scenario 10

⚠️ Real-World Problem

Students believe main() is the very first function executed by the microcontroller when power is applied.

👀 What Student Observes

Upon power-up, hundreds of machine instructions execute to initialize memory and clocks before the CPU ever reaches the first line of main().

⚙️ What is Happening Internally

The ARM Cortex-M hardware follows a fixed architectural startup model: 1. When VDD rises above the Power-On Reset (POR) threshold (~1.7V), reset is released. 2. The hardware automatically reads 32-bit word 0 from address 0x08000000 and loads it into the Main Stack Pointer (MSP). 3. The hardware reads 32-bit word 1 from address 0x08000004 and loads it into the Program Counter (PC). 4. The CPU begins executing instructions at the address pointed to by PC, which is the Reset_Handler assembly function!

1. VDD Stable → Power-On Reset (POR) released
2. Boot Pins Sampled (BOOT0=0 selects internal Flash at 0x08000000)
3. CPU fetches Word 0 @ 0x08000000 → Loaded into MSP (Initial Stack Pointer)
4. CPU fetches Word 1 @ 0x08000004 → Loaded into PC (Reset_Handler Address)
5. Jump to Reset_Handler: Copy .data from Flash to RAM & Zero .bss
6. Call SystemInit() (Configure basic clocks & FPU coprocessor)
7. Call __libc_init_array() (C++ static constructors) → Jump to main()

Startup Memory Initialization Algorithm (in C) 
/* Symbols provided by the linker script (.ld): */
extern uint32_t _sidata; /* Start of .data values in Flash */
extern uint32_t _sdata;  /* Start of .data in RAM */
extern uint32_t _edata;  /* End of .data in RAM */
extern uint32_t _sbss;   /* Start of .bss in RAM */
extern uint32_t _ebss;   /* End of .bss in RAM */

void copy_data_and_zero_bss(void)
{
    // 1. Copy initialized data from Flash to RAM
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;
    while (dst < &_edata) {
        *dst++ = *src++;
    }

    // 2. Zero-out the uninitialized BSS section in RAM
    dst = &_sbss;
    while (dst < &_ebss) {
        *dst++ = 0;
    }
}

Polling versus Interrupt (EXTI)

Goal: Contrast CPU busy-waiting against asynchronous event-driven hardware interrupts.
Scenario 15

⚠️ Real-World Problem

A fast 5-millisecond sensor pulse is missed because the CPU was blocked inside a 500ms HAL_Delay() loop.

👀 What Student Observes

⚙️ What is Happening Internally

In Polling, the CPU constantly burns power asking "has the pin changed?". With Interrupts, the pin is connected to the External Interrupt Controller (EXTI) edge-detector hardware. When a rising edge occurs, EXTI asserts an interrupt line to the Nested Vectored Interrupt Controller (NVIC). The NVIC automatically pushes registers R0-R3, R12, LR, PC, and xPSR onto the Stack (hardware stacking), updates PC to the ISR address, and begins running the handler in under 12 clock cycles!

1. Loop starts
2. Read IDR register
3. If no motion → Wait 100ms
4. Repeat forever...
Drawback: High latency, 100% CPU waste, misses fast pulses

Method B: EXTI Interrupt (Event-Driven)

1. CPU sleeps or computes other tasks
2. PIR edge hits hardware EXTI0 line
3. NVIC pre-empts CPU in 12 cycles
4. HAL_GPIO_EXTI_Callback() fires

Firmware Update with a Bootloader

Goal: Understand in-field firmware updates, VTOR vector relocation, and cryptographic security.
Scenario 19

⚠️ Real-World Problem

An IoT product deployed on a customer's roof needs a bug fix, but opening the weather-sealed enclosure to attach an ST-LINK programmer is impossible.

👀 What Student Observes

The device receives a new application.bin over UART or Wi-Fi, validates its digital signature, flashes it to sector 4, and boots the new firmware.

⚙️ What is Happening Internally

Flash memory is split into two zones: 1. Custom Bootloader (0x08000000 - 0x08007FFF): Runs on reset, checks if an update is requested, downloads bytes, and verifies integrity. 2. User Application (0x08008000 onward): The active product firmware. To jump to the application, the bootloader re-points the Vector Table Offset Register (SCB->VTOR) to 0x08008000, loads the application's initial MSP from 0x08008000, and branches to the application's Reset_Handler address at 0x08008004.

#define APP_START_ADDRESS 0x08008000

typedef void (*pFunction)(void);

void jump_to_application(void)
{
    uint32_t app_stack = *(__IO uint32_t*) APP_START_ADDRESS;
    pFunction app_entry = (pFunction) *(__IO uint32_t*) (APP_START_ADDRESS + 4);

    // 1. Disable all interrupts and clear pending flags
    __disable_irq();

    // 2. Relocate Vector Table to application base
    SCB->VTOR = APP_START_ADDRESS;

    // 3. Initialize Stack Pointer with application's stack top
    __set_MSP(app_stack);

    // 4. Branch to application Reset_Handler
    app_entry();
}

What is the critical difference between a CRC checksum and an ECDSA Digital Signature in firmware updates?

Common Mistake Forgetting to update the linker script of the application! If the application is linked at 0x08000000 but flashed at 0x08008000, all absolute function and vector calls will jump to the wrong memory!
Practical Takeaway Always implement a "Rollback" dual-bank mechanism so that if a newly flashed firmware fails to boot, the bootloader automatically restores the previous working version.

Troubleshooting Scenarios: 10 Diagnostic Lab Cards

Goal: Rapidly diagnose and fix the top 10 hardware, toolchain, and firmware failures.
Scenario 20

⚠️ Real-World Problem

Embedded systems bugs manifest as silent freezes, infinite loops in HardFault_Handler, or baffling electrical misbehavior.

👀 What Student Observes

A systematic diagnostic method separates software bugs, electrical wiring mistakes, and toolchain misconfigurations.

🔴 1. LED Never Turns On
Likely Causes: GPIO clock not enabled in RCC; pin set to input mode; reverse LED diode polarity; missing ground.
Measurement: Measure voltage between pin and GND with multimeter (expect 3.3V).
Fix: Call __HAL_RCC_GPIOA_CLK_ENABLE() and check anode/cathode polarity.
🟡 2. LED is Always ON (Stuck)
Likely Causes: Active-low circuit wired to VDD; CPU stuck in infinite loop before toggle; delay is zero.
Measurement: Attach debugger to see if PC is trapped in an Error_Handler.
Fix: Invert logic (write GPIO_PIN_RESET to turn on) or fix blocking function.
⚡ 3. PIR Sensor Random Triggers
Likely Causes: Floating input pin; PIR stabilization warm-up period not observed; noisy 5V power supply.
Measurement: Oscilloscope shows 50Hz hum picked up on floating wire.
Fix: Configure internal pull-down resistor (GPIO_PULLDOWN) and add 45s boot delay.
4. UART Displays Garbage Text
Likely Causes: Baud rate mismatch; incorrect HSE/HSI clock config; missing common ground wire.
Measurement: Measure bit-width on TX line with scope (115200 baud = 8.68 µs).
Fix: Ensure terminal matches firmware baud rate and connect board GND to USB adapter GND.
🛑 5. Firmware Won't Start After Flash
Likely Causes: BOOT0 pin pulled HIGH (boots into system ROM); flashed to wrong address; corrupt vector table.
Measurement: Check BOOT0 jumper (must be connected to GND for Flash boot).
Fix: Pull BOOT0 to GND and verify flash base is 0x08000000.
🔌 6. Debugger Cannot Connect
Likely Causes: Firmware disabled SWD pins (PA13/PA14); chip in deep standby sleep; loose USB.
Measurement: ST-LINK utility reports "Cannot connect to target".
Fix: Select "Connect Under Reset" in programmer settings and hold black NRST button.
⚠️ 7. Works in Debugger, Fails on Reset
Likely Causes: Uninitialized global variables; debugger initializes clocks/RAM automatically; floating reset.
Measurement: Device runs when GDB attaches, dies when powered from wall adapter.
Fix: Ensure startup BSS zeroing loop is executing and power supply provides >500mA.
💥 8. Immediate HardFault_Handler
Likely Causes: Null pointer dereference; unaligned 32-bit access; calling function pointer without Thumb bit set (bit 0 must be 1).
Measurement: Read Configurable Fault Status Register (SCB->CFSR).
Fix: Check Stack Pointer (SP) in GDB to inspect caller address in Link Register (LR).
📦 9. Bootloader BIN Doesn't Run
Likely Causes: VTOR not updated before jump; application stack pointer invalid; interrupts not disabled.
Measurement: Application vector table word 0 does not match RAM range (0x20000000-0x20020000).
Fix: Set SCB->VTOR = APP_ADDRESS and call __disable_irq() prior to jump.
📏 10. ELF vs. BIN Size Discrepancy
Likely Causes: Confusing host debugging symbols with target executable machine code.
Measurement: Run arm-none-eabi-size on ELF file.
Fix: Ignore ELF byte size on disk; use text + data from size output.

📖 Searchable Embedded Systems Glossary

Instant reference definitions for key toolchain, ARM Cortex-M, and peripheral terms.

Preprocessor
Initial toolchain stage that performs textual inclusion of header files (#include) and macro substitution (#define) before C compilation.
Compiler (cc1)
Translates high-level C code into target-specific assembly language instructions for the ARM Cortex-M architecture.
Assembler (as)
Converts human-readable assembly instructions (LDR, STR, MOV) into raw binary relocatable machine opcodes in an object file (.o).
Linker (ld)
Combines multiple object files, resolves function symbols, and binds sections to physical memory addresses based on a linker script.
Linker Script (.ld)
Configuration file defining physical memory regions (FLASH, RAM) and dictating where code (.text), constants (.rodata), and data (.data, .bss) sit.
ELF (Executable & Linkable Format)
Standard structured binary file format containing machine code, section headers, symbol tables, and DWARF debugging information.
DWARF
Standardized debugging data format embedded in ELF files that allows GDB to map memory addresses back to specific C source file lines and variable names.
Intel HEX (.hex)
ASCII text representation of binary data where each line is a record containing byte counts, 32-bit memory addresses, data, and checksums.
Raw Binary (.bin)
Contiguous binary stream of executable bytes with zero headers or address metadata, flashed directly to a known starting offset.
Vector Table
Array of 32-bit exception and interrupt handler function pointers located at base memory (0x08000000) whose first entry is the initial Stack Pointer.
Reset_Handler
The first assembly function executed by the Cortex-M processor upon release of reset; copies .data to RAM, zeros .bss, and calls main().
Main Stack Pointer (MSP)
Hardware register (SP / R13) holding the memory address of the current stack frame, automatically loaded from address 0x08000000 at power-on.
Program Counter (PC)
CPU register (R15) holding the memory address of the current instruction being fetched and executed.
BSRR (Bit Set/Reset Register)
Dedicated 32-bit GPIO register allowing atomic setting and clearing of output pins without read-modify-write race conditions.
EXTI (Extended Interrupts Controller)
STM32 hardware peripheral monitoring GPIO pin state transitions (rising/falling edges) and routing interrupt requests to the NVIC.
NVIC
Nested Vectored Interrupt Controller: on-core ARM hardware managing interrupt priorities, nesting, and sub-12-cycle low-latency ISR pre-emption.
UART / USART
Universal Asynchronous Receiver-Transmitter: serial communication peripheral transmitting 8N1 bit-streams using fixed baud rate timing.
PIR Sensor
Passive Infrared Sensor: pyroelectric sensor detecting changes in thermal radiation caused by human movement, driving a digital GPIO HIGH.
VTOR
Vector Table Offset Register in the System Control Block (SCB) allowing software to dynamically relocate the interrupt vector table to RAM or an application offset.
SWD (Serial Wire Debug)
Two-wire debug protocol (SWDIO and SWCLK) replacing JTAG to flash microcontrollers and inspect CPU registers via hardware debug probes.
