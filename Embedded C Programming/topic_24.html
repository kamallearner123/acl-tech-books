Topic 24

Application, Driver, HAL & BSP Layered Architecture

Software entropy is the natural tendency of codebases to become disorganized over time. In bare-metal C systems, entropy manifests when high-level business rules (e.g. heating control logic or cloud telemetry packaging) intermingle directly with low-level hardware manipulations (e.g. toggling GPIO bits or configuring timer registers). When hardware revisions occur or chip shortages strike, the entire software stack collapses.

The gold standard for scalable, maintainable firmware is the 4-Tier Layered Architecture: separating software into the Application, Device Driver, Hardware Abstraction Layer (HAL), and Board Support Package (BSP) layers. This physical division of responsibilities guarantees modularity, testability, and portability.

24.1 The 4-Tier Firmware Architecture Hierarchy

Each layer has a clearly bounded responsibility and communicates strictly through well-defined interface contracts:

Figure 24.1: The 4-Tier Firmware Layer Hierarchy (Dependencies Downward Only)

24.2 The Golden Rules of Layered Separation

  1. Dependencies Point Downwards Only: Higher layers can call lower layers; lower layers must never include headers from or call functions in higher layers.
  2. Upward Communication via Callbacks & Events: When a hardware event occurs (e.g. UART byte received or button pressed), the BSP/HAL notifies higher layers asynchronously via registered callbacks or by posting an event to an event queue.
  3. No Layer Skipping: The Application layer must never reach around Drivers and HAL to directly toggle a BSP hardware register (GPIOA->BSRR = ...). Bypassing layers introduces silent couplings that destroy testability.
  4. Complete Silicon Isolation: Files in Layer 1 and Layer 2 must never include vendor chip headers (such as stm32f4xx.h or samd21.h). Vendor headers belong exclusively to Layer 4 (BSP).

24.3 Layer 4: The Board Support Package (BSP)

The Board Support Package binds the abstract software to a specific physical printed circuit board (PCB). It maps schematic net names to physical microcontroller pin multiplexing and clock configuration: 

/* bsp_nucleo_f401.h: Board Support Package for Nucleo Development Board */
#ifndef BSP_NUCLEO_F401_H
#define BSP_NUCLEO_F401_H

#include <stdint.h>
#include <stdbool.h>

/* Schematic Signal Abstractions */
typedef enum {
    BSP_LED_GREEN = 0,
    BSP_LED_MAX
} BspLed_t;

typedef enum {
    BSP_BTN_USER = 0,
    BSP_BTN_MAX
} BspButton_t;

void bsp_system_init(void);
void bsp_led_set(const BspLed_t led, const bool state);
void bsp_led_toggle(const BspLed_t led);
bool bsp_button_read(const BspButton_t btn);

#endif /* BSP_NUCLEO_F401_H */
Program 24.1: Board Support Package (BSP) Public Interface

Notice that bsp_nucleo_f401.h exposes human-meaningful board concepts (BSP_LED_GREEN, BSP_BTN_USER). It hides whether the green LED is connected to Port A Pin 5 or Port B Pin 13.

24.4 Layer 3: Hardware Abstraction Layer (HAL) Contract

The HAL defines standard bus communication protocols (I2C, SPI, UART, CAN). It decouples external component drivers (e.g. an OLED display or EEPROM) from the specific microcontroller peripheral: 

/* hal_i2c.h: Generic Portable I2C Master Interface */
#ifndef HAL_I2C_H
#define HAL_I2C_H

#include <stdint.h>
#include <stddef.h>

typedef enum {
    HAL_I2C_OK = 0,
    HAL_I2C_ERR_NACK,
    HAL_I2C_ERR_BUS_BUSY,
    HAL_I2C_ERR_TIMEOUT
} HalI2cStatus_t;

HalI2cStatus_t hal_i2c_master_transmit(
    const uint8_t  device_addr_7bit,
    const uint8_t * const p_data,
    const size_t   len_bytes,
    const uint32_t timeout_ms);

HalI2cStatus_t hal_i2c_master_receive(
    const uint8_t  device_addr_7bit,
    uint8_t * const p_buffer,
    const size_t   len_bytes,
    const uint32_t timeout_ms);

#endif /* HAL_I2C_H */
Program 24.2: Generic Hardware Abstraction Layer (HAL) I2C Interface

24.5 Layer 2: Device Driver Implementation

The sensor driver consumes the HAL interface. It contains zero STM32 or ARM-specific code, making it 100% reusable across any microcontroller with an I2C HAL: 

/* sensor_sht31.c: Environmental Sensor Driver */
#include "sensor_sht31.h"
#include "hal_i2c.h"

#define SHT31_I2C_ADDR_7BIT      (0x44U)
#define SHT31_CMD_HIGH_PRECISION (0x2400U)

Sht31Status_t sht31_sample_read_mdegc(int32_t * const p_temp_mdegc) {
    if (p_temp_mdegc == NULL) return SHT31_ERR_NULL_PTR;

    uint8_t cmd_buf[2] = { 0x24U, 0x00U };
    if (hal_i2c_master_transmit(SHT31_I2C_ADDR_7BIT, cmd_buf, 2U, 50U) != HAL_I2C_OK) {
        return SHT31_ERR_COMM_FAULT;
    }

    /* Wait for internal 15 ms conversion time non-blockingly or bounded */
    uint8_t rx_data[6];
    if (hal_i2c_master_receive(SHT31_I2C_ADDR_7BIT, rx_data, 6U, 50U) != HAL_I2C_OK) {
        return SHT31_ERR_COMM_FAULT;
    }

    /* Verify CRC8 checksum of payload */
    if (crc8_calculate(&rx_data[0], 2U) != rx_data[2]) {
        return SHT31_ERR_CRC_FAIL;
    }

    uint16_t raw_temp = (uint16_t)(((uint16_t)rx_data[0] << 8) | rx_data[1]);
    *p_temp_mdegc = ((175000 * (int32_t)raw_temp) / 65535) - 45000;

    return SHT31_OK;
}

24.6 Code Comparison: Spaghetti vs. Clean 4-Tier Layering

Compare an unlayered application that accesses registers directly with a structured 4-tier design.

Compare Architecture: Button-Triggered LED Flash

❌ Layerless Spaghetti (Anti-Pattern)

/* In main.c: Directly touches hardware */
#include "stm32f4xx.h"

int main(void) {
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;
    GPIOA->MODER |= (1 << 10); /* Pin A5 output */

    while (1) {
        if (!(GPIOC->IDR & (1 << 13))) {
            GPIOA->BSRR = (1 << 5); /* Turn on */
            delay_ms(100);
            GPIOA->BSRR = (1 << 21); /* Turn off */
        }
    }
}

Disaster: Zero layers. Hardcoded pin addresses, blocking delays, completely unportable, impossible to unit test.

✔ Clean 4-Tier Architecture

/* In main.c (Application Layer) */
#include "bsp.h"
#include "btn_service.h"

int main(void) {
    bsp_system_init();
    ui_service_init();

    while (1) {
        btn_service_process();
        scheduler_run();
    }
}

/* BSP maps physical pins; Driver debounces;
   Application executes business logic */

Excellence: Clean separation of concerns. The application logic is 100% portable to any microcontroller family.

24.7 Interactive Knowledge Check

Test your comprehension of layered firmware architectures, HAL boundaries, and BSP duties.

1. What is the fundamental directional rule of dependencies in a layered firmware architecture?
  • Lower layers depend on higher layers.
  • Dependencies point downwards only: higher layers depend on lower layers, never the reverse.
  • All layers must depend on main.c.
  • Layers can depend on each other circularly without restriction.
Explanation: High-level policy depends on lower abstractions. A driver must never know about or depend on the application calling it.
2. Which layer is responsible for initializing the microcontroller PLL clock tree and pin multiplexing?
  • The Application Layer.
  • The Device Driver Layer.
  • The Board Support Package (BSP) Layer.
  • The User Interface Layer.
Explanation: The BSP is specifically tailored to the physical circuit board, configuring crystal frequencies, PLL multipliers, and pin routes.
3. How should lower layers (such as a UART HAL or button debouncer) communicate events upward to the application layer?
  • By including app_main.h and calling app_process_data() directly.
  • Through registered function pointer callbacks or by pushing events into an event queue.
  • By asserting a CPU HardFault interrupt.
  • Through global shared memory variables without locks.
Explanation: Inversion of control via callbacks or event queues preserves downward-only dependencies while enabling reactive notifications.
4. What is the danger of "Layer Skipping" (e.g. Application code directly toggling a hardware peripheral register)?
  • The compiler will reject the code with a syntax error.
  • It introduces hidden couplings to specific silicon registers, breaking hardware independence and preventing host-based automated unit testing.
  • The MCU crystal frequency will double.
  • It consumes 64 KB of extra Flash.
Explanation: Bypassing the HAL/BSP ties the application directly to physical silicon registers, defeating the entire purpose of a layered architecture.
5. If a company redesigns a product PCB to switch from an STM32 to an ESP32 microcontroller, which layers require modification?
  • Every single file in the codebase must be rewritten.
  • Only the BSP and HAL implementation files; the Application and Device Driver layers remain 100% untouched.
  • Only the Application layer.
  • Only the unit test files.
Explanation: A clean 4-tier architecture isolates silicon specifics to the bottom layers (BSP/HAL). Upper business logic and sensor drivers remain unchanged.
6. What is the role of the Device Driver Layer (Layer 2)?
  • To configure the microcontroller interrupt vector table.
  • To implement communication and control logic for external peripheral ICs (sensors, displays, flash memories) on top of generic HAL bus protocols.
  • To draw high-level user interface menus.
  • To parse cloud JSON payloads.
Explanation: Drivers know how to command specific ICs (e.g. sending command bytes to an SHT31 sensor) using generic HAL bus transfers.
7. Why should vendor CMSIS register header files (e.g. stm32f401xe.h) NEVER be included in application.c?
  • Because CMSIS headers are written in C++.
  • Including vendor silicon headers introduces silicon lock-in and prevents compiling application code on a PC host for testing.
  • CMSIS headers are copyrighted and cannot be compiled.
  • It disables optimization flag -O3.
Explanation: Application code must remain pure C logic without hardware register dependencies, ensuring portable simulation and unit testing.
8. In a 4-tier architecture, what does the HAL GPIO interface provide?
  • A graphical user interface for touchscreens.
  • A generic, chip-agnostic digital pin control API: hal_gpio_write(pin, state), hal_gpio_read(pin).
  • A TCP/IP network socket.
  • An automated unit test runner.
Explanation: HAL GPIO abstracts the hardware details of pin set/reset registers behind clean procedural function signatures.
9. What is a "Mock HAL" in modern firmware engineering?
  • A humorous parody of software engineering.
  • A simulated HAL implementation running on a host PC that records bus transactions in RAM, allowing full driver and application verification without physical hardware.
  • A broken silicon revision.
  • A compiler syntax error generator.
Explanation: A Mock HAL enables continuous integration (CI) test pipelines to run thousands of test cases per minute on standard servers without physical boards.
10. Where do finite-state machines (FSMs) controlling overall product workflow belong in the 4-tier architecture?
  • In Layer 4 (BSP).
  • In Layer 1 (Application Layer).
  • In the Linker Script.
  • In the Vendor Silicon Errata header.
Explanation: System state machines embody product business logic and operational policies, placing them squarely in the Application layer.

24.8 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to structure and enforce a 4-tier layered firmware architecture.

Assignment 1: BSP Creation for Development Board

Task: Create bsp.h and bsp.c for your target hardware. Encapsulate clock initialization, LED control, and push button reading. Ensure that no other file in the project includes stm32f4xx.h or touches raw GPIO registers.

Assignment 2: Portable HAL SPI Master Interface

Task: Author hal_spi.h defining hal_spi_transfer(tx_buf, rx_buf, len, timeout_ms). Implement the driver on target hardware. Write a generic NOR Flash driver in Layer 2 that communicates exclusively through this HAL interface.

Assignment 3: Host PC Mock HAL Implementation

Task: Implement hal_i2c_mock.c on your host PC that simulates an SHT31 temperature sensor returning pre-programmed temperature curves. Run your Layer 2 sensor driver against this mock HAL and verify that temperature calculations are accurate to within 0.01 °C.

Assignment 4: Layer Violation CI Linter

Task: Write a shell script check_architecture.sh that uses grep to search the app/ and drivers/ directories for vendor headers (e.g. #include <stm32...>) or direct register dereferences (e.g. ->MODER). Fail the build if any layer boundary is violated.

Assignment 5: Multi-Board BSP Porting

Task: Build an application that blinks a heartbeat LED and logs temperature. Create two distinct BSP targets: bsp_board_rev_a.c and bsp_board_rev_b.c (with different LED pins and different I2C channels). Use Make or CMake target flags to switch between boards with zero application changes.
