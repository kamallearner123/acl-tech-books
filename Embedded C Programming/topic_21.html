Topic 21

Modular .c and .h File Architecture

A common architectural failure in embedded systems is the "Mega-File Anti-Pattern" — an entire firmware project crammed into a single 10,000-line main.c, or a project fragmented into dozens of header files containing executable C code, un-encapsulated global variables, and mutual circular includes.

Professional embedded firmware is organized into strictly decoupled Translation Units. Each module consists of an Interface Specification (the .h header file) declaring the public API contract, and a private Implementation Unit (the .c source file) encapsulating hardware registers, internal state machines, and private helper functions using the static keyword.

21.1 The Translation Unit Boundary

In C, the compiler never processes an entire project at once. Instead, the preprocessor strips comments, expands macros, and copies included headers into a single flattened text stream called a Translation Unit (TU). The compiler processes each TU independently into an object file (.o), which the linker ultimately resolves:

21.2 Information Hiding via the `static` Keyword

Procedural C lacks object-oriented private or protected access modifiers. In embedded C, true encapsulation is achieved exclusively through the static storage-class specifier:

1. File-Scope Private Variables (Static State)

A variable declared at file scope with static has static storage duration (persists across the entire life of the firmware) but internal linkage. Its symbol is completely invisible to the linker and cannot be accessed or corrupted by any other translation unit: 

/* In uart.c: Completely private to this translation unit */
static uint8_t  s_rx_ring_buffer[256];
static uint16_t s_rx_head_idx = 0U;
static uint16_t s_rx_tail_idx = 0U;

2. File-Scope Private Helper Functions

Functions marked static have internal linkage. This confers two vital engineering advantages:

  • No Symbol Collision: Two different driver files (e.g. spi.c and i2c.c) can both define a private helper named static void configure_clocks(void) without triggering a duplicate symbol linker error.
  • Compiler Optimization: The compiler knows the static function can never be called outside this translation unit. If it is called only once or twice, GCC automatically inlines the entire function, eliminating function call overhead and saving stack memory.

21.3 Header File Hygiene & The Self-Contained Rule

Every header file must follow the Self-Contained Header Rule: a header file must include all prerequisites necessary to compile cleanly on its own.

The Header Isolation Test

To prove that your header motor.h is truly self-contained, create a dummy C file containing only: 

/* test_header.c */
#include "motor.h"

If compiling test_header.c emits errors like unknown type uint32_t or size_t undeclared, your header is defective! It was secretly relying on the caller having previously included <stdint.h> or <stddef.h>.

Include Guards: `#ifndef` vs `#pragma once`

/* Standard ISO C99 / MISRA-Compliant Include Guard */
#ifndef MOTOR_H
#define MOTOR_H

#include <stdint.h>
#include <stdbool.h>

/* Public API declarations */
void motor_init(void);

#endif /* MOTOR_H */

While #pragma once is supported by modern GCC and Clang, the classic #ifndef / #define guard pattern remains strictly mandated by MISRA-C:2012 Rule 20.14 because it guarantees standard-conforming portability across legacy proprietary microcontroller toolchains (IAR, Keil, Cosmic, Renesas CC-RX).

21.4 Breaking Circular Dependency Traps

Circular dependencies occur when Module A needs types from Module B, while Module B needs types from Module A (e.g. telemetry.h includes comm.h, which includes telemetry.h). This causes the preprocessor to omit header declarations due to include guards, triggering bizarre syntax error: unknown type name compiler errors.

The professional solution is Forward Struct Declarations combined with Interface Segregation: 

/* comm.h */
#ifndef COMM_H
#define COMM_H

#include <stdint.h>

/* FORWARD DECLARATION: No need to #include "telemetry.h" */
struct TelemetryPacket_t;

/* Public API using pointer to forward-declared structure */
void comm_send_packet(const struct TelemetryPacket_t * const p_packet);

#endif /* COMM_H */

Because a pointer has a known, fixed physical size (4 bytes on 32-bit Cortex-M), the compiler does not need the complete struct definition in the header. The complete struct is only included in the .c implementation file.

21.5 Code Comparison: Leaky Header vs. Clean Modular C

Compare an un-encapsulated header that leaks variables into global scope with a clean, decoupled modular translation unit.

Compare Architecture: LED Controller Module

❌ Leaky Header (Linker Hazard)

/* led.h: DISASTROUS ANTI-PATTERN! */
#include "stm32f4xx.h"

/* Defines variable in header: Linker collision! */
uint8_t led_status; 

/* Code inside header: duplicated in every .o */
void set_led(uint8_t on) {
    if (on) GPIOA->ODR |= (1 << 5);
    else    GPIOA->ODR &= ~(1 << 5);
}

Flaws: Defining storage in headers causes duplicate symbol link errors if included in more than one .c file. Exposes raw chip registers to application code.

✔ Clean Modular Architecture

/* led.h: Pure Interface Specification */
#ifndef LED_H
#define LED_H
#include <stdbool.h>

typedef enum { LED_OFF = 0, LED_ON } LedState_t;
void led_init(void);
void led_write(const LedState_t state);
#endif

/* led.c: Encapsulated Implementation */
#include "led.h"
#include "bsp_gpio.h"
static LedState_t s_current_state = LED_OFF;

void led_write(const LedState_t state) {
    s_current_state = state;
    bsp_pin_write(LED_PIN, (state == LED_ON));
}

Safety: Zero variable definitions in header, state is static private, hardware registers are completely hidden behind clean procedural API.

21.6 Interactive Knowledge Check

Test your understanding of translation units, linkage, header guards, and modular C architecture.

1. What happens if a global variable definition like uint32_t system_counter = 0; is placed inside a header file included by two separate .c files?
  • The compiler merges them automatically into Flash ROM.
  • The linker halts with a "multiple definition of symbol" error because storage is allocated in both object files.
  • The SysTick interrupt stops incrementing.
  • The variable becomes read-only.
Explanation: A header file must only declare symbols using extern. Defining storage in a header produces duplicate symbol definitions in every translation unit that includes it.
2. What is the effect of declaring a file-scope helper function as static void compute_crc(void)?
  • The function is stored in EEPROM.
  • The function is given internal linkage, restricting its visibility to the current translation unit and enabling compiler inlining optimizations.
  • The function can only be executed once during boot.
  • The function runs with interrupt priority.
Explanation: static on a function strips it from the global symbol table, preventing name clashes and allowing aggressive compiler optimizations.
3. What is the "Self-Contained Header" principle in C firmware design?
  • A header file must contain all executable C code without needing a .c file.
  • A header file must include all necessary dependencies (<stdint.h>, <stdbool.h>) so that it compiles cleanly on its own without assuming prior includes.
  • A header file must never include any other header file.
  • A header must be smaller than 512 bytes.
Explanation: Self-contained headers eliminate fragile include-order dependencies where b.h only compiles if the developer remembered to include a.h first.
4. Why is #ifndef MODULE_H / #define MODULE_H / #endif preferred over #pragma once in strict MISRA-C projects?
  • Because #pragma once is only supported on Linux.
  • Because standard macro guards are fully defined by the ISO C standard, whereas #pragma once is a non-standard compiler extension prohibited by MISRA.
  • Macro guards run 10 times faster during runtime.
  • #pragma once increases SRAM consumption.
Explanation: #pragma directives are implementation-defined. For maximum safety compliance across certified compilers, standard preprocessor macro guards are required.
5. How can circular dependency between two headers (A.h and B.h) be cleanly broken without combining them?
  • By deleting the include guards in both headers.
  • By using a forward struct declaration (e.g. struct B_t;) in A.h and moving pointer dereferencing into the .c implementation file.
  • By compiling the files with the -O0 flag.
  • Circular dependencies are impossible to resolve in C.
Explanation: Declaring struct Foo; informs the compiler that the type exists, allowing pointers to be used in function prototypes without including the complete struct definition.
6. What is the risk of including massive device peripheral headers (e.g. stm32f4xx.h) inside a high-level application business logic header?
  • The MCU crystal will destabilize.
  • It tightly couples application algorithms to specific hardware registers, preventing host-based unit testing and code reuse on different silicon.
  • The compiler converts all variables to 64-bit doubles.
  • It disables Git version tracking.
Explanation: Including hardware headers in application code destroys hardware abstraction, making it impossible to compile or unit-test application logic on a PC.
7. What is an "opaque pointer" in C modular programming?
  • A pointer that cannot be dereferenced by anyone, even the driver.
  • A pointer to an incomplete struct type whose internal fields are defined only in the .c file, completely hiding implementation details from the caller.
  • A pointer stored in blackbox NVRAM.
  • A pointer with a null value.
Explanation: Opaque pointers (handles) enforce true information hiding: callers can pass the handle to APIs, but cannot inspect or corrupt internal struct members.
8. In a well-architected firmware driver, where should hardware register macros (e.g. #define CR1_ENABLE (1 << 0)) be placed?
  • In the public driver.h file.
  • Inside the private driver.c file (or a private internal header like driver_reg.h), hidden from application code.
  • Inside main.c.
  • In the linker script.
Explanation: Bit-level register masks are internal implementation details. Exposing them in public headers pollutes the global namespace and tempts application code to bypass the driver.
9. What is the purpose of declaring a public variable in a header with extern?
  • To allocate memory in the heap.
  • To declare the symbol name and type to callers without allocating storage, which is defined once in a single .c file.
  • To make the variable constant.
  • To instruct the compiler to place the variable in an external SPI Flash.
Explanation: extern provides a reference declaration; the actual storage is defined in exactly one translation unit, satisfying the One Definition Rule (ODR).
10. Why should you avoid putting executable function bodies (non-inline) inside a header file?
  • Because each translation unit including the header compiles a separate instance of the function, causing multiple-definition linker collisions.
  • Because headers can only contain ASCII art.
  • Because the preprocessor strips all C statements.
  • Because the CPU cannot branch to code defined in headers.
Explanation: Function bodies in headers are compiled into every translation unit that includes them, producing duplicate symbol errors during linking unless marked static inline.

21.7 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to master translation unit encapsulation and modular firmware architecture.

Assignment 1: Monolithic Refactoring

Task: Take a 500-line monolithic main.c that mixes UART driver code, button debouncing, and temperature sensor reading. Break it into three decoupled modules: bsp_uart.[ch], btn_debounce.[ch], and temp_sensor.[ch]. Verify successful compilation and linking.

Assignment 2: Automated Self-Contained Header Verification

Task: Write a shell script or Makefile target make check-headers that iterates through every .h file in your project, generates a temporary #include "header.h" test file, compiles it with -Wall -Werror, and verifies zero compilation errors.

Assignment 3: Symbol Leakage Audit with nm

Task: Compile an object file driver.o. Run nm -g driver.o (global symbols) and nm driver.o (all symbols). Verify that internal helper functions and private state variables are marked with t and b (local/internal linkage) and only true public APIs appear as T (global).

Assignment 4: Resolving Circular Include Deadlocks

Task: Intentionally construct a circular dependency: packet.h includes channel.h, and channel.h includes packet.h. Demonstrate the compiler error. Refactor both headers using forward struct declarations and prove clean, zero-warning compilation.

Assignment 5: Multi-Instance Peripheral Driver

Task: Design a modular UART driver supporting multiple hardware channels (UART1 and UART2) using a configuration struct instance: UartHandle_t. Ensure the driver contains zero hardcoded peripheral register addresses, enabling two independent UART instances to share identical driver code.
