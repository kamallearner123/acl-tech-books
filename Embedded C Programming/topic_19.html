Topic 19

States, Events & Transitions

When firmware requirements expand, unstructured code invariably degenerates into a tangled web of ad-hoc boolean flags: is_started, tx_busy, sensor_ready, btn_pressed_flag. With just 10 boolean flags, the system possesses $2^{10} = 1024$ theoretically possible state combinations — the overwhelming majority of which represent invalid, untested, or dangerous machine conditions.

The antidote to boolean flag chaos is formal Automata Theory. By modeling firmware behavior as a Finite-State Machine (FSM), we partition system operation into a finite set of mutually exclusive States, reacting to external Events through well-defined Transitions governed by explicit Guards and executing predictable Actions.

19.1 The FSM Formal Model

Mathematically, a finite-state machine is defined as a 5-tuple $(S, \Sigma, \delta, s_0, F)$:

  • $S$: A finite, non-empty set of States.
  • $\Sigma$: A finite set of inputs or Events (the input alphabet).
  • $\delta$: The Transition Function mapping $(S \times \Sigma) \rightarrow S$.
  • $s_0$: The initial start state ($s_0 \in S$).
  • $F$: The set of final or terminal states (often empty in continuously running embedded superloops).

19.2 Moore vs. Mealy Automata

When mapping real-world physical outputs (solenoids, heater PWM, LEDs) to an FSM, the timing of output generation determines the machine architecture:

Attribute Moore Machine Mealy Machine
Output Dependency Outputs depend solely on the current state. Outputs depend on both current state AND the incoming event.
Action Timing Executed on State Entry (Entry Action) or during state dwell. Executed on the Transition arc between states.
Glitch Vulnerability Immune to input glitches. Outputs change only when state officially transitions. Vulnerable to transient input bounce if events are noisy.
State Count Often requires more states to represent distinct output combinations. Often requires fewer states; transitions handle output variations.

Best Practice in Embedded Hardware Control

In safety-critical firmware, Moore machines are strongly preferred for hardware actuators. Because physical pins (e.g. RELAY_PIN) are updated strictly upon entering a verified state, spurious transitions or noisy inputs cannot briefly toggle an actuator mid-cycle.

19.3 Implementing FSMs in C: The Switch-Case Pattern

The most intuitive, maintainable, and compiler-optimizable implementation of a state machine in embedded C is the structured nested switch-case pattern: 

#include <stdint.h>
#include <stdbool.h>

/* 1. Explicit State Enumeration */
typedef enum {
    PUMP_STATE_STOPPED = 0,
    PUMP_STATE_PRIMING,
    PUMP_STATE_RUNNING,
    PUMP_STATE_FAULT
} PumpState_t;

/* 2. Explicit Event Enumeration */
typedef enum {
    EVENT_START_CMD,
    EVENT_STOP_CMD,
    EVENT_PRESSURE_OK,
    EVENT_PRESSURE_LOST,
    EVENT_TIMEOUT
} PumpEvent_t;

/* 3. Event Structure with Optional Payload */
typedef struct {
    PumpEvent_t signal;
    uint32_t    param;
} Event_t;

static PumpState_t s_current_state = PUMP_STATE_STOPPED;
static uint32_t    s_state_entry_time = 0U;

void pump_fsm_dispatch(const Event_t * const p_evt) {
    if (p_evt == NULL) {
        return;
    }

    switch (s_current_state) {
        case PUMP_STATE_STOPPED:
            if (p_evt->signal == EVENT_START_CMD) {
                /* Action on transition */
                bsp_valve_open();
                s_state_entry_time = millis();
                s_current_state = PUMP_STATE_PRIMING;
            }
            break;

        case PUMP_STATE_PRIMING:
            if (p_evt->signal == EVENT_PRESSURE_OK) {
                bsp_motor_start();
                s_current_state = PUMP_STATE_RUNNING;
            } else if (p_evt->signal == EVENT_TIMEOUT) {
                bsp_valve_close();
                bsp_alarm_strobe();
                s_current_state = PUMP_STATE_FAULT;
            } else if (p_evt->signal == EVENT_STOP_CMD) {
                bsp_valve_close();
                s_current_state = PUMP_STATE_STOPPED;
            }
            break;

        case PUMP_STATE_RUNNING:
            if ((p_evt->signal == EVENT_STOP_CMD) || (p_evt->signal == EVENT_PRESSURE_LOST)) {
                bsp_motor_stop();
                bsp_valve_close();
                s_current_state = (p_evt->signal == EVENT_STOP_CMD) ? 
                                   PUMP_STATE_STOPPED : PUMP_STATE_FAULT;
            }
            break;

        case PUMP_STATE_FAULT:
            if (p_evt->signal == EVENT_STOP_CMD) {
                /* Acknowledge fault and reset */
                s_current_state = PUMP_STATE_STOPPED;
            }
            break;

        default:
            /* Defensive recovery from corrupt state */
            bsp_motor_stop();
            bsp_valve_close();
            s_current_state = PUMP_STATE_FAULT;
            break;
    }
}

19.4 State Transition Tables (State Matrices)

Before writing any C code, safety standards require constructing a State Transition Matrix. This ensures that every possible combination of (State × Event) is analyzed, eliminating unhandled events:

Current State EVENT_START EVENT_STOP EVENT_PRESSURE_OK EVENT_TIMEOUT
STOPPED → PRIMING Ignore Ignore Ignore
PRIMING Ignore → STOPPED → RUNNING → FAULT
RUNNING Ignore → STOPPED Ignore Ignore
FAULT Ignore → STOPPED Ignore Ignore

19.5 Code Comparison: Flag Chaos vs. Structured FSM

Compare an ad-hoc flag-based implementation with a clean state machine.

Compare Control Logic: Microwave Oven Controller

❌ Spaghetti Boolean Flags

bool door_open = false;
bool cooking = false;
bool paused = false;

void on_door_open() {
    door_open = true;
    if (cooking) {
        paused = true;
        magnetron_off();
    }
}
void on_start() {
    /* What if door is open AND paused? */
    if (!door_open || paused) {
        cooking = true;
        magnetron_on();
    }
}

Hazard: Contradictory flag states (e.g. door_open == true and cooking == true) can occur during edge cases, causing physical hazard.

✔ Mutually Exclusive FSM

typedef enum { 
    STATE_DOOR_OPEN, 
    STATE_IDLE, 
    STATE_COOKING, 
    STATE_PAUSED 
} OvenState_t;

void oven_fsm_step(Event_t evt) {
    switch (s_state) {
        case STATE_DOOR_OPEN:
            if (evt == EVT_DOOR_CLOSED) 
                s_state = STATE_IDLE;
            break;
        case STATE_COOKING:
            if (evt == EVT_DOOR_OPENED) {
                magnetron_off();
                s_state = STATE_PAUSED;
            }
            break;
        /* Impossible to cook with door open! */
    }
}

Safety: States are mathematically mutually exclusive. The magnetron can never be activated while the door is open.

19.6 Interactive Knowledge Check

Test your understanding of finite-state automata, Moore/Mealy models, and state matrix mechanics.

1. What is the fundamental difference between a Moore machine and a Mealy machine?
  • A Moore machine uses 32-bit registers; a Mealy machine uses 16-bit registers.
  • In a Moore machine, outputs depend solely on the current state; in a Mealy machine, outputs depend on both the current state and the incoming event.
  • A Moore machine can have infinite states; a Mealy machine has only one.
  • Mealy machines cannot be programmed in C.
Explanation: Moore outputs are tied strictly to state residency (entry actions), making them inherently glitch-free and highly predictable for physical hardware actuators.
2. If a system has 6 independent boolean flags controlling operational logic, how many total state combinations can theoretically exist?
  • 6
  • 12
  • 64 (2^6)
  • 36
Explanation: Boolean flags create an exponential state space ($2^N$). Unstructured code rarely handles the vast majority of illegal flag combinations.
3. What is a "Guard Condition" on a state transition?
  • A watchdog timer that resets the CPU.
  • A boolean predicate that must evaluate to TRUE for the transition to fire when the event occurs.
  • A memory protection unit (MPU) rule.
  • A compiler optimization barrier.
Explanation: In UML notation `EVENT [Guard] / Action`, the transition only fires if the event matches AND the guard evaluates to true (e.g. `[temperature < 100]`).
4. What is the benefit of a "State Transition Matrix" during the design phase of safety-critical firmware?
  • It calculates the PCB manufacturing cost.
  • It forces the engineer to exhaustively examine every (State × Event) combination, guaranteeing no unhandled events exist.
  • It allows the CPU to run without a clock crystal.
  • It compresses Flash ROM size by 50%.
Explanation: Constructing the 2D matrix reveals blind spots — such as what happens if a `STOP_CMD` arrives during `PRIMING` or `FAULT` — before writing code.
5. In an embedded FSM, why is a default: case required in the top-level state switch?
  • To trap invalid or corrupted state variable values caused by memory corruption or single-event upsets (radiation bit flips).
  • To enable floating point math.
  • To initialize peripheral GPIOs.
  • It is optional and should be avoided.
Explanation: If memory corruption causes the state enum to hold an undefined number (e.g. 0x9F), the default: label catches it and forces a safe shutdown.
6. What is an "Internal Transition" in a state machine?
  • A transition that resets the microcontroller.
  • A transition that executes an action in response to an event without changing the active state and without executing entry/exit actions.
  • A transition between two different microcontrollers.
  • An interrupt vector remapping.
Explanation: An internal transition responds to an event (e.g. logging a metric or blinking a status LED) while remaining in the same state without triggering exit/entry logic.
7. Why are Moore machines considered safer for controlling physical actuators (e.g. motors, heaters)?
  • Because Moore machines execute in kernel space.
  • Because actuator drive states are bound strictly to stable states, preventing glitchy output pulses caused by transient input noise.
  • Because Moore machines consume 0 milliwatts of power.
  • Because Mealy machines cannot output boolean values.
Explanation: Actuator states in a Moore machine remain solidly in their defined condition for the entire duration the machine dwells in that state.
8. What should happen when an event arrives that is completely irrelevant to the current state (e.g. `PRESSURE_OK` while `STOPPED`)?
  • The MCU must immediately assert HardFault.
  • The event should be safely ignored (consumed without action or state change) unless specified as a protocol violation.
  • The event must be queued for 10 hours.
  • The Flash memory must be formatted.
Explanation: In automata theory, an event that triggers no transition from the current state is silently ignored, maintaining stability.
9. What is the role of an "Event Queue" paired with an FSM dispatcher?
  • To store compiler optimization macros.
  • To buffer asynchronous events produced by ISRs (e.g. buttons, UART bytes) so the FSM can process them sequentially in the main superloop.
  • To dynamically allocate heap memory.
  • To invert GPIO logic levels.
Explanation: Hardware interrupts post event signals into a ring buffer queue; the main superloop dequeues and dispatches them run-to-completion.
10. Why is passing an Event struct containing both a signal enum and a param payload advantageous?
  • It disables stack alignment checks.
  • It allows data associated with the event (e.g., raw ADC value, received UART byte, error code) to travel cleanly to the state action handler without global variables.
  • It doubles the MCU clock frequency.
  • Payloads are required by the C89 standard.
Explanation: Combining signals with parameter payloads provides rich event context without relying on fragile global variables.

19.7 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to design, model, and implement deterministic state automata.

Assignment 1: Traffic Light Controller with Pedestrian Call

Task: Design a Moore FSM for a traffic intersection: GREEN (30s), YELLOW (4s), RED (25s), and PEDESTRIAN_WALK (15s). A pedestrian button press is an asynchronous event. Draw the state diagram and implement the complete switch-case C engine with non-blocking timing.

Assignment 2: State Transition Matrix Completeness Verification

Task: Take the pump controller from Program 19.1. Write a host-based automated unit test that iterates through all 4 states and injects all 5 events (20 combinations). Verify that every valid transition produces the exact expected state and that all invalid combinations are gracefully ignored.

Assignment 3: Serial Protocol Frame Parser FSM

Task: Implement a byte-by-byte frame parser FSM: WAIT_PREAMBLE_1 (0xAA), WAIT_PREAMBLE_2 (0x55), READ_LENGTH, READ_PAYLOAD, VERIFY_CRC. Test it with corrupted input streams, truncated frames, and noise bytes to verify that it never enters an infinite loop or drops valid frames.

Assignment 4: Moore Actuator Quench Guarantee

Task: Build an FSM for an industrial heater with an OVERTEMP_EVENT. Implement the safety rule where entering the STATE_EMERGENCY_SHUTDOWN immediately forces the PWM duty cycle to 0% inside the state entry handler. Verify that no code path can exit this state without a physical key turn event.

Assignment 5: Event Payload Processing

Task: Create an FSM where the event contains a payload union: either a button hold duration in milliseconds or a float temperature measurement. Write state handlers that evaluate guard conditions against the payload (e.g. transition to CONFIG_MODE only if button held > 3000 ms).
