Topic 15

Naming Conventions & Code Style

In safety-critical firmware engineering, naming conventions and coding style are not cosmetic matters of personal preference; they are rigorous risk-mitigation instruments. Ambiguous identifiers, omitted physical units, and inconsistent scoping indicators directly cause hardware destruction, buffer overflows, and critical flight software failures.

This chapter examines the canonical standards governing embedded C identifiers, with primary reference to the Barr Group Embedded C Coding Standard and MISRA-C:2012. We establish precise syntactic and semantic rules for global and local variables, pointer mechanics, function hierarchies, macros, and hardware register mappings.

15.1 The Cognitive Tax of Inconsistent Naming

Microcontroller firmware directly controls electrical actuators, high-voltage relays, RF transceivers, and lithium battery charging circuits. Consider the catastrophic ambiguity in the following snippet: 

/* DANGEROUS CODE: What do these variables represent? */
uint32_t val = 50;
uint16_t temp = read_temp();
set_valve(1);
wait(val);

Analyzing the failure modes embedded in this trivial example:

  • Is val measured in milliseconds, microseconds, or timer clock ticks? A 1000× error will either melt an actuator or cause a communication timeout.
  • Is temp raw ADC counts (0–4095), degrees Celsius, or hundredths of a Kelvin?
  • Does set_valve(1) open the valve (active-high logic) or close it (active-low hardware pull-down)?
  • Is read_temp() a driver function, a local static function, or an exported HAL routine?

15.2 The Rule of Explicit Physical Units

Every variable or constant representing a physical engineering quantity must incorporate the unit of measurement as an explicit suffix in its identifier.

Quantity Mandatory Suffix Compliant Example Dangerous Non-Compliant
Time (Milliseconds) _ms timeout_ms timeout
Time (Microseconds) _us pulse_width_us pulse_len
Voltage (Millivolts) _mv battery_voltage_mv vbat
Current (Milliamps) _ma charge_current_ma current
Temperature (Celsius) _degc heatsink_temp_degc temp
Frequency (Hertz / kHz) _hz / _khz pwm_frequency_hz frequency
Rotational Speed _rpm motor_speed_rpm speed

Case Study: The $327 Million Mars Climate Orbiter Loss

On September 23, 1999, NASA lost the Mars Climate Orbiter spacecraft as it attempted orbital insertion. The failure was traced to a software module from Lockheed Martin calculating thruster impulse in United States customary units (Pound-force seconds, lbf*s) while the navigation software developed by the Jet Propulsion Laboratory (JPL) expected metric units (Newton-seconds, N*s). Consistent physical unit suffixes such as impulse_ns and impulse_lbfs would have made this discrepancy instantly apparent during code inspection.

15.3 Scope & Storage Prefixes

In procedural C, identifiers should immediately reveal their storage class and lifetime without requiring the engineer to scroll to the top of a file or search external header files.

Figure 15.1: Identifier Scope and Type Encoding Taxonomy

Barr Group Identifier Rules

  • g_: Global variable across translation units (declared in header as extern). Must be minimized.
  • s_: File-scope private variable (declared with static keyword).
  • p_: Explicit pointer variable, e.g., uint8_t *p_tx_buffer.
  • _t: Explicit type definition, e.g., typedef struct SensorConfig_t SensorConfig_t;.

15.4 Function Naming Hierarchy: Module_Noun_Verb

Procedural C has no object-oriented namespaces. To prevent symbol collisions when integrating multiple third-party or team drivers, public functions must follow the strict Module_Noun_Verb() grammar:

[MODULE]_[SUBSYSTEM]_[ACTION](parameters) 
/* Good: Follows hierarchical namespace convention */
bool   uart_rx_fifo_is_empty(void);
void   flash_sector_erase(uint32_t sector_address);
int32_t adc_channel_read_mv(uint8_t channel_id);
void   motor_pid_compute(MotorHandle_t *p_handle);

/* Bad: Vague, ambiguous, prone to symbol conflicts */
bool   is_empty(void);          /* Conflict with queue or stack! */
void   erase(uint32_t addr);    /* Erase what? RAM? Flash? EEPROM? */
int32_t read(uint8_t ch);       /* Conflicts with POSIX read() syscall! */

15.5 Macros, Constants & Enumerations

Preprocessor constants and macro functions must always be written in UPPER_SNAKE_CASE. Additionally, macros must follow strict defensive wrapping rules: 

/* Constants */
#define SYSTEM_CLOCK_FREQ_HZ    (168000000UL)
#define UART_BAUD_RATE_BPS      (115200U)
#define I2C_TIMEOUT_LIMIT_MS    (50U)

/* Macro Functions: ALWAYS parenthesize every argument and the entire expression */
#define ARRAY_SIZE(arr)         (sizeof(arr) / sizeof((arr)[0]))
#define MIN_VAL(a, b)           (((a) < (b)) ? (a) : (b))

/* Multi-statement macros MUST use do { ... } while(0) */
#define CRITICAL_PULSE_PIN(pin) \
    do {                        \
        GPIO_SetHigh(pin);      \
        __NOP();                \
        GPIO_SetLow(pin);       \
    } while (0)
Program 15.2: Safe Preprocessor Macro Style and Guard Patterns

Why `do { ... } while (0)` is Mandatory

If a macro with multiple statements is written as #define FOO() { a(); b(); } and used in an if-else construct: 

if (condition)
    FOO();
else
    bar();

The trailing semicolon after FOO(); expands into { a(); b(); }; else bar();. The semicolon before else causes a compile-time syntax error (broken if-else pairing) or worse, silent logic truncation! Wrapping in do { ... } while (0) ensures the macro behaves syntactically as a single statement requiring a semicolon.

15.6 Code Comparison: Fragile vs. Barr-Standard Compliant Style

Compare an actual embedded driver written without conventions against the same module refactored under Barr Group and MISRA-C rules.

Compare Driver Style: Temperature Sensor Acquisition

❌ Non-Compliant & Fragile

/* No units, global pollution, ambiguous names */
int val;
int stat;

int get_data(int c) {
    if (c == 0) {
        val = read_adc();
        stat = 1;
        return val;
    }
    return -1;
}

#define DELAY 500
void run() {
    int t = get_data(0);
    delay(DELAY);
}

Flaws: Bare int (unspecified bit-width), untyped magic numbers, no physical units (is DELAY ms or us?), dangerous global variables without scope prefix.

✔ Barr-Standard & MISRA Compliant

#define SENSOR_POLL_INTERVAL_MS  (500U)

typedef enum {
    SENSOR_STATUS_OK,
    SENSOR_STATUS_TIMEOUT,
    SENSOR_STATUS_PARAM_ERR
} SensorStatus_t;

static uint16_t s_latest_temp_raw = 0U;

SensorStatus_t sensor_temp_read_mdegc(
    const uint8_t channel_idx,
    int32_t * const p_temp_mdegc) 
{
    if ((p_temp_mdegc == NULL) || (channel_idx > 3U)) {
        return SENSOR_STATUS_PARAM_ERR;
    }
    s_latest_temp_raw = bsp_adc_channel_read(channel_idx);
    *p_temp_mdegc = ((int32_t)s_latest_temp_raw * 1000) / 4096;
    return SENSOR_STATUS_OK;
}

Safety: Explicit fixed-width types, unit suffix (_mdegc for millidegrees Celsius), pointer qualification, status return enum, static storage prefix.

15.7 Interactive Knowledge Check

Test your knowledge of professional embedded C style rules and naming standards.

1. Why should a variable representing a duration always include a suffix like _ms or _us?
  • To assist the compiler's register allocator in selecting a 64-bit register.
  • To make the physical unit explicit, preventing order-of-magnitude timing mistakes in motor controllers and communication drivers.
  • Because the C99 standard rejects variable names without underscores.
  • To enable automatic unit conversion in GDB.
Explanation: Missing units are a primary source of embedded bugs (e.g. passing a microsecond value to a function expecting milliseconds). Suffixes eliminate ambiguity at inspection time.
2. Under the Barr Group Embedded C Coding Standard, what does the s_ prefix signify on an identifier?
  • A signed integer.
  • A static variable with file-scope lifetime and visibility restricted to the current translation unit.
  • A string buffer stored in Flash memory.
  • A semaphore synchronization primitive.
Explanation: s_ designates module-scoped static variables, alerting any engineer that the variable persists across function calls but is internal to that .c file.
3. What is the fundamental problem with defining a multi-statement macro as: #define LED_OFF() GPIO_Low(); delay_ms(1);?
  • In an if (cond) LED_OFF(); statement without braces, delay_ms(1) will execute unconditionally regardless of the condition.
  • The compiler will reject macros that call functions.
  • Flash memory size will double.
  • The SysTick interrupt will be permanently disabled.
Explanation: Without encapsulation in do { ... } while(0), only the first statement belongs to the if block; subsequent statements run unconditionally outside the branch.
4. What naming convention should be applied to public functions in a modular C peripheral driver?
  • CamelCase with the author's initials: kmWriteByte().
  • Hierarchical Module_Noun_Verb(): e.g., spi_flash_sector_erase().
  • Short abbreviated names under 4 characters: sfse().
  • All uppercase letters: SPI_FLASH_ERASE().
Explanation: The module_subsystem_action() convention provides procedural namespacing, preventing link-time collisions when integrating multiple drivers.
5. Why does MISRA-C advise against typedefing pointer types directly (e.g. typedef uint8_t* BufferPtr_t;)?
  • Because 64-bit pointers cannot be held in typedefs.
  • Because it obscures pointer dereference semantics and makes const qualification confusing and error-prone.
  • Because typedefs are not recognized by C linkers.
  • Because it consumes extra SRAM at runtime.
Explanation: Hiding pointer indirection behind a typedef obscures whether const BufferPtr_t makes the pointer constant or the pointee data constant, causing dangerous aliasing bugs.
6. What is the standard suffix for user-defined types (structs, unions, enums) in embedded C?
  • _obj
  • _t (or _type)
  • _var
  • _p
Explanation: The _t suffix universally denotes a type definition, distinguishing type identifiers from variable and function instances.
7. Why is #define TIMEOUT 100 + 50 dangerous when used in uint32_t total = TIMEOUT * 2;?
  • Operator precedence causes it to expand as 100 + 50 * 2 = 200 instead of (100 + 50) * 2 = 300.
  • The preprocessor converts addition to bitwise OR.
  • The expression overflows an 8-bit register.
  • C preprocessors cannot perform arithmetic addition.
Explanation: Macros perform raw textual substitution without precedence. Unparenthesized mathematical expressions in macros lead to catastrophic precedence calculation errors.
8. In active-low signal hardware design (e.g. an active-low reset pin or active-low LED), how should the signal be named in firmware?
  • It should always be named PIN_POSITIVE.
  • It should include an explicit active-low suffix such as _n, _low, or _inv (e.g., RESET_N_PIN).
  • Active-low signals cannot be represented in C.
  • All digital pins must be inverted twice in the preprocessor.
Explanation: Suffixes like _n or _low alert firmware engineers that writing a logical 0 activates the peripheral, preventing reverse electrical behavior.
9. What is the recommended casing convention for enumeration constants in professional embedded C?
  • camelCase, e.g. stateIdle.
  • UPPER_SNAKE_CASE with a shared module prefix, e.g. FSM_STATE_IDLE.
  • kebab-case, e.g. fsm-state-idle.
  • All lowercase without spaces, e.g. fsmstateidle.
Explanation: Prefixing enum values with their enum category in uppercase (e.g. UART_ERR_PARITY, UART_ERR_OVERRUN) prevents name clashes and clarifies context.
10. Why should a global variable declared in a header file always be prefixed with extern and never initialized in the header?
  • Because uninitialized globals are placed in Flash memory.
  • Initializing a variable in a header causes multiple-definition linker errors when included in more than one translation unit.
  • Because GCC does not support global variables in C99.
  • Because extern variables do not consume RAM.
Explanation: extern declares a symbol without defining storage. Initializing in a header creates a storage definition in every file including it, triggering link-time duplicate symbol errors.

15.8 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to audit, refactor, and enforce coding standards across embedded codebases.

Assignment 1: Legacy Codebase Naming Audit

Task: Take a legacy 200-line driver containing bare identifiers (t, val, flag, delay()). Conduct an audit identifying every ambiguous physical unit and scope violation. Refactor all identifiers into strict Barr-compliant names with _ms, _mv, and scope prefixes.

Assignment 2: Macro Safety & Parenthesis Audit

Task: Write a header containing 5 complex arithmetic and bit-manipulation macros. Intentionally remove parentheses in one macro and demonstrate in a test harness how operator precedence produces erroneous values. Rewrite all 5 macros using complete defensive parenthesization and do { ... } while(0) blocks.

Assignment 3: Active-Low Hardware Mapping

Task: Create a Board Support Package (BSP) GPIO header for a development board with 2 active-low LEDs and 2 active-low pushbuttons. Design an API where the active-low electrical logic is encapsulated behind expressive enum names (LED_STATE_ON, LED_STATE_OFF) so application code never deals with inverted boolean logic.

Assignment 4: Automated Style Enforcement with Clang-Format

Task: Create a production .clang-format configuration file enforcing: 4-space indentation, no tabs, braces on new lines for functions (Allman style), column limit of 100 characters, and pointer alignment to the right (uint8_t *ptr). Run clang-format across your source directory and verify zero warnings.

Assignment 5: Prefix Collision Elimination

Task: Build two independent C drivers: display_oled.c and storage_eeprom.c. Both require an internal circular buffer and an initialization routine. Implement strict oled_ and eeprom_ prefixing to prove that both drivers compile and link into the same binary without any symbol conflict.
