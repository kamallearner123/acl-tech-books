Engineering Reference 6

The Complete Firmware Engineering Lifecycle: From Requirements to Deployment

Writing Embedded C in safety-critical and commercial products is never an ad-hoc exercise of typing code into an IDE and hitting "Run". In aerospace (DO-178C), automotive (ISO 26262 / ASPICE), medical devices (IEC 62304), and industrial automation (IEC 61508), every single binary byte flashed onto silicon must trace back to a verifiable requirement, pass static and dynamic quality gates, and be securely packaged for production provisioning and field updates.

This comprehensive reference breaks down the complete 10-Stage Embedded Engineering Lifecycle — guiding you step-by-step from customer requirements and Software Requirements Specifications (SRS), through layered architecture, defensive coding, host unit testing, cross-compilation, linker script layout, cryptographic signing, factory flashing, and Fail-Safe Firmware Over-The-Air (FOTA) deployment.

1. Phase 1: Requirements Engineering & Traceability

Every firmware project originates from system requirements. A system requirement captures customer expectations, operating environments, physical safety limitations, and regulatory standards. The firmware engineering team decomposes these into a formal Software Requirements Specification (SRS).

1.1 Anatomy of a Robust Firmware Requirement

Ambiguous requirements produce defective firmware. Industry standards such as ISO 26262 and IEC 62304 mandate that every software requirement must be unambiguous, verifiable, testable, and uniquely identifiable.

Field Example Specification Significance in C Implementation
Requirement ID REQ_SW_TEMP_042 Referenced in C Doxygen comments, Git commits, and test assertions.
Type Functional / Safety Critical (ASIL B / SIL 2) Determines coding standard stringency (e.g., MISRA Mandatory vs Required).
Functional Statement "The firmware shall sample the PT100 temperature sensor at 50 Hz ± 2% via SPI1." Dictates hardware timer prescaler and reload values (20 ms period).
Safety / Fail-Safe "If temperature exceeds 85.0°C for > 100 ms, de-energize the heater relay within 10 ms." Guarantees dedicated hardware comparator or high-priority timer interrupt.
Verification Method Automated Host Unit Test + Hardware HIL Test Maps directly to test_temp_sensor.c and automated HIL test rack.

1.2 Bi-Directional Traceability Matrix (RTM)

In an audit, you must demonstrate bi-directional traceability:

  • Forward Traceability: Can every customer requirement be traced down to an architectural module, a specific C function, and a unit test?
  • Backward Traceability: Does every line of C code exist for a documented reason? (Any code without a corresponding requirement is deemed dead code or unintended functionality, strictly forbidden under DO-178C Level A and ISO 26262 ASIL D).
/**
 * @file    sensor_temp.c
 * @brief   Temperature Acquisition and Over-Temperature Protection Driver
 * @implements REQ_SW_TEMP_042, REQ_SW_TEMP_043
 * @standard   ISO 26262 ASIL-B
 */
#include "sensor_temp.h"
#include "bsp_gpio.h"

#define MAX_SAFE_TEMP_MILLICELSIUS   (85000L)
#define MAX_OVERTEMP_DUR_TICKS       (5U)       /* 5 * 20ms = 100ms */

static uint32_t s_overtemp_counter = 0U;

void SensorTemp_ProcessSample(int32_t current_temp_mc)
{
    /* Trace: REQ_SW_TEMP_043 - Over-temperature safety cutoff */
    if (current_temp_mc > MAX_SAFE_TEMP_MILLICELSIUS) {
        s_overtemp_counter++;
        if (s_overtemp_counter >= MAX_OVERTEMP_DUR_TICKS) {
            BSP_Relay_Deenergize(); /* Force safe state within 10ms */
        }
    } else {
        s_overtemp_counter = 0U;
    }
}

2. Phase 2: Hardware-Software Partitioning & Architecture

Before writing application logic, the lead systems and firmware architects perform Hardware/Software Partitioning. They decide which tasks belong in hardware logic (DMA streams, CRC hardware accelerators, PWM timer dead-time generators) and which tasks run in firmware.

2.1 Layered Architecture Model

To ensure the business logic is portable across silicon revisions and testable on a Linux development workstation without hardware attached, the codebase must adhere to strict architectural layers:

  1. Application Layer: Pure business logic, decision trees, control loops (PID), telemetry encoders. Zero hardware register dependencies.
  2. Services & Middleware: Ring buffers, software timer wheels, state machine dispatchers, communication protocol stacks (CANopen, Modbus, MQTT).
  3. Device Driver Layer: Chip-specific drivers for external sensors, EEPROMs, displays, and motor drivers (e.g., BME280, DRV8301).
  4. Hardware Abstraction Layer (HAL): Clean generic interfaces for MCU peripherals (I2C_Write(), GPIO_SetPin()).
  5. Board Support Package (BSP) & Startup: Silicon-level vector tables, clock tree init, pin-mux configuration, and linker script layout.

2.2 Memory Budgeting & Sizing

Embedded systems operate within severe static memory envelopes. The architect must create a deterministic static memory budget before implementation:

  • Flash Budget: Vector Table (1 KB) + Bootloader (32 KB) + App Image (256 KB) + Factory Config (16 KB) + Calibration Data (16 KB).
  • SRAM Budget: Stack (allocated conservatively for worst-case ISR nesting, e.g. 4 KB) + .data / .bss (static global variables, e.g. 20 KB) + DMA circular buffers (8 KB). Dynamic heap (malloc) is sized to 0 KB.

3. Phase 3: Detailed Design & State Machine Modeling

Unstructured firmware written with arbitrary if-else chains degenerates into "spaghetti code" as features grow. Complex firmware is modeled formally using Finite-State Machines (FSMs) or Hierarchical State Machines (HSMs) before coding.

Design Rule: Every mission-critical peripheral driver or application supervisor must have an accompanying State Transition Table mapping current state + event → guard condition, action callback, and next state. 
/* Tabular 2D State Machine Transition Entry */
typedef enum {
    STATE_BOOT = 0,
    STATE_SELF_TEST,
    STATE_IDLE,
    STATE_ARMED,
    STATE_FAULT,
    STATE_MAX
} SystemState_t;

typedef enum {
    EVENT_POWER_ON = 0,
    EVENT_TEST_PASSED,
    EVENT_TEST_FAILED,
    EVENT_ARM_COMMAND,
    EVENT_EMERGENCY_STOP,
    EVENT_MAX
} SystemEvent_t;

typedef void (*StateAction_t)(void);

typedef struct {
    SystemState_t next_state;
    StateAction_t action;
} StateTransition_t;

/* Constant transition matrix stored strictly in Flash (.rodata) */
static const StateTransition_t g_state_table[STATE_MAX][EVENT_MAX] = {
    [STATE_BOOT] = {
        [EVENT_POWER_ON] = { STATE_SELF_TEST, Action_RunPOST }
    },
    [STATE_SELF_TEST] = {
        [EVENT_TEST_PASSED] = { STATE_IDLE,  Action_InitPeripherals },
        [EVENT_TEST_FAILED] = { STATE_FAULT, Action_TriggerAlarm }
    },
    [STATE_IDLE] = {
        [EVENT_ARM_COMMAND]    = { STATE_ARMED, Action_EngageMotors },
        [EVENT_EMERGENCY_STOP] = { STATE_FAULT, Action_IsolateActuators }
    },
    [STATE_ARMED] = {
        [EVENT_EMERGENCY_STOP] = { STATE_FAULT, Action_IsolateActuators }
    }
};

4. Phase 4: Embedded C Implementation & Coding Standards

Embedded C implementation demands strict defensive disciplines. In desktop applications, an invalid pointer causes a crash report and an OS exit. In automotive or medical devices, an unhandled trap can cause catastrophic physical injury.

4.1 Cardinal Rules of Embedded C Production Code

  • Prohibit Dynamic Heap Allocation: Functions like malloc(), calloc(), and free() are banned by MISRA-C Directive 4.12. Heap allocation introduces runtime indeterminism, memory fragmentation, and potential allocation failures in long-running systems.
  • Fixed-Width Integer Types: Always use stdint.h types (uint8_t, int32_t, uint32_t). The standard C int varies in width between 16-bit and 32-bit compilers, causing silent overflow bugs.
  • Volatile for Hardware Registers & Shared Flags: Any memory address modified outside the normal compiler control flow (peripherals, DMA, ISRs) must be qualified with volatile to prevent the compiler from caching values in CPU registers.
  • Defensive Parameter Validation: All public API entry points must check for NULL pointers and numerical range violations before performing memory or peripheral operations.
View Dangerous / Non-Compliant C Code (Anti-Pattern) 
/* ANTI-PATTERN: Non-deterministic, unsafe embedded C */
int calculate_crc(char *data, int len) {
    char *buf = (char *)malloc(len); // VIOLATION: Heap allocation!
    int crc = 0;
    for(int i = 0; i <= len; i++) {   // VIOLATION: Off-by-one buffer overrun!
        crc += data[i];
    }
    free(buf);
    return crc;
}
Program 6.3-A: Non-compliant code exhibiting heap usage, ambiguous integer types, and potential memory leaks
/* PRODUCTION-GRADE: MISRA-C compliant, deterministic, defensive */
#include <stdint.h>
#include <stdbool.h>
#include "status_codes.h"

Status_t CRC16_Calculate(const uint8_t * const p_data, 
                         uint16_t length, 
                         uint16_t * const p_crc_out)
{
    /* Rule: Validate all pointers and ranges before access */
    if ((p_data == NULL) || (p_crc_out == NULL) || (length == 0U)) {
        return STATUS_ERROR_INVALID_PARAM;
    }

    uint16_t crc = 0xFFFFU;
    for (uint16_t i = 0U; i < length; ++i) {
        crc ^= (uint16_t)p_data[i];
        for (uint8_t bit = 0U; bit < 8U; ++bit) {
            if ((crc & 0x0001U) != 0U) {
                crc = (crc >> 1U) ^ 0xA001U;
            } else {
                crc = (crc >> 1U);
            }
        }
    }

    *p_crc_out = crc;
    return STATUS_OK;
}

5. Phase 5: Static Analysis & Quality Gates

Static Code Analysis inspects source code without executing it, checking for syntax violations, memory leaks, unreachable code, integer overflows, and MISRA-C conformance.

5.1 Multi-Layered Static Analysis Toolchain

  1. Compiler Warning Enforcement: Compiling with -Wall -Wextra -Werror -pedantic -Wconversion -Wshadow guarantees that no warning passes into the build.
  2. Open-Source Linters: cppcheck --enable=all --inconclusive --error-exitcode=1 executed during local development and pre-commit Git hooks.
  3. Commercial Deep-Static Analyzers: Tools like PC-lint Plus, Coverity, or Polyspace verify formal mathematical proofs that variables cannot exceed bounds or divide by zero.

6. Phase 6: Dynamic Verification & Testing Hierarchy

In the V-Model, verification mirrors the design phases on the left side of the "V". Testing is performed in three progressive tiers:

Testing Tier Execution Environment Test Tooling Primary Objective
Tier 1: Unit Testing Host PC / Linux CI (x86_64) Unity, CMock, Ceedling, GoogleTest Verify algorithms, drivers, and state transitions with mocked hardware interfaces. Fast feedback (seconds).
Tier 2: Integration Testing Target MCU or Virtual Emulators (QEMU, Renode) GDB automated scripts, OpenOCD, PySerial Verify interactions between RTOS tasks, DMA controllers, peripheral ISRs, and hardware timing jitter.
Tier 3: Hardware-in-the-Loop (HIL) Automated Test Racks with physical hardware CANoe, NI LabVIEW, Rigol Oscilloscopes, Logic Analyzers System validation against real physical loads, bus errors, brown-out power spikes, and environmental stress.

6.1 Structural Code Coverage Metrics

  • Statement Coverage: Has every executable line been touched at least once? (Baseline requirement).
  • Branch / Decision Coverage: Has every if, else, and case branch evaluated to both TRUE and FALSE?
  • Modified Condition / Decision Coverage (MC/DC): Has every condition in a multi-condition boolean statement (e.g., if (A || B)) been proven to independently affect the decision outcome? (Mandated by DO-178C Level A and ISO 26262 ASIL D).

7. Phase 7: Cross-Compilation, Linker Scripts & Binary Artifacts

Embedded C source files are compiled on a host computer (x86_64) targeting a completely different processor architecture (e.g., ARM Cortex-M4 32-bit RISC). This requires an Embedded Cross-Compiler Toolchain like arm-none-eabi-gcc.

7.1 The Four Stages of the Build Pipeline

  1. Preprocessor (cpp): Expands #include directives, strips comments, and evaluates macro expressions (#define, #ifdef). Emits .i files.
  2. Compiler (cc1): Translates preprocessed C code into architecture-specific Assembly instructions. Emits .s files.
  3. Assembler (as): Assembles human-readable assembly into machine-code relocatable object files. Emits .o files.
  4. Linker (ld): Merges all object files, resolves function and global variable addresses, and places sections according to the Linker Script (.ld). Emits the final .elf binary.

7.2 Anatomy of the Linker Script

The linker script dictates the exact byte-level physical address where machine code and data reside inside silicon Flash and SRAM: 

/* Minimal ARM Cortex-M4 Linker Script (stm32f401.ld) */
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 96K
}

SECTIONS
{
  /* Interrupt Vector Table placed at beginning of Flash */
  .isr_vector :
  {
    . = ALIGN(4);
    KEEP(*(.isr_vector))
    . = ALIGN(4);
  } > FLASH

  /* Executable code and constants */
  .text :
  {
    . = ALIGN(4);
    *(.text)
    *(.text*)
    *(.rodata)
    *(.rodata*)
    . = ALIGN(4);
    _etext = .; 
  } > FLASH

  /* Initialized variables: load in Flash, executed in RAM */
  .data : AT (_etext)
  {
    . = ALIGN(4);
    _sdata = .;
    *(.data)
    *(.data*)
    . = ALIGN(4);
    _edata = .;
  } > RAM

  /* Zero-initialized variables */
  .bss :
  {
    . = ALIGN(4);
    _sbss = .;
    *(.bss)
    *(.bss*)
    . = ALIGN(4);
    _ebss = .;
  } > RAM

  /* Stack boundary symbol for CRT0 initialization */
  _estack = ORIGIN(RAM) + LENGTH(RAM);
}
Program 6.4: Standard Cortex-M Linker Script assigning memory regions and boundary symbols

7.3 Output Artifacts

  • firmware.elf: Executable and Linkable Format containing machine code, symbol names, and DWARF debugging data used by GDB.
  • firmware.hex: Intel HEX ASCII format with explicit physical address records, utilized by factory gang programmers.
  • firmware.bin: Raw binary representation containing the exact byte-for-byte stream programmed into MCU flash.
  • firmware.map: Crucial text report listing every object file, function address, static variable size, and RAM/Flash consumption.

8. Phase 8: Cryptographic Signing, CRC & Secure Boot Packaging

A raw binary image cannot be deployed directly to modern connected devices. To protect against malicious firmware injection and memory corruption, production firmware must be packaged with a Cryptographic Header verified by an on-chip Secure Bootloader. 

/* 64-byte Canonical Production Firmware Header */
typedef struct __attribute__((packed)) {
    uint32_t magic_word;        /* E.g., 0x41505443 ("APTC") */
    uint32_t header_version;   /* Header layout version */
    uint32_t app_version;      /* Semantic version: Major.Minor.Patch.Build */
    uint32_t payload_size_bytes;/* Exact size of the raw application binary */
    uint32_t load_address;     /* Physical Flash entry address (e.g. 0x08020000) */
    uint32_t crc32;            /* CRC32 of payload for rapid integrity check */
    uint8_t  sha256[32];       /* Cryptographic digest of the application payload */
    uint8_t  ecdsa_sig[64];    /* Elliptic Curve Digital Signature (NIST P-256) */
} FirmwareHeader_t;

9. Phase 9: Factory Provisioning & Mass Flashing

During mass manufacturing on the assembly line, newly assembled printed circuit boards (PCBs) arrive with completely blank silicon microcontrollers.

9.1 Manufacturing Test & Provisioning Workflow

  1. Bed-of-Nails Test Fixture: Spring-loaded pogo pins contact SWD (SWCLK, SWDIO), UART, power rails (3.3V, GND), and test points.
  2. Power Rail In-Circuit Test (ICT): Measure resistance and supply currents to ensure zero shorts before applying active power.
  3. Primary Flashing: An automated gang programmer (e.g. Segger Flasher ATE or STM32CubeProgrammer CLI) flashes the Primary Bootloader, Option Bytes, and Calibration Data.
  4. Board Functional Self-Test: The factory firmware executes an automated suite testing all peripheral buses, crystal oscillator lock, and sensor communications, logging results to manufacturing MES servers.
  5. Silicon Locking (RDP): Once verified, the programmer writes MCU Option Bytes to enable Readout Protection (RDP Level 1 or 2), permanently disabling SWD debug access to prevent competitors or hackers from dumping intellectual property.
#!/usr/bin/env bash
# Automated Production Flashing Script via STM32_Programmer_CLI
set -e

MCU_SN="$1"
BIN_FILE="build/production_firmware_v2.1.4.bin"

echo "=== Flashing Device S/N: ${MCU_SN} ==="

# 1. Connect, Erase Flash, and Program Signed Binary
STM32_Programmer_CLI -c port=SWD sn="${MCU_SN}" mode=UR -e all \
    -w "${BIN_FILE}" 0x08000000 -v

# 2. Lock Flash Readout Protection (RDP Level 1)
STM32_Programmer_CLI -c port=SWD sn="${MCU_SN}" -ob RDP=0xBB

echo "=== Flashing & Security Lock Succeeded ==="

10. Phase 10: In-Field Deployment & Firmware Over-The-Air (FOTA)

Once products are in customers' hands or deployed in the field (automobiles, satellites, medical clinics), physical SWD access is impossible. The system must support reliable, fail-safe updates via Bootloaders and FOTA.

10.1 Dual-Bank A/B Flash Architecture

The golden rule of remote firmware updates: Never overwrite currently running firmware in-place. If power is lost mid-flash, the device will be "bricked". Robust systems utilize a Dual-Bank Flash layout:

[0x08000000 - 0x0801FFFF] → Secure Bootloader & Keys (128 KB)
[0x08020000 - 0x080FFFFF] → Slot A: Active Application (896 KB) [Currently Running]
[0x08100000 - 0x081DFFFF] → Slot B: Staging Slot (896 KB) [Receives New OTA]
[0x081E0000 - 0x081FFFFF] → Non-Volatile Storage (NVS) & Boot Flags (128 KB)

10.2 Safe Update & Automatic Rollback Protocol

  1. Download & Stream: Application receives incoming chunks over CAN, BLE, or Cellular, writing to the Staging Slot (Slot B).
  2. Header & Cryptographic Check: Bootloader verifies SHA-256 digest and ECDSA public key signature before touching the active application.
  3. Trial Execution Flag: Bootloader sets the boot flag to TRIAL_RUN and vectors execution to Slot B.
  4. Watchdog Confirmation: Slot B must boot successfully, perform self-tests, and write a confirmation flag (IMAGE_CONFIRMED) within 30 seconds.
  5. Automatic Rollback: If the trial firmware triggers a HardFault or the hardware watchdog resets the MCU before confirmation, the Bootloader automatically reverts execution back to Slot A!

Topic Quiz (10 Questions)

1. In safety-critical embedded systems, what is "Backward Traceability"?
  • The ability to roll back the microcontroller to an older firmware version over UART.
  • Demonstrating that every line of production source code traces back to an approved system or software requirement, proving zero undocumented dead code exists.
  • Stepping backward through CPU instructions using a JTAG hardware debugger.
  • Reversing the direction of current in an H-bridge actuator driver.
Backward traceability proves that no unauthorized or orphaned code exists in the binary. Every function must exist for a verified requirement.
2. Why does MISRA-C Directive 4.12 prohibit the use of dynamic memory allocation (malloc, calloc, free) in production embedded C?
  • Dynamic memory allocation is only supported in C++, not in C.
  • Heap allocation introduces non-deterministic execution times, heap fragmentation, and the catastrophic risk of runtime allocation failure.
  • Microcontroller silicon does not have hardware memory management units (MMUs) capable of reading RAM.
  • Dynamic memory allocation causes the CPU clock frequency to drop by 50%.
Heap allocation cannot guarantee deterministic execution time and invariably leads to fragmentation in long-running embedded systems. Static allocation guarantees all memory is bounded at link time.
3. What is the fundamental role of the Linker Script (.ld file) during the cross-compilation pipeline?
  • It executes unit tests on the host computer before compilation starts.
  • It converts C language syntax into Python scripts for test automation.
  • It defines physical memory boundaries (Flash, RAM) and maps code and data sections (.text, .rodata, .data, .bss, vector table) to exact physical target addresses.
  • It encrypts the source code to protect intellectual property from competitors.
The linker script instructs the GNU Linker (ld) where physical memory banks reside and where each symbol and section must be mapped in target address space.
4. What is the difference between a .elf file and a .bin file?
  • The .elf file contains metadata, section headers, symbol tables, and DWARF debug info; the .bin file is a stripped, raw byte-for-byte binary image flashed directly into memory.
  • The .bin file can only run on Linux; the .elf file can only run on ARM Cortex-M.
  • The .elf file is compressed with ZIP; the .bin file is uncompressed.
  • There is no difference; they are identical files with different extensions.
An ELF file contains rich debugging symbols and sections used by GDB. The raw .bin contains only the raw bytes destined for flash without headers.
5. In a Dual-Bank Flash A/B update scheme, why is an automated "Rollback Guard" essential?
  • To allow the user to downgrade to an older software version if they dislike the new UI.
  • If the newly installed firmware crashes, hangs, or fails self-tests during its trial run, the bootloader automatically reverts to the previous working slot, preventing field bricking.
  • To save flash memory space by compressing the firmware binary.
  • To prevent the microcontroller from overheating during flash writes.
Rollback protection guarantees high availability. If the new slot fails to boot and kick the watchdog or mark itself confirmed, the bootloader reverts to the known-good image.
6. What critical security step is performed during factory mass provisioning to protect intellectual property?
  • Removing the crystal oscillator from the PCB.
  • Overclocking the MCU core by 200%.
  • Configuring Option Bytes to activate Readout Protection (RDP Level 1 or 2), disabling SWD/JTAG debug port access.
  • Filling the remaining flash sectors with random ascii characters.
Setting Readout Protection (RDP) disables hardware debug probe access, preventing unauthorized extraction of binary firmware via SWD/JTAG.
7. Why are unit tests in professional embedded systems typically executed on a Host PC (Linux x86_64) rather than directly on target microcontrollers?
  • Microcontrollers cannot run any test assertion code.
  • Host testing executes thousands of tests in seconds, integrates seamlessly into CI/CD pipelines, uses AddressSanitizer/Valgrind, and tests logic before hardware silicon is fabricated.
  • Because target microcontrollers only support assembly code.
  • Host execution eliminates the need for any hardware integration testing.
Host-based testing provides instantaneous developer feedback, runs headlessly in cloud CI pipelines, and allows decoupling algorithmic logic from hardware peripherals via mocks.
8. What is the role of CMock in an embedded C unit test environment?
  • A cross-compiler that translates C code to ARM assembly.
  • A tool that parses C header files and automatically generates mock functions to simulate hardware peripherals and external dependencies.
  • A hardware probe used to measure voltage transients on I2C buses.
  • A flash memory erase utility for ST-LINK programmers.
CMock inspects your C interface headers and generates mock implementations where you can configure expected arguments and canned return values.
9. What cryptographic mechanism ensures that an incoming OTA firmware update was created by the legitimate device manufacturer and was not tampered with?
  • A simple XOR checksum.
  • An asymmetric digital signature (e.g., ECDSA NIST P-256 or RSA-3072) verified against a public key burned into on-chip Secure Boot ROM.
  • A secret string stored in an unencrypted C header file.
  • Checking if the file extension ends in .bin.
Asymmetric cryptography ensures only holders of the private key (the OEM) can sign binary images, while the device verifies using the embedded public key.
10. What code coverage metric required by DO-178C Level A and ISO 26262 ASIL D verifies that each condition in a multi-condition Boolean expression independently affects the decision outcome?
  • Line Coverage
  • Function Call Coverage
  • MC/DC (Modified Condition / Decision Coverage)
  • Cyclomatic Complexity Index
MC/DC is the gold standard of dynamic structural coverage for highest-tier functional safety standards.

Hands-On Engineering Assignments

Assignment 1: Requirements Deconstruction & Traceability Matrix

Task: Take a high-level customer requirement: "The automotive steering angle sensor must report the wheel position over CAN-FD every 10 ms, with fault detection triggering a limp-home state within 20 ms." Deconstruct this into three atomic software requirements (Functional, Timing, and Safety). Write the C header file declarations and Doxygen traceability tags implementing them.

Assignment 2: Host-Based Mock Test Harness with Unity

Task: Write a pure C motor controller supervisor function. Using the Unity unit-test framework on Linux/WSL, mock the hardware GPIO and timer interfaces. Write test cases that verify normal operation, overcurrent shutdown, and timeout fallback without requiring physical hardware.

Assignment 3: Linker Script Partitioning for Dual-Bank Bootloading

Task: Create a GNU Linker Script (.ld) for a 1 MB Flash Cortex-M4 microcontroller. Divide Flash into Bootloader (128 KB), Application Slot A (448 KB), and Application Slot B (448 KB). Ensure that Vector Table symbols are properly aligned to 512-byte boundaries to support ARM VTOR reallocation.

Assignment 4: Binary Packaging & Cryptographic Checksum Tool

Task: Write a host C or Python build-step script that takes a raw firmware.bin file, computes its CRC32 and SHA-256 digest, prepends the 64-byte FirmwareHeader_t structure, and outputs a production-ready firmware_signed.bin.

Assignment 5: Automated Factory Flashing & Fusing Script

Task: Write a bash or Python script utilizing STM32_Programmer_CLI or Segger JLink.exe that automates factory programming: probe detection, chip erase, programming firmware_signed.bin, verifying checksums, configuring Option Bytes for Readout Protection (RDP), and generating a serial-number manufacturing log file.
