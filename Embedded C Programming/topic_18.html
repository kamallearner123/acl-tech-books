Topic 18

MISRA-C Concepts & Safety Compliance

The C programming language was conceived in 1972 as an expressive systems programming language designed for operating system kernel construction. To maximize compiler performance on early mini-computers, the ISO C standard intentionally left dozens of language constructs either Undefined (e.g., signed integer overflow, division by zero), Unspecified (e.g., order of function argument evaluation), or Implementation-Defined (e.g., bitwise right shift of negative values).

In safety-critical domains — including automotive powertrain control (ISO 26262), aerospace avionics (DO-178C), medical devices (IEC 62304), and railway interlocking (EN 50128) — undefined behavior is utterly intolerable. MISRA-C (Motor Industry Software Reliability Association) provides a rigorous, restricted subset of the C language that systematically eliminates insecure, ambiguous, and non-deterministic features.

18.1 The MISRA-C Rule Classification Taxonomy

The current canonical benchmark is MISRA-C:2012 (incorporating Amendments 1, 2, and 3 for C99 and C11 support). It organizes guidelines into Directives (guidelines requiring process verification or design documentation) and Rules (testable syntactic and semantic constraints enforceable by static analyzers).

18.2 Canonical High-Impact MISRA-C Rules

Below are the most critical rules every embedded C developer must understand and apply:

Rule 15.6: Braces in Control Statements (Mandatory / Required)

The body of an iteration-statement or a selection-statement shall be an enclosed compound statement in braces. 

/* VIOLATION: Omitted braces risk accidental code execution (Apple goto fail bug) */
if (status != OK)
    goto cleanup;

/* COMPLIANT: Explicit braces leave no syntactic ambiguity */
if (status != OK) {
    goto cleanup;
}

Rule 14.4: Essentially Boolean Expressions (Required)

The controlling expression to an if-statement or while-loop shall have essentially boolean type. 

uint32_t count = get_event_count();

/* VIOLATION: Using integer count as implicit boolean truth */
if (count) { ... }

/* COMPLIANT: Explicit relational comparison yielding boolean */
if (count > 0U) { ... }

Rule 17.7: Non-Void Return Values (Required)

The value returned by a function having non-void return type shall be used or explicitly cast to void. 

/* VIOLATION: Return code silently ignored */
uart_send_byte(0x55);

/* COMPLIANT: Checked or explicitly acknowledged as intentionally discarded */
if (uart_send_byte(0x55) != UART_OK) {
    handle_comm_fault();
}

/* COMPLIANT: Casting to (void) proves intentional omission to auditor */
(void)snprintf(buf, sizeof(buf), "%u", count);

Rule 21.3: Dynamic Memory Allocation Prohibited (Required)

The memory allocation and deallocation functions of <stdlib.h> shall not be used (malloc, calloc, free, realloc).

Dynamic heap allocation leads to non-deterministic allocation latency, heap fragmentation, out-of-memory memory exhaustion, and memory leaks. Safety-critical embedded systems allocate all memory statically at compile-time or use fixed-size block pools.

18.3 The Essential Type Model & Type Conversions

Standard C performs silent implicit promotions: any integer narrower than int (such as uint8_t or int16_t) is automatically promoted to a signed int during arithmetic expressions. If signed overflow occurs, standard C permits undefined behavior!

MISRA-C:2012 introduces the Essential Type Model (Section 10), enforcing strict rules to prevent accidental signed/unsigned conversions and truncated assignments: 

uint8_t a = 200U;
uint8_t b = 100U;

/* VIOLATION (Rule 10.3): (a + b) is promoted to signed int (300).
   Assigning it to uint16_t without explicit cast causes essential type mismatch. */
uint16_t sum = a + b; 

/* COMPLIANT: Explicit cast matches the essential type destination */
uint16_t sum_safe = (uint16_t)a + (uint16_t)b;

18.4 The Formal Deviation Procedure

A common myth is that 100% compliance with every MISRA-C rule is possible without exceptions. In bare-metal microcontroller systems, this is technically impossible. For example, accessing a memory-mapped peripheral register requires casting an integer address to a volatile pointer: 

/* Directly violates MISRA-C:2012 Rule 11.4 (conversion between int and pointer) */
#define USART1 ((USART_TypeDef *) 0x40011000UL)

When a rule cannot be satisfied, engineers must author a formal Deviation Record. An approved deviation requires:

  • Guideline Identifier: e.g., MISRA-C:2012 Rule 11.4 (Advisory/Required).
  • Scope: Specific line numbers and file (e.g., bsp_registers.h, lines 45–120).
  • Technical Justification: Why adherence is physically impossible (hardware register mapping).
  • Safety Evidence: Verification that the target memory address is verified against the vendor microcontroller reference manual, 4-byte aligned, and marked volatile.

18.5 Automated Compliance with Cppcheck

Compliance should never depend on manual eyeball review. Open-source tools like cppcheck include a dedicated MISRA addon that parses compiler ASTs and flags violations directly in CI: 

# Run MISRA-C static analysis with Cppcheck in terminal
cppcheck --enable=all --addon=misra.py --suppress=missingIncludeSystem src/

18.6 Code Comparison: Fragile vs. MISRA-C:2012 Compliant C

Compare a typical standard C routine with a refactored version conforming to MISRA-C:2012.

Compare Code: Packet Checksum Calculation

❌ Non-Compliant Standard C

/* Multiple MISRA Violations */
int calc_sum(char *p, int len) {
    int sum; /* Uninitialized */
    int i;
    for (i = 0; i < len; i++)
        sum += *p++; /* No braces, side-effect */
    if (sum) /* Not boolean */
        return sum;
} /* Missing return on else path */

Violations: Missing braces (15.6), uninitialized variable (9.1), non-boolean condition (14.4), unhandled return path (17.4), pointer arithmetic with side effect (13.3).

✔ MISRA-C:2012 Compliant

uint32_t calc_sum(
    const uint8_t * const p_data, 
    const uint32_t        len_bytes) 
{
    uint32_t sum = 0U;

    if (p_data != NULL) {
        for (uint32_t i = 0U; i < len_bytes; ++i) {
            sum += (uint32_t)p_data[i];
        }
    }

    return sum;
}

Compliance: Fully initialized variables, explicit types, explicit pointer null check, single deterministic return statement, proper compound braces.

18.7 Interactive Knowledge Check

Test your understanding of MISRA-C:2012 rule classifications, essential types, and deviations.

1. What is the fundamental difference between a MISRA-C "Mandatory" rule and a "Required" rule?
  • Mandatory rules apply only to automotive; Required rules apply to medical.
  • Mandatory rules must never be violated under any circumstances (no deviation permitted); Required rules may be violated only with an approved formal deviation record.
  • Mandatory rules are checked by the compiler; Required rules are checked by humans.
  • There is no difference; both terms are synonyms.
Explanation: Under MISRA-C compliance claims, Mandatory rules allow zero deviations. Required rules allow documented engineering deviations with safety justification.
2. Why does MISRA-C Rule 21.3 strictly forbid the use of malloc() and free() in safety-critical systems?
  • Because heap memory is only supported on 64-bit microprocessors.
  • Dynamic heap allocation introduces heap fragmentation, non-deterministic allocation time, and unpredictable out-of-memory crash risks.
  • Because malloc disables the SysTick interrupt during execution.
  • To reduce GCC compiler licensing costs.
Explanation: Safety-critical architectures require deterministic resource bounding. Heaps fragment over time, leading to spontaneous memory allocation failure under load.
3. What infamous software vulnerability demonstrated the necessity of MISRA-C Rule 15.6 (mandatory braces on control flow statements)?
  • The Heartbleed OpenSSL bug.
  • The Apple SSL/TLS "goto fail" security vulnerability.
  • The Ariane 5 rocket float overflow.
  • The Y2K bug.
Explanation: In 2014, an unbraced if (err) goto fail; goto fail; in Apple's SSL library caused a critical authentication bypass because the second goto fail; executed unconditionally.
4. What is the MISRA-C "Essential Type Model"?
  • A set of mandatory C++ classes.
  • A formal type system layered over ISO C to constrain dangerous implicit integer promotions and mixed-sign arithmetic.
  • A tool that converts C code to Rust automatically.
  • An ARM hardware register file.
Explanation: Standard C automatically promotes narrow integers to signed ints. The Essential Type Model tracks original intended types and enforces explicit casting.
5. If a developer needs to assign 0x40011000UL to a pointer to configure a hardware peripheral, how is this handled under MISRA-C?
  • By modifying the silicon mask inside the microcontroller chip.
  • By filing a formal Deviation Record for Rule 11.4 justifying the memory-mapped register access.
  • By disabling compiler optimizations.
  • By pretending the peripheral does not exist.
Explanation: Casting integer addresses to hardware pointers is unavoidable in bare-metal drivers; a formal deviation record documents the necessity and safety checks.
6. Why does MISRA-C Rule 17.7 require that non-void return values be explicitly checked or cast to (void)?
  • To prevent register spilling in the CPU pipeline.
  • To ensure that failure status codes (e.g. from I2C or flash write operations) are not silently ignored by the caller.
  • Because void casts make functions execute twice as fast.
  • To satisfy the ISO C89 grammar.
Explanation: Ignoring return codes is a primary source of silent corruption. Casting to (void) forces developers to make an explicit, conscious choice when ignoring a return.
7. Under MISRA-C, why is #include "my_file.c" strictly prohibited?
  • Including implementation .c files violates modular translation unit separation and causes duplicate symbol and static scope anomalies.
  • Because C preprocessors only accept files ending in .h.
  • Because it causes the linker to crash.
  • It disables inline assembly.
Explanation: MISRA Rule 20.3 bans including .c files: headers (.h) declare interfaces; implementation files (.c) must be compiled independently.
8. What does MISRA-C mandate regarding recursion (functions calling themselves directly or indirectly)?
  • Recursion is allowed if limited to 100 levels.
  • Direct and indirect recursion is strictly prohibited (Rule 17.2) to prevent unbounded stack growth and guarantee deterministic stack depth.
  • Recursion is mandatory in all tree-traversal algorithms.
  • Recursion is permitted only on ARM Cortex-M7 cores.
Explanation: In safety-critical embedded systems, stack overflow is catastrophic. Banning recursion allows static analyzers to calculate the exact worst-case stack depth at compile time.
9. What is the requirement regarding the default: label in a switch statement under MISRA-C Rule 16.4?
  • It must be placed as the first label in the switch block.
  • Every switch statement shall have a default label terminated by a break or throw statement.
  • It must only be used if there are more than 10 cases.
  • It is forbidden because it slows down binary jump tables.
Explanation: A mandatory default clause ensures that unexpected or corrupted integer/enum values are trapped and handled defensively.
10. Which international functional safety standard explicitly references MISRA-C as a recognized software coding guideline for road vehicles?
  • ISO 9001
  • ISO 26262
  • IEEE 802.11
  • PCI-DSS
Explanation: ISO 26262 Part 6 explicitly lists MISRA-C as a recommended language subset for achieving Automotive Safety Integrity Levels (ASIL A through D).

18.8 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to audit codebases and establish automated MISRA static verification pipelines.

Assignment 1: Cppcheck MISRA Addon Integration

Task: Configure cppcheck with the official misra.py addon in your local workspace. Run static analysis on a sample embedded driver. Inspect the violation log and identify at least three separate MISRA-C rule infractions.

Assignment 2: Formal Deviation Authoring

Task: In a GPIO driver, map a 32-bit hardware base address (e.g. 0x40020000UL) to a peripheral pointer structure. Author a formal, audit-ready MISRA Deviation Record in Markdown citing Rule 11.4 with complete technical justification and safety evidence.

Assignment 3: Essential Type Model Refactoring

Task: Take a math routine with mixed uint8_t, int16_t, and signed constants. Refactor the code using explicit type promotions and casts until it passes MISRA-C Rules 10.1, 10.3, and 10.4 without a single diagnostic warning.

Assignment 4: Elimination of Dynamic Memory

Task: Take an existing message buffer module that uses malloc() and free(). Refactor it to use a statically allocated, fixed-block memory pool manager (Rule 21.3 compliant). Prove that allocation latency is constant $O(1)$ and heap fragmentation is zero.

Assignment 5: CI/CD MISRA Quality Gate

Task: Write a shell script or Makefile target make misra-gate. Ensure that any commit containing an unsuppressed MISRA Mandatory rule violation causes the build to exit with an error code, preventing code merging.
