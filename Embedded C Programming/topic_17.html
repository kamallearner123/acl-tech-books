Topic 17

Documentation Practices & Doxygen

In firmware engineering, code comments must never merely paraphrase the C syntax: writing i++; /* increment i */ is worse than useless, as it adds visual noise without conveying design intent. A firmware developer needs to know the invisible contract: Is this function safe to call from an Interrupt Service Routine (ISR)? Does it block? Which hardware registers does it touch? What are the valid input ranges and electrical timing prerequisites?

This chapter establishes professional firmware documentation standards utilizing Doxygen, the industry-standard documentation extraction tool, alongside Architecture Decision Records (ADRs) to capture technical rationale that code alone cannot express.

17.1 The Doxygen Tag Taxonomy

Doxygen comments begin with the block marker /** or the line marker ///. The core tags used in embedded software interfaces include:

Tag Purpose Embedded Significance
@file File banner & overview Declares the driver module, copyright, version, and hardware target.
@brief Single-sentence summary Displayed in IDE hover tooltips and table-of-contents listings.
@param[in,out] Parameter direction & constraints Specifies pointer ownership, physical units, and allowed value ranges.
@return / @retval Return value specification Documents exact status enum meanings, error conditions, and error recovery.
@pre Precondition requirement Prerequisite hardware clocks, PLL locks, or initialized peripherals.
@post Postcondition guarantee State of peripheral or buffers after successful execution.
@warning Critical safety warnings Highlights electrical danger, non-reentrancy, or blocking behavior.
@note Silicon errata / design notes References chip silicon errata or hardware revision specifics.

17.2 The Firmware Execution Context Contract

One of the most catastrophic defects in embedded software occurs when a function that is non-reentrant or contains blocking delays is mistakenly invoked from inside a hardware Interrupt Service Routine (ISR).

17.3 Production Header Documentation Example

The following complete C header demonstrates production-grade Doxygen documentation for a non-volatile SPI Flash driver: 

/**
 * @file      spi_flash.h
 * @brief     Driver interface for Winbond W25Q64 64M-bit SPI NOR Flash memory.
 * @details   Implements sector erase, page programming, and high-speed DMA read.
 *            Compliant with JEDEC JESD216 standard.
 *
 * @author    Embedded Firmware Engineering Team
 * @copyright (c) 2026 Apt Computing Labs. All rights reserved.
 * @version   2.1.0
 */

#ifndef SPI_FLASH_H
#define SPI_FLASH_H

#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

/**
 * @brief SPI Flash status return codes.
 */
typedef enum {
    SPI_FLASH_OK = 0,               /**< Operation completed successfully. */
    SPI_FLASH_ERR_NULL_PTR,         /**< Provided buffer pointer was NULL. */
    SPI_FLASH_ERR_ADDR_OUT_OF_BOUNDS,/**< Byte address exceeds 8 MByte capacity. */
    SPI_FLASH_ERR_TIMEOUT,          /**< Flash status register busy timeout. */
    SPI_FLASH_ERR_BUSY              /**< Write/Erase cycle currently active. */
} SpiFlashStatus_t;

/**
 * @brief Erases a 4 Kilobyte sector in NOR Flash memory.
 *
 * @details Sends the 0x20 Sector Erase opcode followed by the 24-bit sector
 *          address. This function triggers an internal high-voltage erase
 *          operation lasting between 45 ms (typical) and 400 ms (maximum).
 *
 * @param[in] sector_address  Byte address within the sector to erase. Must be
 *                            4096-byte aligned (bits [11:0] == 0).
 *
 * @pre   The SPI peripheral must be initialized via spi_master_init().
 * @pre   The write-enable latch must be active (spi_flash_write_enable()).
 * @post  All 4096 bytes in the target sector are reset to 0xFF.
 *
 * @warning This function is NOT safe to invoke from an ISR context because
 *          it polls the internal WIP (Write-In-Progress) bit with a timeout.
 * @warning Sector erases wear flash cells; maximum endurance is 100,000 cycles.
 *
 * @retval SPI_FLASH_OK                 Sector erased successfully.
 * @retval SPI_FLASH_ERR_ADDR_OUT_OF_BOUNDS Address >= 0x00800000UL or unaligned.
 * @retval SPI_FLASH_ERR_TIMEOUT        Hardware did not clear WIP within 500 ms.
 */
SpiFlashStatus_t spi_flash_sector_erase_4k(const uint32_t sector_address);

#endif /* SPI_FLASH_H */

17.4 Architecture Decision Records (ADRs)

Code documentation explains how a function operates; an Architecture Decision Record (ADR) captures why a fundamental architectural choice was made over alternative designs.

ADRs are short text/markdown documents maintained directly within the Git repository (e.g. docs/adr/0004-use-cooperative-superloop.md). The standard lightweight format includes:

ADR 0004: Cooperative Superloop vs Preemptive RTOS

Status: Accepted

Context: Our battery-powered cardiac sensor uses an ARM Cortex-M0+ with 16 KB SRAM. We evaluated whether to introduce FreeRTOS or implement a cooperative run-to-completion superloop.

Decision: We selected a cooperative superloop with SysTick delta timing.

Consequences:

  • Positive: Zero RTOS context-switch overhead, saves ~6 KB SRAM in task stack allocations, deterministic execution order eliminates race conditions.
  • Negative: Every driver must guarantee run-to-completion execution under 1.5 ms; long tasks cannot preemptively yield without state machines.

17.5 Code Comparison: Cryptic vs. Fully Specified Header

Observe the contrast between a header that forces the user to guess hardware behavior and one that provides a bulletproof contract.

Compare Header Documentation: Motor Speed Controller

❌ Cryptic & Hazardous

/* Set motor speed */
int set_speed(int s);

/* Read sensor */
int read_sensor();

Questions Unanswered: What are the units of s (RPM, PWM duty cycle percent, raw timer counts)? What happens if s < 0? Can this be called from a timer interrupt?

✔ Doxygen Contract

/**
 * @brief Sets target rotational velocity.
 * @param[in] target_rpm Target speed [0..6000].
 * @pre   PWM timer initialized via bsp_pwm_init().
 * @note  Thread-safe; updates atomic compare register.
 * @retval STATUS_OK Target speed applied.
 * @retval STATUS_ERR_OUT_OF_RANGE Speed > 6000.
 */
MotorStatus_t motor_set_velocity_rpm(
    const uint16_t target_rpm);

Precision: Units, boundaries, prerequisites, thread safety, and return codes are completely defined.

17.6 Interactive Knowledge Check

Test your understanding of Doxygen syntax, firmware documentation contracts, and ADR structures.

1. What is the fundamental difference between @param[in] and @param[out] in Doxygen?
  • @param[in] variables must be floats; @param[out] variables must be integers.
  • @param[in] indicates read-only input data supplied by caller; @param[out] indicates pointer memory populated by the function as a return payload.
  • @param[in] applies only to registers; @param[out] applies only to stack variables.
  • There is no difference; they are interchangeable.
Explanation: Explicit parameter directional tags clarify pointer ownership and caller responsibilities for memory allocation.
2. Why is documenting the "Execution Context" (e.g., ISR vs Task) vital in embedded systems?
  • To instruct the linker which Flash memory sector to use.
  • Calling a blocking, mutex-locking, or non-reentrant function from an ISR causes deadlocks, crashes, or severe interrupt latency spikes.
  • Because Doxygen will fail to compile if context is missing.
  • To enable automatic hardware acceleration.
Explanation: ISRs run with elevated CPU priority and cannot block on mutexes or sleep. Marking an API as "ISR-Safe" or "Thread-Only" prevents catastrophic runtime deadlocks.
3. What Doxygen tag is used to document a specific return value and its corresponding meaning?
  • @output
  • @retval
  • @result_code
  • @status
Explanation: @retval <value> <description> generates clean tabular documentation of each specific return code.
4. What is the primary purpose of an Architecture Decision Record (ADR)?
  • To track developer hourly billing rates.
  • To record the context, technical rationale, and trade-offs of significant architectural decisions for future maintainers.
  • To replace unit test suites.
  • To store compiler optimization flags.
Explanation: ADRs document why a particular design was chosen over alternatives, preventing future engineers from unwittingly undoing intentional design choices.
5. What Doxygen comment syntax documents an enum field or struct member on the same line?
  • /**< Description */
  • /*> Description */
  • //< Description
  • #pragma doc Description
Explanation: The < character tells Doxygen that the comment applies to the preceding member on the same line.
6. What is a @pre precondition tag used for in a hardware driver header?
  • To specify the price of the microcontroller.
  • To specify conditions that must be true prior to invoking the function (e.g., peripheral clock enabled, interrupts disabled).
  • To list the author's previous projects.
  • To define the C compiler preprocessor mode.
Explanation: @pre explicitly states necessary prerequisites, such as requiring peripheral clock initialization before calling communication APIs.
7. Why should silicon errata workarounds be explicitly tagged with @note or @warning in firmware source code?
  • To prevent the compiler from generating Thumb-2 instructions.
  • To explain seemingly illogical code sequences (e.g., extra dummy reads or delays) so future maintainers do not delete them as "redundant".
  • Silicon errata do not affect firmware.
  • To automatically register the issue with the semiconductor foundry.
Explanation: Errata workarounds often look bizarre (e.g., clearing a bit twice or inserting two NOPs). Without clear notes citing the manufacturer's silicon errata notice, an optimizer or developer will delete them.
8. In Doxygen, what command generates a clickable cross-reference to another function or structure?
  • @goto
  • @see (or @ref)
  • @jump
  • @link_extern
Explanation: @see and @ref create hyperlinks in the generated HTML and PDF manuals to related functions, structures, and documents.
9. What is the danger of writing documentation comments that explain "how" instead of "why"?
  • The "how" quickly goes out of sync as the code is refactored, while failing to convey the underlying design motivation and safety constraints.
  • Doxygen will produce binary executable files instead of HTML.
  • Comments consume flash memory on the target microcontroller.
  • The GCC compiler will generate extra assembly instructions.
Explanation: The C code itself already demonstrates how the algorithm works. Documentation must explain why constraints exist, what trade-offs were made, and the safety rationale.
10. Which Doxygen configuration option must be enabled in the Doxyfile to produce warnings when public API functions lack documentation?
  • OPTIMIZE_FOR_FORTRAN = YES
  • WARN_IF_UNDOCUMENTED = YES
  • GENERATE_TREEVIEW = NO
  • DISABLE_INDEX = YES
Explanation: Setting WARN_IF_UNDOCUMENTED = YES allows continuous integration (CI) build pipelines to fail if a developer merges undocumented APIs.

17.7 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to master automated documentation pipelines and architectural contract design.

Assignment 1: Automated Doxygen Pipeline Setup

Task: Generate a production Doxyfile using doxygen -g. Configure it to extract documentation for C code, include call graphs via Graphviz Dot (HAVE_DOT = YES), and fail on warnings (WARN_AS_ERROR = YES). Generate the HTML output and verify the resulting navigation tree.

Assignment 2: Driver Header Contract Refactoring

Task: Take an undocumented I2C temperature sensor header. Write full Doxygen documentation for all functions, enums, and structs. Explicitly include @pre, @post, @param[in,out], @retval, and state whether each function is safe for ISR execution.

Assignment 3: Architecture Decision Record (ADR) Authoring

Task: Author an ADR in Markdown evaluating whether to use a DMA circular ring buffer versus byte-by-byte interrupt reception for an incoming 115200 baud UART GPS stream. Document the Context, Decision, Consequences, and latency/RAM trade-offs.

Assignment 4: Silicon Errata Documentation & Defensive Guard

Task: Research an actual STM32 or NXP erratum (e.g., STM32F4 I2C bus lockup when transmitting the address byte). Write a C recovery routine with full Doxygen citations referencing the exact manufacturer errata document number, date, and workaround steps.

Assignment 5: CI Linting for Missing Documentation

Task: Write a shell script or Makefile target make doc-check that executes Doxygen and parses stderr. Intentionally add an undocumented public function to a header and verify that the build script detects the warning and exits with non-zero exit code.
