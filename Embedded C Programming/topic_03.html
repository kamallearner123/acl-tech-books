Topic 3

Compile, Runtime, Link & Logic Errors

In firmware development, bugs do not merely manifest as crash popups or error logs; they can cause frozen microcontrollers, scrambled motor drive PWM signals, silent memory corruption, or hardware damage. Understanding the lifecycle stage at which an error occurs—whether caught by the preprocessor/compiler, flagged during linking, triggered as a CPU fault at runtime, or hiding as a subtle logic race condition—is critical to diagnostic efficiency.

A skilled embedded engineer builds a mental model of the error taxonomy, transforming cryptic compiler warnings and catastrophic ARM Cortex-M HardFault exceptions into actionable root-cause investigations.

3.1 Taxonomy of Firmware Defects

Firmware defects are classified into four distinct operational categories based on where in the software engineering pipeline they are discovered.

Defect Class Detection Phase Typical Root Causes Detection Tool
Compile-Time Errors Translation / Compilation Syntax errors, missing semicolons, type mismatches, macro redefinitions, static assertion failures. gcc -Wall -Wextra -Werror
Link-Time Errors Object Linking Undefined symbol references (undefined reference to `foo`), multiple symbol definitions, memory region overflow (SRAM/Flash full). ld / Linker Map file
Runtime Faults Target Silicon Execution Null-pointer dereferences, stack overflows, unaligned memory access, division by zero, bus/memory faults. HardFault_Handler, GDB, SWD probe
Logic & Concurrency Errors Target Silicon Execution Off-by-one loop boundaries, interrupt race conditions, missing volatile on ISR flags, deadlocks. Unit tests, Logic Analyzers, ITM tracing

3.2 Linker Errors: Demystifying Common Linker Failures

Because C compilation operates strictly on individual translation units (.c files), the compiler only verifies that function declarations exist. The linker is responsible for knitting object files together and assigning physical addresses. The two most common linker traps are:

1. Undefined Reference (undefined reference to `foo`)

This occurs when a header file declares a function prototype extern void foo(void); and code calls it, but the object file containing the definition foo.o was omitted from the linker command line or Makefile.

2. Multiple Definition of Symbol (multiple definition of `bar`)

A catastrophic mistake in C is placing variable definitions inside a header file without the extern qualifier: 

/* IN config.h -- WRONG: Generates duplicate definitions in every .c file that includes it! */
uint32_t system_baud_rate = 115200;

/* IN config.h -- CORRECT: Declaration only */
extern uint32_t system_baud_rate;

/* IN config.c -- CORRECT: Single definition in exactly one compilation unit */
uint32_t system_baud_rate = 115200;

3.3 Runtime Undefined Behavior (UB) & Hardware Faults

In C, Undefined Behavior (UB) refers to code executions where the ISO standard imposes no requirements. The compiler optimizer is legally permitted to assume that undefined behavior never occurs, leading to silent instruction elimination, infinite loops, or unpredictable processor traps.

Figure 3.1: Hardware Fault Escalation Hierarchy in ARM Cortex-M Processors
Key ARM Cortex-M Fault Registers:
  • CFSR (Configurable Fault Status Register): Combines MemManage, BusFault, and UsageFault flags. Pinpoints divide-by-zero or unaligned memory traps.
  • HFSR (HardFault Status Register): Indicates if a configurable fault escalated due to lack of handler or priority lockup.
  • BFAR (BusFault Address Register): Holds the exact 32-bit physical address that triggered an AHB/APB bus violation.
Real World Example: In 2010, Toyota experienced unintended acceleration investigations involving electronic throttle control firmware. Embedded safety audits highlighted the catastrophic danger of stack overflow into global memory and unhandled pointer errors. When the call stack collides with global variables in RAM, memory is silently overwritten, corrupting throttle angle setpoints without throwing an explicit compile error.

3.4 Hands-On Code Implementations

The following production C handler intercepts ARM Cortex-M HardFault exceptions, extracts the stacked CPU register frame, and logs the instruction address (Program Counter) that triggered the crash before invoking safe system reset. 

/**
 * Program 3.2: Cortex-M HardFault Diagnostic Frame Extractor
 * File: hardfault_handler.c
 * Target: ARM Cortex-M3 / M4 / M7
 */

#include <stdint.h>
#include <stdio.h>

/* Stacked exception frame layout pushed by ARM hardware onto MSP or PSP */
typedef struct {
    uint32_t r0;
    uint32_t r1;
    uint32_t r2;
    uint32_t r3;
    uint32_t r12;
    uint32_t lr;   /*!< Link Register (Return Address) */
    uint32_t pc;   /*!< Program Counter (Faulting Instruction!) */
    uint32_t psr;  /*!< Program Status Register */
} ExceptionStackFrame_t;

/* System Control Block Configurable Fault Status Register (CFSR) Address */
#define SCB_CFSR  (*(volatile uint32_t *)0xE000ED28UL)
#define SCB_HFSR  (*(volatile uint32_t *)0xE000ED2CUL)
#define SCB_BFAR  (*(volatile uint32_t *)0xE000ED38UL)

/**
 * @brief C-level HardFault decoder invoked from assembly stub.
 * @param[in] stack_frame Pointer to register context captured at time of fault.
 */
void HardFault_Decoder_C(const ExceptionStackFrame_t * const stack_frame) {
    /* Safe capture of fault diagnostic context */
    const uint32_t faulting_pc  = stack_frame->pc;
    const uint32_t faulting_lr  = stack_frame->lr;
    const uint32_t cfsr_val     = SCB_CFSR;
    const uint32_t hfsr_val     = SCB_HFSR;

    /* Print diagnostics to SWD ITM or non-volatile crash log buffer */
    printf("\n!!! HARDWARE HARDFAULT EXCEPTION DETECTED !!!\n");
    printf("Faulting PC  : 0x%08lX\n", (unsigned long)faulting_pc);
    printf("Return LR    : 0x%08lX\n", (unsigned long)faulting_lr);
    printf("SCB->CFSR    : 0x%08lX\n", (unsigned long)cfsr_val);
    printf("SCB->HFSR    : 0x%08lX\n", (unsigned long)hfsr_val);

    if (cfsr_val & (1UL << 25)) {
        printf("Cause: Divide-by-zero UsageFault attempted!\n");
    }
    if (cfsr_val & (1UL << 24)) {
        printf("Cause: Unaligned memory access attempted!\n");
    }
    if (cfsr_val & (1UL << 15)) {
        printf("BusFault Address: 0x%08lX\n", (unsigned long)SCB_BFAR);
    }

    /* In production: flush non-volatile flight log, disable actuators, and reset */
    while (1) {
        /* Hang in debugger or trigger Watchdog reset */
    }
}

3.5 Buggy vs. Modern Safe Code Comparison

A subtle and prevalent logic error occurs when unsigned integer promotion interacts with loop termination conditions, producing an inadvertent infinite loop that never terminates.

View Buggy/Legacy Code

Because i is an unsigned 8-bit integer (uint8_t), the condition i >= 0 is always true! When i reaches 0, the next decrement wraps around to 255: 

/* BUGGY: Infinite loop due to unsigned integer underflow */
void transmit_buffer_reverse(const uint8_t *buf, uint8_t len) {
    uint8_t i;
    /* When i is 0, i-- wraps to 255. The loop condition (i >= 0) is NEVER false! */
    for (i = len - 1; i >= 0; i--) {
        uart_send_byte(buf[i]); /* Out of bounds access when i wraps! */
    }
}
Program 3.3-A: Infinite Loop Caused by Unsigned Type Underflow

Here is the safe modern implementation. By using a pre-decrement loop idiom or standard signed types, the loop terminates reliably at zero without relying on signed underflow: 

/* SAFE / PRODUCTION-GRADE: Pre-decrement loop idiom or size_t */
#include <stdint.h>
#include <stddef.h>

void transmit_buffer_reverse(const uint8_t * const buf, const size_t len) {
    if ((buf == NULL) || (len == 0U)) {
        return;
    }

    size_t i = len;
    while (i > 0U) {
        --i; /* Safely decrements from (len - 1) down to 0 */
        uart_send_byte(buf[i]);
    }
}

Topic Quiz (10 Questions)

Test your ability to diagnose compile, link, runtime, and concurrency bugs.

1. What toolchain stage is responsible for reporting 'multiple definition of symbol' errors?
  • The Preprocessor (cpp)
  • The C Compiler (cc1)
  • The Linker (ld)
  • The Hardware Debugger (gdb)
The compiler checks symbols within a single file; only the linker resolves global symbols across multiple object files, catching duplicates.
2. Why does the compiler flag: 'warning: comparison is always true due to limited range of data type' on 'uint8_t i; if (i >= 0)'?
  • uint8_t cannot be compared to literals.
  • Unsigned integers can never be negative; any value from 0 to 255 is inherently >= 0.
  • The variable is in Flash memory.
  • i must be cast to a float first.
Unsigned types have a minimum value of 0. Checking if an unsigned integer is >= 0 is tautologically true, signaling a loop logic defect.
3. What is an 'undefined reference' linker error typically caused by?
  • A syntax error in a macro.
  • A function or variable is declared in a header, but the object file containing its definition was not provided to the linker.
  • A divide-by-zero in main().
  • A missing semicolon after a struct definition.
An undefined reference occurs when the linker searches all input object files and libraries but finds no address assigned to the requested symbol.
4. Which ARM Cortex-M hardware exception is triggered when code attempts an unaligned memory access with unaligned traps enabled?
  • SysTick Exception
  • UsageFault
  • NMI (Non-Maskable Interrupt)
  • PendSV Exception
UsageFault handles program errors such as executing undefined instructions, unaligned memory accesses, and division by zero.
5. What happens during a stack overflow in a bare-metal microcontroller without an MPU (Memory Protection Unit)?
  • The OS displays a blue screen.
  • The stack pointer grows downward past its allocated boundary, silently overwriting global variables or heap data in SRAM.
  • The CPU immediately halts clock cycles.
  • The linker refuses to flash the board.
Without hardware memory protection (MPU), stack growth beyond bounds silently corrupts neighboring global data (.data/.bss), causing unpredictable erratic behavior.
6. What is the danger of modifying a shared variable inside an Interrupt Service Routine (ISR) without the 'volatile' keyword?
  • The ISR will refuse to fire.
  • The main loop thread may cache the variable in a CPU register and never observe changes made by the ISR.
  • The variable will be stored in ROM.
  • The variable will overflow on every tick.
The compiler optimizes loops by caching variables in registers unless 'volatile' instructs it that external events (like ISRs) can alter memory asynchronously.
7. In C, what is the consequence of reading an uninitialized local variable?
  • The variable is guaranteed to be 0 by the standard.
  • It invokes Undefined Behavior; the variable contains whatever garbage was previously on the stack frame.
  • The compiler automatically triggers a hard fault.
  • The variable is allocated in the .bss section.
Local automatic stack variables are not zero-initialized by the C runtime. Reading them reads leftover stack garbage and constitutes undefined behavior.
8. What is a 'race condition' between a main superloop and a timer ISR?
  • A test to see which thread runs faster.
  • When an interrupt preempts the main loop in the middle of a non-atomic multi-byte read or write, leaving shared data in an inconsistent state.
  • When the CPU clock frequency exceeds the crystal oscillator rating.
  • When the linker script overlaps Flash and RAM.
Updating a 32-bit integer on an 8-bit MCU or updating multi-field structs non-atomically allows an ISR to interleave, reading half-updated corrupted data.
9. Which compiler flag instructs GCC to treat all warnings as fatal compilation errors?
  • -Wall
  • -Wextra
  • -Werror
  • -O3
-Werror turns all compiler warnings into build-halting errors, preventing developers from ignoring diagnostic warnings.
10. In an ARM Cortex-M stacked exception frame, which stacked register holds the exact instruction address where the fault occurred?
  • R0
  • LR (Link Register)
  • PC (Program Counter)
  • SP (Stack Pointer)
The hardware exception mechanism pushes PC (Program Counter) at offset +24 in the exception frame, recording the precise address of the faulting instruction.

Hands-On Assignments

Execute these 5 laboratory assignments to master defect identification and error recovery.

Assignment 1: Intentional Linker Error Reproduction

Task: Create a multi-file project with main.c, math.c, and math.h. Deliberately define a global variable int sensor_data = 10; in math.h without extern. Include math.h in both main.c and math.c. Build with GCC and document the exact linker error. Then fix it using extern.

Assignment 2: The Stack Smashing Canary Lab

Task: Write a function with a local buffer: uint8_t buffer[8];. Write a loop that writes 16 bytes into this buffer. Compile with GCC flag -fstack-protector-all. Run the program and observe the runtime abort triggered by the compiler's canary check mechanism.

Assignment 3: Unaligned Access Fault Trigger and Recovery

Task: Create a byte buffer in RAM. Cast an odd byte address (e.g. &buffer[1]) into a uint32_t * pointer and attempt a 32-bit write. On an ARM Cortex-M with the unaligned trap bit enabled in the CCR (Configuration and Control Register), verify that this generates a UsageFault and decode the stacked PC in GDB.

Assignment 4: Non-Atomic ISR Race Condition Simulation

Task: Write a program where a simulated 64-bit millisecond timestamp variable is incremented in an ISR. In the main loop, continuously read the timestamp and verify that the lower 32 bits never decrement relative to the upper 32 bits. Demonstrate how reading without a critical section produces temporary backward time jumps.

Assignment 5: Memory Section Overflow Detection

Task: Create an embedded project with a linker script allocating 16 KB of SRAM. Declare a static array consuming 18 KB of RAM. Run the linker and examine the error message. Inspect the generated linker map file (-Wl,-Map=output.map) to see how sections are arranged and where the boundary overflow occurred.
