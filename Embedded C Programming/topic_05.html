Topic 5

Unit Testing Concepts

Historically, embedded firmware testing was performed almost exclusively on physical target boards using flash programmers, logic analyzers, and oscilloscopes. While on-target hardware-in-the-loop (HIL) testing remains vital, relying on physical hardware for every minor code iteration creates crippling development bottlenecks: flashing takes seconds, setting up fault injection is difficult, and automated Continuous Integration (CI) test execution becomes complex and expensive.

Modern embedded engineering adopts the Embedded Testing Pyramid: 80% or more of firmware logic (state machines, ring buffers, communication packet parsers, PID algorithms, sensor filters) is compiled and verified natively on the developer's host workstation using native C unit test frameworks like Unity and CMock.

5.1 The Embedded Testing Pyramid

The embedded testing hierarchy balances execution speed, cost, and fidelity across three distinct layers:

Figure 5.1: The Embedded Software Testing Pyramid
Pyramid Tiers Explained:
  • Host Unit Tests (Unity): Compiled with native GCC/Clang on x86_64 or Apple Silicon. Mocks out hardware registers, executing thousands of test cases in milliseconds.
  • Integration Tests: Validates interactions between drivers, queues, and RTOS scheduler tasks in a simulated or target environment.
  • HIL (Hardware-in-the-Loop): The complete compiled firmware runs on physical silicon, validating crystal oscillator tolerances, ADC impedances, and electrical noise resilience.

5.2 The Unity Test Framework for C

Unity is a lightweight, pure-C testing framework specifically architected for embedded systems. It requires minimal RAM, avoids dynamic memory allocation, and produces clear, actionable test runner output.

A standard Unity test file contains three essential components:

  1. void setUp(void): Executed immediately before every single test function to initialize mock state and reset structures.
  2. void tearDown(void): Executed immediately after every test to clean up state and verify mock expectations.
  3. test_...() functions containing assertions like TEST_ASSERT_EQUAL_UINT32(expected, actual).

5.3 Decoupling Hardware Registers via Mocking

Firmware often fails unit testing because functions directly access silicon registers:
GPIOA->ODR |= (1 << 5);. When compiled on a host PC, this attempts to dereference address 0x40020014, immediately triggering a segmentation fault.

The professional architectural solution is Hardware Abstraction Layer (HAL) separation: business logic talks to interface functions, which are linked to hardware on target builds and linked to mock functions on host test builds.

5.4 Hands-On Code Implementations

The following self-contained implementation demonstrates a robust circular ring buffer paired with a full Unity-style test harness: 

/**
 * Program 5.1: Circular Ring Buffer with Unity-Style Unit Test Harness
 * File: test_ring_buffer.c
 * Target: Host Machine Native Execution (gcc -Wall test_ring_buffer.c)
 */

#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

/* ------------------- Production Ring Buffer Module ------------------- */

#define RING_BUF_CAPACITY 8U

typedef struct {
    uint8_t buffer[RING_BUF_CAPACITY];
    size_t  head;
    size_t  tail;
    size_t  count;
} RingBuffer_t;

void ring_buf_init(RingBuffer_t * const rb) {
    if (rb != NULL) {
        rb->head = 0U;
        rb->tail = 0U;
        rb->count = 0U;
    }
}

bool ring_buf_push(RingBuffer_t * const rb, const uint8_t byte) {
    if ((rb == NULL) || (rb->count >= RING_BUF_CAPACITY)) {
        return false; /* Buffer full or null */
    }
    rb->buffer[rb->head] = byte;
    rb->head = (rb->head + 1U) % RING_BUF_CAPACITY;
    rb->count++;
    return true;
}

bool ring_buf_pop(RingBuffer_t * const rb, uint8_t * const byte_out) {
    if ((rb == NULL) || (byte_out == NULL) || (rb->count == 0U)) {
        return false; /* Buffer empty or null */
    }
    *byte_out = rb->buffer[rb->tail];
    rb->tail = (rb->tail + 1U) % RING_BUF_CAPACITY;
    rb->count--;
    return true;
}

/* --------------------- Embedded Test Harness --------------------- */

static uint32_t s_tests_run = 0;
static uint32_t s_tests_passed = 0;
static RingBuffer_t s_test_rb;

#define TEST_ASSERT(cond, msg) \
    do { \
        if (!(cond)) { \
            printf("  [FAIL] Line %d: %s\n", __LINE__, msg); \
            return; \
        } \
    } while (0)

#define RUN_TEST(test_func) \
    do { \
        s_tests_run++; \
        ring_buf_init(&s_test_rb); /* setUp */ \
        printf("Running: %s...", #test_func); \
        test_func(); \
        s_tests_passed++; \
        printf(" PASSED\n"); \
    } while (0)

/* Test Case 1: Initial state after initialization */
void test_ring_buffer_init_is_empty(void) {
    TEST_ASSERT(s_test_rb.count == 0U, "Count should be zero on init");
    uint8_t byte = 0;
    TEST_ASSERT(!ring_buf_pop(&s_test_rb, &byte), "Pop on empty should return false");
}

/* Test Case 2: Push and Pop single byte */
void test_ring_buffer_push_pop_single(void) {
    TEST_ASSERT(ring_buf_push(&s_test_rb, 0x42), "Push should succeed");
    TEST_ASSERT(s_test_rb.count == 1U, "Count should be 1");
    uint8_t popped = 0;
    TEST_ASSERT(ring_buf_pop(&s_test_rb, &popped), "Pop should succeed");
    TEST_ASSERT(popped == 0x42, "Popped value mismatch");
    TEST_ASSERT(s_test_rb.count == 0U, "Buffer should be empty");
}

/* Test Case 3: Capacity overflow rejection */
void test_ring_buffer_overflow_rejected(void) {
    for (uint8_t i = 0; i < RING_BUF_CAPACITY; ++i) {
        TEST_ASSERT(ring_buf_push(&s_test_rb, i), "Push up to capacity must succeed");
    }
    TEST_ASSERT(!ring_buf_push(&s_test_rb, 0xFF), "Pushing past capacity must fail");
    TEST_ASSERT(s_test_rb.count == RING_BUF_CAPACITY, "Count must remain at max capacity");
}

int main(void) {
    printf("=== Starting Ring Buffer Unit Test Suite ===\n");
    RUN_TEST(test_ring_buffer_init_is_empty);
    RUN_TEST(test_ring_buffer_push_pop_single);
    RUN_TEST(test_ring_buffer_overflow_rejected);

    printf("\nTest Summary: %u / %u Passed (100%% Success)\n", s_tests_passed, s_tests_run);
    return (s_tests_passed == s_tests_run) ? 0 : 1;
}

5.5 Buggy vs. Modern Safe Code Comparison

A catastrophic flaw in naive ring buffer implementations is neglecting to validate buffer count before updating indices, causing silent memory overwrite bugs when multiple calls occur.

View Buggy/Legacy Code

This unverified push function has no full-capacity check, overwriting unread data and desynchronizing head and tail indices: 

/* BUGGY: No capacity or pointer check, silent data loss */
void push_byte(uint8_t byte) {
    /* Bug: If buffer is full, head advances past tail and destroys unread data! */
    g_buf[g_head++] = byte;
    if (g_head >= 16) g_head = 0;
}
Program 5.2-A: Unvalidated Buffer Push with Silent Overwrite Hazard

The unit-tested production code rigorously verifies capacity, returns explicit status booleans, and cleanly manages atomic boundaries: 

/* SAFE / TESTED: Strict boundary check, status return */
bool safe_ring_buf_push(RingBuffer_t * const rb, const uint8_t byte) {
    if (rb == NULL) return false;
    if (rb->count >= RING_BUF_CAPACITY) return false; /* Reject overflow */
    
    rb->buffer[rb->head] = byte;
    rb->head = (rb->head + 1U) & (RING_BUF_CAPACITY - 1U);
    rb->count++;
    return true;
}

Topic Quiz (10 Questions)

Test your knowledge of host-based unit testing, mocking, and firmware TDD.

1. What is the primary advantage of executing firmware unit tests natively on a host PC rather than on target hardware?
  • Host PCs don't require C compilers.
  • Instant compilation and test execution speed (milliseconds vs seconds), enabling rapid TDD and automated CI pipelines.
  • Host PCs automatically test crystal oscillator tolerances.
  • Host testing eliminates the need for linker scripts.
Host unit testing executes thousands of tests in fractions of a second without waiting for JTAG flashing cycles, supercharging test iteration.
2. In the Unity test framework, what is the role of the 'setUp()' function?
  • To flash the microcontroller over UART.
  • To execute initialization code before every individual test function, ensuring each test begins in a known clean state.
  • To compile the assembly files.
  • To allocate heap memory for the test suite.
setUp() is invoked by Unity immediately prior to running each test case, resetting data structures to prevent inter-test side effects.
3. What is a 'Mock' in embedded unit testing?
  • A joke left in code comments.
  • A simulated replacement for a hardware driver or dependency that verifies how it was called and returns predetermined test responses.
  • A physical prototype PCB.
  • A hardware debugger probe.
Mocks emulate hardware peripherals (like I2C or Flash chips), allowing application logic to be tested thoroughly without physical hardware.
4. Why does direct register access (e.g. GPIOA->ODR = 0x01) cause a segmentation fault when compiled and run on a host PC?
  • Host PCs do not have a C compiler.
  • The physical memory address (e.g. 0x40020014) is invalid or protected in the host OS virtual memory space.
  • The host CPU cannot execute 32-bit instructions.
  • ODR is an illegal variable name on Linux.
Host operating systems enforce virtual memory page protection; dereferencing arbitrary microcontroller hardware addresses causes an instant SIGSEGV crash.
5. What is the fundamental cycle of Test-Driven Development (TDD)?
  • Code -> Flash -> Debug -> Document
  • Red (Write a failing test) -> Green (Write minimal code to pass) -> Refactor (Clean up architecture)
  • Compile -> Link -> Flash -> Ship
  • Plan -> Build -> Deploy -> Patch
TDD follows the Red-Green-Refactor cadence, verifying requirements with failing tests before writing production implementation code.
6. What code coverage metric requires verifying that every branch decision outcome and every Boolean condition within that decision independently affects the outcome?
  • Statement Coverage
  • Function Coverage
  • MC/DC (Modified Condition / Decision Coverage)
  • Line Coverage
MC/DC is required by DO-178C (avionics) and ISO 26262 ASIL D (automotive) for the highest levels of safety criticality.
7. Which tool in the Unity ecosystem automatically generates mock C functions and header stubs from existing interfaces?
  • Gcov
  • CMock
  • Valgrind
  • GDB
CMock parses C header files and automatically synthesizes mock functions capable of verifying expected parameters and returning canned data.
8. What is a 'Stub' in embedded testing?
  • A damaged PCB trace.
  • A simplified dummy implementation of a dependency that returns hardcoded values to satisfy linker requirements during testing.
  • A broken test assertion.
  • A hardware jumper cable.
Stubs provide simple canned return values so that code under test can link and execute without calling real hardware drivers.
9. Which GCC flag enables source code instrumentation to generate test execution coverage metrics (.gcda / .gcno files)?
  • -O3
  • --coverage (or -fprofile-arcs -ftest-coverage)
  • -Werror
  • -nostdlib
`--coverage` instructs GCC to emit branch and line execution counters, analyzed by gcov or lcov to generate coverage reports.
10. Why is achieving 100% statement coverage insufficient on its own to guarantee bug-free firmware?
  • Statement coverage only applies to C++ code.
  • Statement coverage does not test untested branch paths, missing edge cases (e.g. null inputs or buffer boundaries), or concurrency race conditions.
  • Compilers invert statement coverage calculations.
  • Statement coverage increases binary size.
Executing every line once does not verify what happens when conditions evaluate false, when boundary values are passed, or when timing interrupts interleave.

Hands-On Assignments

Execute these 5 laboratory assignments to build automated unit test suites for firmware components.

Assignment 1: Test-Driven Ring Buffer Development

Task: Clone or implement the Unity test harness. Write unit tests for a circular buffer verifying: (1) empty status on init, (2) push and pop FIFO sequence integrity, (3) wrap-around behavior across array bounds, and (4) rejection of null output pointers. Execute tests natively on your host PC with GCC.

Assignment 2: Hardware Register Mocking

Task: Create an abstract LED driver interface: led_set_state(led_id, state). Write a mock implementation on host PC that logs state changes into an array. Author unit tests verifying that an alert subsystem turns ON the warning LED when temperature exceeds 80 degrees.

Assignment 3: Code Coverage Analysis with Gcov

Task: Compile your unit test suite with gcc --coverage. Execute the test suite and run gcov. Inspect the annotated source file (.gcov) to identify any branches or defensive error checks that were never exercised. Add unit tests to achieve 100% branch coverage.

Assignment 4: State Machine Test Harness

Task: Design a 3-state connection finite-state machine (DISCONNECTED, CONNECTING, CONNECTED). Write unit tests verifying all valid transitions. Then write tests feeding unexpected events (e.g. timeout event while DISCONNECTED) to verify the state machine rejects illegal transitions gracefully.

Assignment 5: Packet Parser Fuzzing Test

Task: Implement a binary packet frame parser that validates a start-of-frame byte (0xAA), length byte, payload, and XOR checksum. Write an automated test feeder that generates 10,000 randomized corrupt byte streams. Verify that the parser never triggers a segmentation fault or buffer overflow.
