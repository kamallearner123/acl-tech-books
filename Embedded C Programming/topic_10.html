Topic 10

Git Workflow for Firmware

Version control for embedded systems presents unique challenges that rarely occur in pure software web or desktop development. A firmware repository must manage not only C source files and unit tests, but also external vendor Hardware Abstraction Layers (ST HAL, NXP MCUXpresso, ESP-IDF), silicon errata patches, hardware board revision branches (e.g. PCB Rev A vs Rev B pin mappings), and binary calibration data.

Adopting a disciplined Git workflow ensures that every single device flashed on a production manufacturing line can be traced to an exact Git commit SHA, that third-party code is cleanly isolated using git submodule or git subtree, and that build artifact pollution is eliminated with robust .gitignore templates.

10.1 Repository Layout & .gitignore Hygiene

A clean firmware repository strictly separates application logic, board support packages, and vendor silicon libraries:

Figure 10.1: Standard Industrial Firmware Repository Architecture

Committed binaries (.o, .elf, .bin) cause repository bloat because Git stores entire binary diffs for every single build. A strict .gitignore is mandatory: 

# Standard Embedded .gitignore
build/
*.o
*.d
*.elf
*.bin
*.hex
*.map
*.gcda
*.gcno

# IDE metadata
.vscode/
.idea/
*.launch
.metadata/

10.2 Managing Third-Party Vendor Code via Git Submodules

Silicon vendors frequently release hundreds of megabytes of HAL and middleware code. Copying this code directly into your repository creates maintenance nightmares. Using Git submodules locks vendor code to a specific external commit hash: 

# Add official FreeRTOS kernel as a submodule
git submodule add https://github.com/FreeRTOS/FreeRTOS-Kernel.git lib/FreeRTOS

# When cloning a repository with submodules:
git clone --recurse-submodules https://github.com/my-org/my-firmware.git

# Updating submodules:
git submodule update --init --recursive

10.3 Automated Build Metadata Injection into C Firmware

In manufacturing, customer field units report firmware versions over serial or CAN bus. Hardcoding version numbers in C source code is prone to human error.

The professional approach uses the build system to query Git directly and inject the exact commit hash, build timestamp, and dirty flag into the C compiler as preprocessor defines: 

# In Makefile:
GIT_VERSION := $(shell git describe --tags --always --dirty)
GIT_COMMIT  := $(shell git rev-parse --short HEAD)

CFLAGS += -DGIT_VERSION=\"$(GIT_VERSION)\" -DGIT_COMMIT=\"$(GIT_COMMIT)\"

10.4 Hands-On Code Implementations

Here is a C version information service that reports the injected Git commit and dirty status over the device's diagnostic serial port: 

/**
 * Program 10.2: Automated Version & Git Traceability Module
 * File: version_info.c
 */

#include <stdio.h>
#include <stdint.h>

#if !defined(GIT_VERSION)
    #define GIT_VERSION "UNKNOWN_DEV"
#endif

#if !defined(GIT_COMMIT)
    #define GIT_COMMIT "0000000"
#endif

typedef struct {
    const char *firmware_version;
    const char *git_commit_sha;
    const char *build_date;
    const char *build_time;
} VersionMetadata_t;

static const VersionMetadata_t s_firmware_version = {
    .firmware_version = GIT_VERSION,
    .git_commit_sha  = GIT_COMMIT,
    .build_date      = __DATE__,
    .build_time      = __TIME__
};

void print_system_boot_banner(void) {
    printf("\n==================================================\n");
    printf("  Industrial Gateway Controller Firmware\n");
    printf("  Version     : %s\n", s_firmware_version.firmware_version);
    printf("  Git Commit  : %s\n", s_firmware_version.git_commit_sha);
    printf("  Build Stamp : %s %s\n", s_firmware_version.build_date, s_firmware_version.build_time);
    printf("==================================================\n\n");
}

10.5 Buggy vs. Modern Safe Code Comparison

Hardcoded version strings frequently diverge from actual Git release tags, making post-mortem crash analysis in the field nearly impossible.

View Buggy/Legacy Code

This snippet hardcodes version strings in C. Developers forget to increment it, so 5 different firmware builds all report "v1.0.0": 

/* BUGGY: Manually hardcoded version; desynchronizes with Git tags */
#define FIRMWARE_VERSION "v1.0.0"

void print_version(void) {
    /* Developers ship 12 bugfixes but forget to edit this string! */
    printf("Version: %s\n", FIRMWARE_VERSION);
}
Program 10.3-A: Hardcoded Untraceable Version String

Automated injection guarantees that every flashed device unambiguously identifies its exact Git commit hash: 

/* SAFE / PRODUCTION-GRADE: Compiler-injected Git commit hash */
#ifndef GIT_COMMIT_HASH
    #error "Build system must pass -DGIT_COMMIT_HASH=\"$(git rev-parse --short HEAD)\""
#endif

void print_version_safe(void) {
    /* Guaranteed traceability: 100% matched to exact Git commit in repository */
    printf("Firmware SHA: %s\n", GIT_COMMIT_HASH);
}

Topic Quiz (10 Questions)

Test your knowledge of version control, submodules, and firmware release workflows.

1. Why should intermediate build artifacts (.o, .elf, .bin, .map) be excluded from Git repositories?
  • Git cannot store binary files.
  • Binary files cause severe repository bloat and merge conflicts because Git must store full object copies for every single build.
  • Compilers refuse to build if .elf files are tracked.
  • The linker script breaks.
Binaries cannot be text-diffed; committing build artifacts balloons repository size and causes endless merge conflicts across team members.
2. What command clones a Git repository along with all of its nested third-party submodules?
  • git clone --all
  • git clone --recurse-submodules
  • git clone --submodules-only
  • git clone -f
--recurse-submodules initializes and fetches all registered submodules in a single command during repository cloning.
3. What is the benefit of injecting 'git describe --tags --always --dirty' into C firmware at compile time?
  • It compresses the binary.
  • It allows field devices to report their exact release tag, commit hash, and whether uncommitted local changes were present during compilation.
  • It disables all breakpoints in GDB.
  • It enables hardware watchdog timers.
The --dirty flag immediately flags whether firmware was compiled from uncommitted modifications, preventing untraceable rogue test builds.
4. What Git feature allows large binary files (like factory test datasets, FPGA bitstreams, and bootloader images) to be versioned without bloating the core repository?
  • Git Submodule
  • Git LFS (Large File Storage)
  • Git Rebase
  • Git Stash
Git LFS replaces large binary assets with text pointer files, storing actual data blobs on an external remote storage server.
5. What file records the URLs and local paths of external Git submodules within a repository?
  • .gitignore
  • .gitmodules
  • .gitconfig
  • Makefile
.gitmodules is a tracked text file in the repository root mapping submodule paths to remote repository URLs.
6. How should hardware PCB revisions (e.g. Rev A using PA5 for an LED vs Rev B using PB3) be managed in firmware architecture?
  • Maintain two completely separate Git repositories.
  • Use a common codebase with Board Support Package (BSP) abstraction layers selected via build flags or runtime GPIO hardware revision strapping pins.
  • Rewrite the application logic from scratch.
  • Manually edit pin numbers before every flash.
Hardware abstraction layers and runtime board revision strapping pins allow a single firmware codebase to support multiple PCB hardware revisions.
7. What is the command to initialize and update submodules in a repository that was cloned without the --recurse-submodules flag?
  • git pull --all
  • git submodule update --init --recursive
  • git checkout submodules
  • git reset --submodule
`git submodule update --init --recursive` registers and fetches all nested submodules listed in .gitmodules.
8. What is a 'semantic versioning' tag format recommended for release firmware?
  • vYYYY-MM-DD
  • vMAJOR.MINOR.PATCH (e.g. v2.1.4)
  • commit_number
  • build_1, build_2
SemVer (Major.Minor.Patch) clearly conveys breaking API changes, backward-compatible feature additions, and bugfixes.
9. What does 'git status' display if a submodule has uncommitted changes inside its directory?
  • It ignores the submodule completely.
  • It reports that the submodule has modified content or a new commits pointer.
  • It deletes the submodule.
  • It triggers a merge conflict.
Git tracks submodules as a specific commit SHA; local modifications within a submodule are flagged in git status as modified content.
10. Why is a Continuous Integration (CI) build server configured to compile firmware on every push to main?
  • To flash every developer's desk board over Wi-Fi.
  • To ensure the codebase always compiles cleanly from scratch, unit tests pass, and binary size limits are enforced on a clean environment.
  • To rewrite Git history.
  • To delete unused branches automatically.
CI verifies that changes compile cleanly in an isolated environment without relying on hidden local machine dependencies or untracked files.

Hands-On Assignments

Execute these 5 laboratory assignments to master professional firmware version control workflows.

Assignment 1: Git-Driven Version Injection in C

Task: Configure your Makefile or CMakeLists.txt to pass -DGIT_COMMIT=\"$(shell git rev-parse --short HEAD)\". Create a C function that prints this string over serial. Make a commit, rebuild, and verify that the printed string automatically reflects the new commit hash.

Assignment 2: Git Submodule Integration

Task: Add the official Unity test framework as a submodule in tests/unity. Link Unity into your host unit test build. Verify that .gitmodules is properly created and committed to your repository.

Assignment 3: Embedded .gitignore Hardening

Task: Build your complete firmware project. Run git status. Ensure that not a single object file (.o), dependency file (.d), map file (.map), or binary image appears in the untracked files list.

Assignment 4: Semantic Tagging and Release Archival

Task: Create an annotated Git tag for a stable milestone: git tag -a v1.0.0 -m "Release v1.0.0 stable production firmware". Write a script that archives the exact source tree and compiled binary into a zip release asset using git archive.

Assignment 5: Dirty Build Warning Trap

Task: Modify your build script to check if uncommitted Git changes exist (git diff --quiet || echo "-DIRTY"). If dirty changes exist when running make release, emit a bright warning to the developer: "WARNING: Building release binary from uncommitted workspace!".
