Topic 6

The Build Pipeline

When an engineer invokes gcc main.c -o firmware.elf, GCC acts as a compiler driver, coordinating four distinct low-level translation tools behind the scenes: the Preprocessor (cpp), the Compiler Proper (cc1), the Assembler (as), and the Linker (ld).

In embedded firmware engineering, understanding the mechanics of each build stage is vital. When a build runs out of Flash memory, throws a symbol collision, or emits an unexpected machine instruction, the engineer must isolate exactly which stage of the pipeline failed and inspect intermediate output artifacts (.i, .s, .o, .map).

6.1 The Four Stages of the C Compilation Pipeline

Every C source file undergoes a sequential transformation pipeline before being flashed into microcontroller Flash memory:

Figure 6.1: The Four-Stage C Build Pipeline Architecture
Pipeline Stages Detailed:
  • 1. Preprocessor (cpp): Resolves directives starting with # (#include, #define, #ifdef). Strips comments. Emits a clean translation unit.
  • 2. Compiler Proper (cc1): Parses C grammar into an Abstract Syntax Tree (AST), performs dead-code elimination and register allocation, and outputs assembly instructions (.s).
  • 3. Assembler (as): Translates human-readable mnemonic assembly into binary machine code, generating symbol tables and relocations in an object file (.o).
  • 4. Linker (ld): Glues multiple .o files together, resolves cross-module function calls, and maps sections into physical Flash and RAM based on the Linker Script.

6.2 Stage 1: The Preprocessor in Detail

The preprocessor operates purely as a text-substitution engine before syntactic analysis occurs. Directives include:

  • #include <header.h>: Literally replaces the line with the complete text of the included file.
  • #define NAME VALUE: Replaces every token matching NAME with VALUE throughout the translation unit.
  • #ifdef / #ifndef / #endif: Conditionally includes or excludes blocks of code based on preprocessor flags (e.g. #ifdef DEBUG).

Inspect preprocessor output directly using the -E GCC flag:
arm-none-eabi-gcc -E -dD main.c -o main.i

6.3 Stage 2 & 3: Compilation & Assembly

During compilation, GCC translates the preprocessed C code into assembly. You can inspect the emitted assembly code by stopping compilation with the -S flag:
arm-none-eabi-gcc -S -O2 -mcpu=cortex-m4 main.c -o main.s

The assembler then turns main.s into an object file containing machine code instructions:
arm-none-eabi-as -mcpu=cortex-m4 main.s -o main.o
At this stage, memory addresses for external functions (like printf or SystemInit) are left as zero or placeholder offsets in a relocation table.

6.4 Stage 4: Linking and Linker Scripts

The Linker resolves all external symbols and places code and variables into physical memory as dictated by a Linker Script (.ld). The linker script defines memory regions and places sections: 

/* Minimal Linker Script Architecture */
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 128K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 32K
}

SECTIONS
{
    .text : {
        *(.isr_vector)  /* Startup Vector Table at 0x08000000 */
        *(.text*)       /* Program machine code */
        *(.rodata*)     /* Constants and strings */
    } > FLASH

    .data : {
        _sdata = .;     /* Start of initialized data in RAM */
        *(.data*)
        _edata = .;     /* End of initialized data */
    } > RAM AT > FLASH  /* Loaded in Flash, copied to RAM at boot */

    .bss : {
        _sbss = .;      /* Zero-initialized RAM variables */
        *(.bss*)
        _ebss = .;
    } > RAM
}

6.5 Hands-On Code Implementations

Here is a complete C program demonstrating how preprocessor symbols and memory section attributes (__attribute__((section(...)))) interact with the linker: 

/**
 * Program 6.2: Build Pipeline Section Placement & Startup Initialization
 * File: pipeline_demo.c
 */

#include <stdint.h>

/* 1. Placed in .rodata (Flash memory) */
const uint32_t FIRMWARE_VERSION = 0x00010203UL;

/* 2. Placed in .data (Flash initial values copied to SRAM by Reset_Handler) */
uint32_t g_heartbeat_counter = 100UL;

/* 3. Placed in .bss (Zero-initialized in SRAM by Reset_Handler) */
uint8_t g_rx_buffer[64];

/* 4. Placed in custom section .fastcode (Copied from Flash to RAM for 0-wait-state speed) */
__attribute__((section(".fastcode")))
void critical_motor_commutate(void) {
    /* High-speed motor commutation algorithm executing directly from SRAM */
    g_heartbeat_counter++;
}

int main(void) {
    critical_motor_commutate();
    return (int)g_heartbeat_counter;
}

6.6 Buggy vs. Modern Safe Code Comparison

A classic preprocessor hazard is creating multi-statement macros without the standard do { ... } while(0) idiom, leading to silent syntax truncation when used inside if/else statements.

View Buggy/Legacy Code

This multi-statement macro breaks if/else blocks because the semicolon after the macro call causes the compiler to treat the else as an orphan: 

/* BUGGY MACRO: Fails in if/else blocks */
#define SET_PINS_HIGH() \
    PORTA |= 0x01; \
    PORTB |= 0x02

/* Usage: */
if (condition)
    SET_PINS_HIGH(); /* Semicolon terminates if statement! */
else                 /* COMPILE ERROR: 'else' without a previous 'if' */
    PORTA &= ~0x01;
Program 6.3-A: Broken Multi-Statement Macro

The correct pattern wraps multi-statement macros in do { ... } while (0), or better, uses a static inline C function: 

/* SAFE / PRODUCTION-GRADE: do-while(0) wrapper or static inline */
#define SET_PINS_HIGH() \
    do { \
        PORTA |= 0x01U; \
        PORTB |= 0x02U; \
    } while (0)

/* Even better: C99 static inline function */
static inline void set_pins_high(void) {
    PORTA |= 0x01U;
    PORTB |= 0x02U;
}

Topic Quiz (10 Questions)

Test your understanding of preprocessor behavior, compilation stages, assembly, and linking.

1. Which stage of the GCC build pipeline translates preprocessed C code (.i) into assembly language (.s)?
  • The Preprocessor (cpp)
  • The Compiler Proper (cc1)
  • The Assembler (as)
  • The Linker (ld)
cc1 is the actual compiler component in the GCC toolchain that converts C code into target assembly instructions.
2. Which GCC flag stops compilation after the preprocessing stage, outputting the expanded source code?
  • -S
  • -c
  • -E
  • -O2
-E halts the toolchain after the preprocessor runs, displaying all expanded macros and included header contents.
3. What is the fundamental difference between an object file (.o) and an executable ELF binary (.elf)?
  • An object file contains ASCII text; an ELF file contains binary.
  • An object file contains relocatable code with unresolved external addresses; an ELF binary has all addresses resolved and mapped to physical memory.
  • Object files are generated by Make; ELF files are generated by CMake.
  • ELF files only run on Intel x86.
Object files are relocatable chunks of machine code; the linker maps them to absolute physical addresses in Flash and RAM to produce the final executable.
4. Where are initialized global variables (e.g. int counter = 42;) stored at runtime and at power-off?
  • In Flash at runtime; in SRAM at power-off.
  • Stored in Flash at power-off (load address), and copied to SRAM (.data section) by the startup code at boot (runtime address).
  • Stored entirely on the CPU stack.
  • In the .bss section.
Initialized data must persist across power-cycles in Flash, but must be mutable at runtime, so startup code copies initial values into SRAM.
5. What does the .bss memory section contain in an embedded C program?
  • Executable machine instructions.
  • Constant strings and calibration tables.
  • Uninitialized or zero-initialized global and static variables that are cleared to 0 by the startup Reset_Handler.
  • Interrupt vector tables.
.bss holds zero-initialized global/static variables. Because they are 0, they consume zero Flash space; the startup code zeroes their RAM footprint.
6. Which command-line flag stops GCC after assembly, generating an object file (.o) without invoking the linker?
  • -S
  • -c
  • -E
  • -o
-c compiles and assembles the source file into an object file (.o) but skips linking.
7. Why do C developers use the 'do { ... } while (0)' construct inside multi-statement macros?
  • To force the loop to repeat twice.
  • To ensure the macro behaves as a single compound statement that integrates safely into if/else structures with trailing semicolons.
  • To allocate variables on the heap.
  • To enable compiler optimization flags.
do { ... } while(0) syntactically encapsulates multiple lines into a single statement that safely takes a trailing semicolon in if/else clauses.
8. What is a Linker Map file (-Wl,-Map=output.map)?
  • A geographic map of the silicon manufacturing foundry.
  • A comprehensive text document generated by the linker detailing the exact physical memory address, size, and source file of every symbol and section.
  • A bitmap image of the microcontroller.
  • A schematic of the PCB traces.
The map file is an indispensable diagnostic document showing precisely where every function, variable, and section is placed in memory.
9. What GCC attribute instructs the compiler to place a specific function or variable into a custom linker section (e.g. .fastcode)?
  • __attribute__((aligned(4)))
  • __attribute__((naked))
  • __attribute__((section(".section_name")))
  • __attribute__((pure))
__attribute__((section(...))) allows developers to override default section placement, routing time-critical code into SRAM or DMA buffers into specific RAM banks.
10. Why is the startup code's Reset_Handler responsible for copying the .data section from Flash to RAM before calling main()?
  • Flash memory cannot be read by the CPU.
  • SRAM loses its contents on power-down, so initialized global variables must be re-populated from non-volatile Flash on every boot.
  • The linker forbids running code in Flash.
  • It compresses the binary image.
Volatile SRAM powers up with random garbage; the Reset_Handler must copy initial variable values from non-volatile Flash into SRAM before main() begins.

Hands-On Assignments

Execute these 5 laboratory assignments to inspect every transformation stage of the build pipeline.

Assignment 1: Step-by-Step Manual Compilation

Task: Take a C source file containing includes and macros. Compile it manually in 4 separate commands: (1) gcc -E main.c -o main.i, (2) gcc -S main.i -o main.s, (3) as main.s -o main.o, and (4) gcc main.o -o main. Inspect the contents of main.i and main.s with a text editor.

Assignment 2: Dissecting the Linker Map File

Task: Compile an embedded project with flag -Wl,-Map=firmware.map. Open firmware.map and locate: (1) the address of your main() function, (2) the exact Flash addresses allocated to .rodata strings, and (3) the amount of unused padding bytes inserted between structures.

Assignment 3: Custom RAM Section Execution (.fastcode)

Task: Modify a linker script to define a .fastcode section that loads from Flash into RAM. Tag a compute-heavy math function with __attribute__((section(".fastcode"))). Write the startup copy loop in C to populate this RAM region and verify via disassembly that calls jump to the RAM address.

Assignment 4: Macro Stringification and Token Pasting

Task: Write preprocessor macros utilizing stringification (#) and token pasting (##) operators to automatically generate pin configuration functions (e.g. DEFINE_PIN(LED, A, 5) expanding to GPIOA_PIN_5). Generate preprocessed output (-E) to verify correct token expansion.

Assignment 5: Linker Garbage Collection Optimization

Task: Add unused functions to a C file. Compile first without special flags and note the binary size. Then recompile with -ffunction-sections -fdata-sections and link with -Wl,--gc-sections. Run size to quantify how many bytes of unused dead code the linker stripped.
