Topic 22

Interfaces, APIs & Abstraction

A major cause of software fragility in embedded projects is premature coupling to physical silicon. When application algorithms (such as temperature PID control or telemetry logging) directly access microcontroller peripheral registers (e.g., I2C1->DR or USART2->CR1), the entire codebase becomes permanently locked to a single chip vendor. Migrating to another MCU during a silicon supply-chain shortage requires a total rewrite, and automated host-based unit testing on developer laptops becomes impossible.

Hardware Abstraction is the discipline of creating strict procedural interfaces that separate what an application requires from how the physical hardware achieves it. In this chapter, we master modern C abstraction patterns: Opaque Struct Handles (PIMPL in C), Virtual Method Tables (vtables) for runtime polymorphism, and the Dependency Inversion Principle (DIP).

22.1 The Opaque Pointer Pattern (Handles in C)

In standard C, exposing a struct definition in a public header file allows client code to directly read and write internal struct fields. If the driver developer later modifies an internal buffer size or changes a register representation, the client code breaks, or worse, silently introduces memory alignment bugs.

The Opaque Pointer Pattern (analogous to the PIMPL idiom in C++) completely conceals the struct internals behind an incomplete type declaration:

Figure 22.1: Opaque Pointer Encapsulation Boundary
/* display.h: Public Interface */
#ifndef DISPLAY_H
#define DISPLAY_H

#include <stdint.h>
#include <stdbool.h>

/* Incomplete struct forward declaration */
struct DisplayInstance_t;
typedef struct DisplayInstance_t * DisplayHandle_t;

typedef enum {
    DISPLAY_OK = 0,
    DISPLAY_ERR_NULL_PTR,
    DISPLAY_ERR_TIMEOUT
} DisplayStatus_t;

DisplayStatus_t display_pixel_draw(DisplayHandle_t h_disp, uint16_t x, uint16_t y, uint16_t color);
DisplayStatus_t display_flush(DisplayHandle_t h_disp);

#endif /* DISPLAY_H */

22.2 Polymorphism in C: The Virtual Table (vtable) Pattern

Polymorphism allows application code to interact with different hardware implementations through a uniform, interchangeable interface. Consider an application that logs telemetry data to non-volatile memory: depending on product configuration, the physical media could be an internal EEPROM, an external SPI NOR Flash, or a RAM Mock for unit tests.

In C, runtime polymorphism is constructed using a Virtual Method Table (vtable) struct of function pointers: 

/* storage_interface.h */
#ifndef STORAGE_INTERFACE_H
#define STORAGE_INTERFACE_H

#include <stdint.h>
#include <stddef.h>

/* Abstract Storage Interface Vtable */
typedef struct {
    int32_t (*read)(void *p_context, uint32_t addr, uint8_t *p_buf, size_t len);
    int32_t (*write)(void *p_context, uint32_t addr, const uint8_t *p_buf, size_t len);
    int32_t (*erase_sector)(void *p_context, uint32_t sector_addr);
} StorageInterface_t;

/* Generic Polymorphic Storage Device Object */
typedef struct {
    const StorageInterface_t *p_vtable;
    void                     *p_driver_context;
} StorageDevice_t;

/* Polymorphic Dispatch Wrapper */
static inline int32_t storage_read(const StorageDevice_t * const p_dev, 
                                   uint32_t addr, uint8_t *p_buf, size_t len) 
{
    if ((p_dev == NULL) || (p_dev->p_vtable == NULL) || (p_dev->p_vtable->read == NULL)) {
        return -1;
    }
    return p_dev->p_vtable->read(p_dev->p_driver_context, addr, p_buf, len);
}

#endif /* STORAGE_INTERFACE_H */

22.3 Concrete Implementation & Host Mocking

We can now implement concrete drivers that satisfy the StorageInterface_t contract without modifying the caller: 

/* mock_storage.c: In-Memory RAM Mock for PC-Based Automated Testing */
#include "storage_interface.h"
#include <string.h>

#define MOCK_STORAGE_SIZE (4096U)
static uint8_t s_mock_ram[MOCK_STORAGE_SIZE];

static int32_t mock_read(void *p_ctx, uint32_t addr, uint8_t *p_buf, size_t len) {
    (void)p_ctx;
    if ((addr + len) > MOCK_STORAGE_SIZE) return -1;
    (void)memcpy(p_buf, &s_mock_ram[addr], len);
    return (int32_t)len;
}

static int32_t mock_write(void *p_ctx, uint32_t addr, const uint8_t *p_buf, size_t len) {
    (void)p_ctx;
    if ((addr + len) > MOCK_STORAGE_SIZE) return -1;
    (void)memcpy(&s_mock_ram[addr], p_buf, len);
    return (int32_t)len;
}

static int32_t mock_erase(void *p_ctx, uint32_t addr) {
    (void)p_ctx;
    if (addr >= MOCK_STORAGE_SIZE) return -1;
    (void)memset(&s_mock_ram[addr], 0xFF, 256U);
    return 0;
}

/* Static Vtable: Stored in .rodata */
static const StorageInterface_t s_mock_vtable = {
    .read = mock_read,
    .write = mock_write,
    .erase_sector = mock_erase
};

StorageDevice_t mock_storage_create(void) {
    StorageDevice_t dev = {
        .p_vtable = &s_mock_vtable,
        .p_driver_context = NULL
    };
    return dev;
}

22.4 Code Comparison: Hardcoded Silicon vs. Inverted Abstraction

Compare an application tightly bound to an STM32 I2C peripheral with an application decoupled via abstract interfaces.

Compare Architecture: Temperature Acquisition Service

❌ Silicon-Coupled Anti-Pattern

/* Directly accesses STM32 registers */
#include "stm32f4xx.h"

int32_t get_temperature(void) {
    I2C1->CR1 |= I2C_CR1_START;
    while (!(I2C1->SR1 & I2C_SR1_SB));
    I2C1->DR = 0x90;
    /* ... 50 lines of register access */
    return temp_mdegc;
}

Disasters: Cannot run in PC unit tests. Cannot change from I2C to SPI. Cannot port to NXP or ESP32 without rewriting business logic.

✔ Clean Abstract Dependency

/* Depends solely on abstract interface */
typedef struct {
    int32_t (*sample_read_mdegc)(void *ctx, int32_t *p_temp);
} TempSensorIf_t;

int32_t thermal_monitor_step(
    const TempSensorIf_t *p_sensor, 
    void *ctx) 
{
    int32_t temp = 0;
    if (p_sensor->sample_read_mdegc(ctx, &temp) == 0) {
        if (temp > 85000) fan_relay_on();
    }
    return temp;
}

Superiority: Unit-testable on PC with simulated temperatures. Zero silicon dependencies in application logic.

22.5 Interactive Knowledge Check

Test your knowledge of abstraction, opaque pointers, vtables, and hardware isolation.

1. What is the primary purpose of using an "Opaque Pointer" (incomplete struct handle) in a public header file?
  • To enable 64-bit memory addressing on 32-bit MCUs.
  • To enforce information hiding, preventing callers from accessing or corrupting internal struct fields and preserving binary compatibility.
  • To instruct the compiler to place the struct in Flash memory.
  • To eliminate the need for the C linker.
Explanation: Declaring struct Foo; in a header gives callers a typed pointer handle without revealing field layouts, strictly preventing direct member manipulation.
2. How is runtime polymorphism achieved in procedural C without C++ virtual classes?
  • Through preprocessor macro recursion.
  • By defining an interface structure containing function pointers (a vtable) and passing a generic context pointer.
  • By writing assembly language trampolines in RAM.
  • Polymorphism is mathematically impossible in C.
Explanation: A struct containing function pointers acts as a virtual method table (vtable), allowing different driver implementations to be invoked identically through the same interface.
3. What is the performance overhead of invoking a driver function through a function pointer vtable on ARM Cortex-M?
  • Over 10,000 clock cycles.
  • Extremely small: typically 1 to 3 clock cycles (one memory load and a branch with link exchange: LDR + BLX).
  • Zero clock cycles because the compiler always removes function pointers.
  • It causes a guaranteed pipeline flush lasting 10 milliseconds.
Explanation: Calling through a function pointer on Cortex-M requires loading the address into a register and executing BLX — virtually negligible overhead for peripheral I/O.
4. What is the Dependency Inversion Principle (DIP) in the context of embedded firmware?
  • Drivers must depend directly on application UI widgets.
  • High-level policy modules should not depend on low-level silicon drivers; both must depend on abstract interfaces.
  • All interrupts must be inverted to active-low polarity.
  • The SysTick timer must count downwards instead of upwards.
Explanation: DIP ensures that business logic depends on an abstract sensor or communication contract, allowing the physical implementation to be swapped without changing application logic.
5. Why should global errno variables be avoided in multi-rate embedded API design?
  • Because errno is copyrighted by Microsoft.
  • A global error variable is not reentrant; an interrupt occurring between the failing call and checking errno can overwrite the error state.
  • Because it occupies 16 KB of Flash memory.
  • It disables all watchdog timers.
Explanation: Global error state creates race conditions across ISRs and cooperative tasks. Explicit status return enumerations are thread-safe and reentrant.
6. What is the purpose of the void *p_context pointer passed to vtable action functions?
  • To store the return address of the main function.
  • To carry instance-specific private state (e.g. peripheral base address, channel ID, buffer pointers) to the implementation.
  • To enable floating point math in the driver.
  • It is required by the ARM NVIC hardware.
Explanation: The context pointer functions as the procedural equivalent of the this pointer in object-oriented programming, linking the abstract call to instance data.
7. Why is host-based unit testing on a PC vastly easier when using hardware abstraction interfaces?
  • Because PCs have built-in I2C oscilloscope cards.
  • Because physical peripheral drivers can be replaced with mock RAM implementations, allowing algorithms to be tested rapidly in simulated scenarios without physical target hardware.
  • Because GCC on Linux does not support C syntax errors.
  • Because PC testing eliminates all compiler warnings automatically.
Explanation: Abstract interfaces allow injecting mocks that simulate sensor failures, temperature spikes, or corrupt packets on a PC in milliseconds without hardware emulators.
8. What is the risk of "leaky abstractions" in embedded systems?
  • Coolant fluid leaking from electrolytic capacitors.
  • When an interface fails to hide underlying hardware quirks (e.g. page boundaries, flash erase delays, or bus wait states), forcing callers to write hardware-specific workaround code.
  • Memory leaks in the heap.
  • DMA buffers overflowing into the stack.
Explanation: A leaky abstraction exposes implementation details (like requiring callers to pause for 5 ms after an EEPROM write), defeating the purpose of hardware independence.
9. In MISRA-C:2012, what rule governs function pointer casting?
  • Function pointers may be freely cast to void *.
  • A function pointer shall not be converted to any type other than an integral type or a pointer to a function of compatible signature (Rule 11.1).
  • Function pointers are completely forbidden.
  • Function pointers must always point to address 0.
Explanation: MISRA-C Rule 11.1 prohibits casting function pointers to object pointers (like void*) or incompatible signatures, preventing undefined branching behavior.
10. When should an architect prefer static compile-time interface binding (via linking or header aliasing) over runtime vtables?
  • When the system has more than 16 MB of Flash.
  • When the product hardware is fixed at build time and zero indirect call overhead or maximum compiler inlining is required for high-frequency control loops.
  • When using C++ instead of C.
  • Static binding is never used in embedded systems.
Explanation: If a board will only ever have one specific ADC chip, binding the interface at compile-time allows the compiler to inline driver calls with zero indirect branch overhead.

22.6 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to master opaque handles, vtables, and hardware decoupling in embedded C.

Assignment 1: Opaque Handle Refactoring

Task: Take a UART driver where struct Uart_t is currently exposed in uart.h. Refactor the header to declare an opaque handle typedef struct UartInstance_t* UartHandle_t;. Move the struct definition into uart.c. Verify that attempting to access struct fields in main.c produces a compile-time "dereferencing pointer to incomplete type" error.

Assignment 2: Polymorphic Digital Temperature Sensor API

Task: Create an abstract TemperatureSensor_t interface with a vtable: init(), read_mdegc(). Implement two concrete drivers: (1) An I2C sensor driver (e.g. LM75) and (2) An SPI sensor driver (e.g. MAX31855). Write application code that logs temperature from either sensor interchangeably.

Assignment 3: Host PC Mock Storage Unit Test

Task: Implement the StorageInterface_t and mock_storage_create() from Program 22.2 and 22.3. Write a host-based Unity test suite that writes a telemetry packet, re-reads it, verifies CRC checksums, and tests boundary errors without any physical target microcontroller.

Assignment 4: Function Pointer Call Overhead Measurement

Task: Write a benchmark comparing direct function calls versus indirect vtable calls. Use the ARM Cortex-M DWT->CYCCNT cycle counter to measure the exact execution duration of 1,000,000 iterations of both approaches. Calculate the precise CPU cycle overhead per indirect call.

Assignment 5: Dependency Inversion Architecture Audit

Task: Inspect an existing firmware repository. Draw the module dependency graph. Identify any instances where high-level application modules directly include vendor register headers (e.g. #include <stm32f4xx.h>). Refactor the dependency using an abstract Hardware Abstraction Layer (HAL) interface.
