Topic 7

GCC & Cross-Compilers

In desktop application development, developers frequently rely on default compiler settings. In embedded systems, every compiler flag directly influences hardware register operations, Flash consumption, SRAM layout, execution speed, and Floating-Point Unit (FPU) machine instruction generation.

A professional embedded engineer must master cross-compiler target triplets (e.g. arm-none-eabi), understand the critical trade-offs between optimization levels (-O0 through -Os), enforce zero-tolerance warning policies (-Wall -Wextra -Werror -Wpedantic), and configure hardware floating-point ABIs to avoid catastrophic software emulation bloat.

7.1 Anatomy of a Target Triplet

Cross-compiler binaries are named according to a canonical target triplet format:
[arch]-[vendor]-[os]-[abi]

Triplet Component Example Value Technical Meaning in Embedded Firmware
Architecture arm / riscv32 Target CPU instruction set (ARM Cortex-M, RISC-V RV32IMC, Xtensa).
Vendor / OS none Indicates bare-metal execution with no underlying Linux, Windows, or POSIX OS kernel.
Application Binary Interface eabi / eabihf Embedded ABI. hf (hard-float) passes floating-point arguments directly in hardware FPU registers (s0-s15).

7.2 Optimization Levels Demystified (-O0 to -Os)

GCC provides several optimization tiers that fundamentally alter emitted machine code:

  • -O0 (No Optimization): Emits literal 1:1 translations of C code. All variables live on the stack. Crucial for step-by-step debugger stepping, but produces bloated binaries and slow execution.
  • -O2 (Balanced Speed): Aggressive inlining, loop unrolling, and register allocation. Standard for high-speed signal processing.
  • -O3 (Aggressive Speed): Highest performance; may increase binary size via excessive loop unrolling and function duplication.
  • -Os (Optimize for Size): The industry standard for embedded production. Enables all -O2 optimizations that do not increase code size. Strives to minimize Flash footprint.
  • -Og (Optimize for Debugging): Enables reasonable optimizations while preserving stack variables and line mappings for smooth GDB debugging.

7.3 Hardware Floating-Point Flags (-mfloat-abi)

On ARM Cortex-M4F, M7, and RISC-V with FPU, misunderstanding floating-point flags can cause software math libraries to be silently linked, increasing Flash consumption by 20 KB:

  • -mfloat-abi=soft: Emulates all float operations in software using integer instructions. Slowest performance.
  • -mfloat-abi=softfp: Uses hardware FPU instructions, but passes arguments via integer core registers (R0-R3), incurring packing/unpacking overhead.
  • -mfloat-abi=hard: Full hardware acceleration. Floating-point numbers are passed directly inside FPU hardware registers (S0-S15).
Critical GCC Flag: In C, floating-point literals without an f suffix (e.g. float y = x * 1.5;) are treated as 64-bit double precision by the standard! If the MCU only has a 32-bit single-precision FPU, GCC will link heavy software 64-bit emulation libraries. Always pass -fsingle-precision-constant to force literals to 32-bit single precision.

7.4 Hands-On Code Implementations

The following complete C module illustrates how to write code that verifies active compiler flags, architecture defines, and FPU capabilities at compile time: 

/**
 * Program 7.1: Cross-Compiler Feature & FPU Hardware Verification
 * File: compiler_diag.c
 * Target: ARM Cortex-M4F / ARM GCC
 */

#include <stdio.h>
#include <stdint.h>

/* Verify ARM architecture target */
#if !defined(__arm__)
    #warning "Compiling for non-ARM target architecture!"
#endif

/* Check for hardware FPU single-precision support */
#if defined(__ARM_FP) && (__ARM_FP & 0x04)
    #define HAS_HARDWARE_FPU 1
#else
    #define HAS_HARDWARE_FPU 0
#endif

/* Check active optimization level */
#if defined(__OPTIMIZE_SIZE__)
    const char *BUILD_OPT_LEVEL = "Optimized for Size (-Os)";
#elif defined(__OPTIMIZE__)
    const char *BUILD_OPT_LEVEL = "Optimized for Speed (-O2 / -O3)";
#else
    const char *BUILD_OPT_LEVEL = "No Optimization (-O0 / Debug)";
#endif

void print_compiler_diagnostics(void) {
    printf("=== Cross-Compiler Build Configuration ===\n");
    printf("Compiler: GCC %d.%d.%d\n", __GNUC__, __GNUC_MINOR__, __GNUC_PATCHLEVEL__);
    printf("Optimization: %s\n", BUILD_OPT_LEVEL);
    printf("Hardware FPU: %s\n", HAS_HARDWARE_FPU ? "Enabled (Hard-Float)" : "Disabled (Software Emulated)");

#if defined(__ARM_ARCH_7EM__)
    printf("Target Core: ARMv7E-M (Cortex-M4/M7)\n");
#elif defined(__ARM_ARCH_6M__)
    printf("Target Core: ARMv6-M (Cortex-M0/M0+)\n");
#endif
}

7.5 Buggy vs. Modern Safe Code Comparison

Writing floating-point code without recognizing implicit promotion to double results in massive Flash consumption and instruction stalls.

View Buggy/Legacy Code

Notice the literal 0.05 lacks an f suffix. The compiler promotes raw_adc to 64-bit double, executes software double multiplication, and converts back to float: 

/* BUGGY: Unintended 64-bit double promotion on Cortex-M4 single-precision FPU */
float convert_adc_volts(float raw_adc) {
    /* 0.05 is double precision! Pulls in software double-precision runtime library */
    return raw_adc * 0.05 + 1.2; 
}
Program 7.2-A: Unintended Double Precision Promotion

Adding explicit f suffixes or compiling with -fsingle-precision-constant generates single-cycle hardware VMUL.F32 and VADD.F32 instructions: 

/* SAFE / FAST: Explicit single-precision float literals */
float convert_adc_volts_fast(const float raw_adc) {
    /* Pure single-precision float arithmetic executed directly in hardware FPU */
    return (raw_adc * 0.05f) + 1.2f;
}

Topic Quiz (10 Questions)

Test your understanding of cross-compiler toolchains, flags, and architecture targets.

1. In the target triplet 'arm-none-eabi-gcc', what does 'none' represent?
  • No C compiler is used.
  • The target is bare-metal with no operating system kernel.
  • No optimizations are enabled.
  • Zero warnings are reported.
The 'none' field designates the target operating system vendor; 'none' signifies bare-metal execution without Linux or POSIX.
2. Which GCC optimization level is considered standard for production embedded firmware to minimize Flash footprint?
  • -O0
  • -O3
  • -Os
  • -Ofast
-Os applies all size-reducing optimizations from -O2 while avoiding optimizations like aggressive loop unrolling that bloat Flash memory.
3. What is the difference between '-mfloat-abi=softfp' and '-mfloat-abi=hard'?
  • softfp operates without clock signals.
  • softfp emits FPU hardware instructions but passes parameters via integer registers; hard passes parameters directly in FPU registers (s0-s15).
  • hard float requires an external math coprocessor chip.
  • softfp is only supported on 64-bit CPUs.
-mfloat-abi=hard achieves the highest efficiency by passing arguments directly in hardware floating-point registers without conversion.
4. Why should embedded developers use the '--specs=nano.specs' linker flag?
  • It enables Bluetooth.
  • It links against Newlib-Nano, a stripped-down C standard library that significantly reduces Flash and RAM consumption.
  • It disables interrupts.
  • It prevents the board from overheating.
Newlib-Nano replaces standard Newlib with lightweight formatted I/O and memory functions, typically saving 20 KB to 40 KB of Flash space.
5. Which GCC warning flag alerts developers when an implicit conversion may alter an integer value (e.g. assigning uint32_t to uint8_t)?
  • -Wall
  • -Wextra
  • -Wconversion
  • -Wpedantic
-Wconversion is not enabled by default in -Wall; it must be specified explicitly to catch implicit truncation and sign changes.
6. What happens if you compile a Cortex-M3 target with '-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard'?
  • The program runs 2x faster.
  • Execution triggers an Undefined Instruction UsageFault because Cortex-M3 lacks physical hardware FPU instructions.
  • The compiler automatically simulates the FPU.
  • The board fails to power up.
Cortex-M3 hardware lacks an FPU. Emitting hardware VFP instructions will cause the Cortex-M3 core to throw a hardware UsageFault exception.
7. What is the effect of the GCC flag '-fsingle-precision-constant'?
  • It disables all floating-point math.
  • It treats floating-point literals without an 'f' suffix (e.g. 1.23) as single-precision float rather than double precision.
  • It rounds all numbers to the nearest integer.
  • It enables double-precision hardware emulation.
It prevents implicit promotion of float constants to 64-bit double, keeping calculations inside the 32-bit hardware FPU.
8. Which GCC flag warns when a local variable shadows a global variable or another variable in an outer scope?
  • -Werror
  • -Wshadow
  • -Winline
  • -Wformat
-Wshadow warns when a local variable hides an identically-named outer variable, preventing accidental assignments to the wrong variable.
9. What instruction set flag is mandatory for ARM Cortex-M processors, which do not support the legacy 32-bit ARM instruction set?
  • -marm
  • -mthumb
  • -mriscv
  • -mx86
Cortex-M microcontrollers exclusively execute Thumb and Thumb-2 instructions; compiling with -marm will fail or trigger immediate fault exceptions.
10. What does the '-nostdlib' flag instruct the linker to do?
  • It disables all C libraries and startup files, requiring the developer to provide raw startup and runtime primitives.
  • Do not use standard system startup files or libraries when linking.
  • It forces the linker to use Linux libraries.
  • It compresses the binary by 50%.
-nostdlib prevents linking of standard C runtime libraries and default CRT startup files, commonly used in custom bootloaders.

Hands-On Assignments

Execute these 5 laboratory assignments to master compiler tuning and toolchain diagnostics.

Assignment 1: Optimization Benchmark Matrix

Task: Take a mathematical sensor filtering algorithm. Compile it using 4 optimization flags: -O0, -O1, -O2, and -Os. For each build, measure: (1) Flash consumption (.text size via size) and (2) execution cycle count via DWT timer. Create a comparative matrix.

Assignment 2: FPU Disassembly Inspection

Task: Write a float multiplication loop. Compile with -mfloat-abi=soft, then recompile with -mfloat-abi=hard -mfpu=fpv4-sp-d16. Run objdump -d on both binaries. Identify the software helper function call (__aeabi_fmul) in the soft build versus the native hardware instruction (vmul.f32) in the hard build.

Assignment 3: Newlib vs. Newlib-Nano Footprint Comparison

Task: Create a program that calls sprintf() with floating-point formatting. Link first using standard Newlib, and then re-link with --specs=nano.specs -u _printf_float. Compare the Flash memory size delta and document the savings.

Assignment 4: Zero-Tolerance Strict Warning Enforcement

Task: Configure your build flags to include: -Wall -Wextra -Werror -Wpedantic -Wconversion -Wshadow -Wdouble-promotion. Write small test cases that violate each warning and observe the compiler error. Refactor the code until it builds with zero warnings.

Assignment 5: Dead Code Stripping via Garbage Collection

Task: Write 10 uncalled helper functions across 3 files. Build first without section flags. Then build with -ffunction-sections -fdata-sections -Wl,--gc-sections. Verify in the linker map file that the unused functions are eliminated from the final binary.
