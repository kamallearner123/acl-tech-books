Topic 20

State Tables & Finite-State Machines

While the nested switch-case pattern examined in Topic 19 is ideal for simple state machines with 3 to 6 states, it degrades rapidly as system requirements scale. A complex medical ventilator or automotive battery management system (BMS) with 15 states and 20 distinct events produces a massive, monolithic function spanning thousands of lines. The cyclomatic complexity skyrockets, violating software engineering standards and creating severe maintenance hazards.

The architectural solution is the Table-Driven Finite-State Machine. By decoupling state machine topology (the state transition matrix) from state action execution logic, transitions become static data structures stored directly in Flash ROM. State lookups execute in guaranteed $O(1)$ constant time, and adding a new state or event requires zero modifications to the core dispatch engine.

20.1 The 2D State Table Architecture

In a two-dimensional state table, the current state indexes the rows, and the event signal indexes the columns. Each intersection cell contains a Transition Descriptor consisting of:

  1. Target Next State: The state to transition into upon event receipt.
  2. Action Handler Pointer: A function pointer to the specific action routine to execute during the transition.

20.2 Complete C Implementation of a Table-Driven Engine

Below is a production-grade, MISRA-compliant implementation of a 2D table-driven FSM with typed event parameters and flash placement. 

#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

/* Forward declaration */
typedef struct Fsm_t Fsm_t;

/* State & Event Enumerations */
typedef enum {
    STATE_STANDBY = 0,
    STATE_CHARGING,
    STATE_DISCHARGING,
    STATE_ERROR,
    STATE_MAX /* Boundary guard */
} BatteryState_t;

typedef enum {
    EVENT_PLUG_AC = 0,
    EVENT_UNPLUG_AC,
    EVENT_LOAD_CONNECTED,
    EVENT_OVERTEMP_FAULT,
    EVENT_MAX /* Boundary guard */
} BatteryEvent_t;

typedef struct {
    BatteryEvent_t signal;
    uint32_t       payload;
} Event_t;

/* Action handler function pointer type */
typedef void (*StateAction_t)(Fsm_t * const p_fsm, const Event_t * const p_evt);

/* Transition descriptor stored in Flash ROM */
typedef struct {
    BatteryState_t next_state;
    StateAction_t  action_fn;
} Transition_t;

/* FSM Context Instance */
struct Fsm_t {
    BatteryState_t state;
    uint32_t       cell_voltage_mv;
    int16_t        temperature_degc;
};

/* Forward Action Prototypes */
static void act_start_charge(Fsm_t * const p_fsm, const Event_t * const p_evt);
static void act_stop_charge(Fsm_t * const p_fsm, const Event_t * const p_evt);
static void act_start_discharge(Fsm_t * const p_fsm, const Event_t * const p_evt);
static void act_trip_error(Fsm_t * const p_fsm, const Event_t * const p_evt);
static void act_ignore(Fsm_t * const p_fsm, const Event_t * const p_evt);

/* 2D State Transition Matrix: Stored in .rodata (Flash) to conserve SRAM */
static const Transition_t g_state_table[STATE_MAX][EVENT_MAX] = {
    /* Current State: STATE_STANDBY */
    [STATE_STANDBY] = {
        [EVENT_PLUG_AC]        = { STATE_CHARGING,    act_start_charge },
        [EVENT_UNPLUG_AC]      = { STATE_STANDBY,     act_ignore },
        [EVENT_LOAD_CONNECTED] = { STATE_DISCHARGING, act_start_discharge },
        [EVENT_OVERTEMP_FAULT] = { STATE_ERROR,       act_trip_error }
    },
    /* Current State: STATE_CHARGING */
    [STATE_CHARGING] = {
        [EVENT_PLUG_AC]        = { STATE_CHARGING,    act_ignore },
        [EVENT_UNPLUG_AC]      = { STATE_STANDBY,     act_stop_charge },
        [EVENT_LOAD_CONNECTED] = { STATE_CHARGING,    act_ignore },
        [EVENT_OVERTEMP_FAULT] = { STATE_ERROR,       act_trip_error }
    },
    /* Current State: STATE_DISCHARGING */
    [STATE_DISCHARGING] = {
        [EVENT_PLUG_AC]        = { STATE_CHARGING,    act_start_charge },
        [EVENT_UNPLUG_AC]      = { STATE_DISCHARGING, act_ignore },
        [EVENT_LOAD_CONNECTED] = { STATE_DISCHARGING, act_ignore },
        [EVENT_OVERTEMP_FAULT] = { STATE_ERROR,       act_trip_error }
    },
    /* Current State: STATE_ERROR */
    [STATE_ERROR] = {
        [EVENT_PLUG_AC]        = { STATE_ERROR, act_ignore },
        [EVENT_UNPLUG_AC]      = { STATE_ERROR, act_ignore },
        [EVENT_LOAD_CONNECTED] = { STATE_ERROR, act_ignore },
        [EVENT_OVERTEMP_FAULT] = { STATE_ERROR, act_ignore }
    }
};

/* Generic O(1) Dispatch Engine */
void fsm_dispatch(Fsm_t * const p_fsm, const Event_t * const p_evt) {
    if ((p_fsm == NULL) || (p_evt == NULL)) {
        return;
    }

    /* Bounds check indices defensively against buffer overrun */
    if ((p_fsm->state >= STATE_MAX) || (p_evt->signal >= EVENT_MAX)) {
        act_trip_error(p_fsm, p_evt);
        p_fsm->state = STATE_ERROR;
        return;
    }

    const Transition_t * const p_trans = &g_state_table[p_fsm->state][p_evt->signal];

    /* Execute the registered transition action */
    if (p_trans->action_fn != NULL) {
        p_trans->action_fn(p_fsm, p_evt);
    }

    /* Advance to target state */
    p_fsm->state = p_trans->next_state;
}

20.3 Memory Footprint Analysis: RAM vs. ROM

A critical advantage of the table-driven pattern in microcontrollers is memory placement. Because the state table is marked const, it resides permanently in Flash ROM (.rodata), consuming zero SRAM:

sizeof(Transition_t) = 4 bytes (enum) + 4 bytes (function pointer) = 8 bytes
Table Footprint = 4 States × 4 Events × 8 bytes = 128 bytes of Flash ROM
Runtime RAM Consumption per FSM Instance = 12 bytes of SRAM

Even for a massive machine with 16 states and 16 events ($256$ cells), the table occupies only $256 \times 8 = 2048\text{ bytes}$ (2 KB) of Flash, leaving the entire volatile SRAM free for buffers and application data.

20.4 Hierarchical State Machines (HSMs) & Behavioral Inheritance

In classical flat FSMs, global events (such as EVENT_ESTOP, EVENT_LOW_BATTERY, or EVENT_RESET) must be explicitly listed in every single state, resulting in massive code duplication.

Hierarchical State Machines (HSMs) (formalized by David Harel in 1987) introduce Behavioral Inheritance: a substate inherits the event handlers of its superstate. If the substate does not consume an incoming event, the event automatically propagates upwards to the parent container state.

20.5 Code Comparison: Giant Switch-Case vs. 2D Table Engine

Compare a sprawling procedural switch-case with a modular table-driven architecture.

Compare Architecture: Complex Industrial Machine FSM

❌ Giant Nested Switch-Case

void fsm_dispatch(Event_t evt) {
    switch (g_state) {
        case S1:
            if (evt == E1) { ... }
            else if (evt == E2) { ... }
            else if (evt == E3) { ... }
            break;
        case S2:
            if (evt == E1) { ... }
            /* Repeated 20 times */
            /* 1,500 lines of code */
            /* Cyclomatic Complexity > 50 */
    }
}

Drawbacks: High cyclomatic complexity, variable lookup latency $O(N)$, hard to test individual cell paths, easy to introduce unintended fall-through bugs.

✔ 2D Table Engine

static const Transition_t table[S_MAX][E_MAX] = {
    [S1] = { [E1] = { S2, act1 }, [E2] = { S3, act2 } },
    [S2] = { [E1] = { S1, act3 } }
};

void fsm_dispatch(Fsm_t *fsm, Event_t evt) {
    const Transition_t *t = &table[fsm->state][evt];
    t->action(fsm);
    fsm->state = t->next_state;
}

Benefits: Constant $O(1)$ dispatch time, 5 lines of engine logic, stored entirely in Flash ROM, table serves as self-documenting test matrix.

20.6 Interactive Knowledge Check

Test your mastery of table-driven state machine architecture and hierarchical automata.

1. What is the time complexity of event dispatch in a two-dimensional table-driven state machine?
  • O(N) proportional to the number of states.
  • O(1) constant time, because lookup is a direct two-dimensional array index operation.
  • O(log N) using binary search trees.
  • O(N^2) quadratic time.
Explanation: Array indexing table[state][event] calculates the address in 1 to 2 CPU cycles, providing deterministic real-time dispatch latency regardless of machine size.
2. Why should the 2D state transition table be qualified with the const keyword in embedded C?
  • To allow the processor to modify the table at runtime.
  • To ensure the linker places the table into non-volatile Flash ROM (.rodata) rather than precious volatile SRAM (.data).
  • To prevent the preprocessor from deleting the file.
  • Because function pointers cannot exist in RAM.
Explanation: Marking large lookup tables as const places them in Flash memory, preserving scarce microcontroller SRAM for dynamic variables and buffers.
3. What is the primary software maintenance benefit of separating the state transition table from the action functions?
  • It eliminates the need for header files.
  • It separates machine topology from business logic: changing a transition requires editing only table data without touching procedural control flow code.
  • It doubles the serial baud rate.
  • It bypasses the C linker.
Explanation: Table-driven design encapsulates the graph structure in a declarative data matrix, keeping individual action handlers tiny, focused, and independently unit-testable.
4. In an FSM with 10 states and 8 events, how many cells does the 2D transition table contain?
  • 18
  • 80
  • 100
  • 64
Explanation: The table dimension is [STATES][EVENTS] = 10 × 8 = 80 cells.
5. What is the core innovation introduced by Hierarchical State Machines (HSMs)?
  • Replacing C with assembly language.
  • Behavioral inheritance: substates inherit event handlers from parent superstates, eliminating duplicate transitions for common events like E-Stop.
  • Running state machines on multi-core processors only.
  • Eliminating the need for event queues.
Explanation: HSMs allow parent superstates to handle shared events (e.g. EVENT_ESTOP or EVENT_LOW_BATTERY) once, rather than repeating the transition across every child substate.
6. What defensive check must be executed before indexing into g_state_table[fsm->state][evt->signal]?
  • Verify the clock crystal frequency.
  • Verify that fsm->state < STATE_MAX and evt->signal < EVENT_MAX to prevent out-of-bounds array access memory corruption.
  • Disable the SysTick timer.
  • Read the MCU temperature sensor.
Explanation: Array bounds verification guards against corrupted enums caused by memory bit-flips or uninitialized variables, satisfying MISRA-C Rule 18.1.
7. What is an "Ignore Action" (act_ignore) in a table-driven FSM?
  • An empty function that triggers a CPU reboot.
  • A benign action handler that takes no action and leaves the state unchanged when an irrelevant event occurs.
  • A compiler warning suppressor.
  • A function that deletes the transition table from RAM.
Explanation: An explicit ignore function (or NULL pointer check) cleanly absorbs events that have no effect in the current state without triggering an error.
8. In C99, what syntax feature allows sparse or readable initialization of the 2D state transition table?
  • Operator overloading.
  • Designated Initializers: [STATE_IDLE] = { [EVENT_START] = { ... } }.
  • Templates.
  • Lambda expressions.
Explanation: C99 designated initializers allow indexing table entries by their explicit enum names, making the matrix readable and resilient to enum reordering.
9. What is the cyclomatic complexity of a table-driven fsm_dispatch() function?
  • Proportional to the number of states times events ($S \times E$).
  • Extremely low (typically 2 to 3), consisting only of bounds validation and pointer invocation.
  • Infinite.
  • Equal to the number of CPU registers.
Explanation: Because branching is replaced by tabular indexing, the dispatch engine has virtually zero cyclomatic complexity, passing any static analysis audit with ease.
10. When should an engineer transition from a nested switch-case FSM to a 2D table-driven FSM?
  • Only when the microcontroller has more than 1 GB of RAM.
  • When state and event counts grow beyond ~6-8 items and switch-case complexity threatens readability, maintainability, and test coverage.
  • Never; switch-case is always superior.
  • Only when using C++ compilers.
Explanation: Switch-case is excellent for small FSMs (low boilerplate). Table-driven FSMs are superior for mid-to-large FSMs where tabular structure prevents maintenance bugs.

20.7 Hands-On Engineering Laboratories

Execute these 5 laboratory assignments to master table-driven automata and hierarchical state machine architectures.

Assignment 1: Vending Machine 2D Table Engine

Task: Implement a complete table-driven state machine for an automated vending machine: states WAITING_COIN, CREDIT_INSERTED, DISPENSING, RETURNING_CHANGE; events COIN_10C, COIN_25C, BUTTON_SELECT, BUTTON_CANCEL, MOTOR_DONE. Store the transition table in const Flash and verify dispatch latency.

Assignment 2: State Entry and Exit Action Extenders

Task: Extend the Transition_t structure to support Moore-style entry and exit actions. When entering DISPENSING, turn on a dispensing LED; when exiting, turn it off. Verify that transitioning from state A to state B executes: State_A_Exit() → Transition_Action() → State_B_Entry().

Assignment 3: Host-Based Automated State Table Tester

Task: Write a test runner in C on the host PC that automatically executes every single cell in the 2D matrix. Verify that all out-of-bounds state and event indices are trapped defensively without a segmentation fault or undefined behavior.

Assignment 4: Flash vs. SRAM Footprint Verification

Task: Compile the table-driven FSM with GCC ARM toolchain. Use arm-none-eabi-nm -S and arm-none-eabi-size -A to prove that the 2D transition table is located in the .rodata Flash segment and consumes zero bytes in the .bss or .data SRAM segments.

Assignment 5: Lightweight Hierarchical FSM Dispatcher

Task: Build a 2-level hierarchical state machine where an unhandled event in a substate delegates automatically to a parent state handler via a parent function pointer: fsm->parent_state_handler(fsm, evt). Test with an emergency stop event and confirm clean hierarchical bubbling.
