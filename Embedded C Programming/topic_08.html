Topic 8

objdump, size, nm & GDB

Compiling C source code produces an Executable and Linkable Format (ELF) binary. An ELF file is not a black box: it contains complete metadata regarding physical memory section layouts, function and variable symbol tables, and DWARF debugging information.

Proficient firmware engineers do not guess where memory is being consumed or why code crashes; they inspect the binary directly using GNU Binutils: size to monitor Flash and SRAM footprints, nm to identify memory-hogging variables, objdump to verify emitted assembly instructions, and GDB paired with hardware debug probes (JTAG/SWD) to inspect live registers and set non-intrusive hardware watchpoints.

8.1 Memory Footprint Auditing with 'size'

The size utility reports the byte allocation across ELF sections. Understanding how the numbers map to physical microcontroller memory is essential: 

$ arm-none-eabi-size -B firmware.elf
   text    data     bss     dec     hex filename
  24576    1024    4096   29696    7400 firmware.elf
Program 8.1: Standard Output of GNU size Utility
Section Physical Memory Location Calculation for Total Hardware Usage
text Non-volatile Flash / ROM Machine instructions + vector table + const read-only data (.rodata).
data Both Flash & SRAM Consumes Flash for initial values; consumes SRAM at runtime.
bss Volatile SRAM only Zero-initialized variables. Consumes 0 bytes of Flash!
TOTALS Flash = text + data SRAM = data + bss (+ stack & heap)

8.2 Symbol Table Exploration with 'nm'

When SRAM is running low, the nm utility locates the exact variables consuming the most memory by sorting symbols by byte size:
arm-none-eabi-nm --size-sort --print-size --radix=d firmware.elf

Common symbol types reported by nm:

  • T / t: Code section symbol (Function in .text). Capital T = global; lowercase t = static private.
  • D / d: Initialized data symbol (resides in .data).
  • B / b: Uninitialized symbol (resides in .bss).
  • R / r: Read-only data symbol (resides in .rodata Flash).

8.3 Disassembly with 'objdump -d -S'

The objdump utility converts binary machine code back into assembly. When compiled with debug symbols (-g), the -S flag interleaves original C source lines directly with emitted assembly instructions:
arm-none-eabi-objdump -d -S -C firmware.elf > firmware.asm

8.4 Remote Hardware Debugging with GDB

To debug physical silicon, GDB connects to an in-circuit debug server (OpenOCD, J-Link, pyOCD) over a TCP socket (typically port 3333):

8.5 Hands-On Code Implementations

The following GDB script automates connecting to an OpenOCD target, loading an ELF binary into Flash, resetting the CPU, and halting at main(): 

# GDB Remote Debugging Automation Script
# Usage: arm-none-eabi-gdb -x debug.gdb firmware.elf

# 1. Connect to OpenOCD GDB server running on localhost
target extended-remote localhost:3333

# 2. Reset and halt the microcontroller core
monitor reset halt

# 3. Flash the compiled ELF binary into on-chip microcontroller Flash
load

# 4. Set hardware breakpoint at main()
b main

# 5. Set hardware data write watchpoint on a memory address to catch corruption
# watch *0x20000004

# 6. Resume execution until main() is reached
continue

# Useful GDB inspection commands during active debug session:
# info registers           - Print all CPU core registers (R0-R15, xPSR, MSP, PSP)
# x/16xw 0x20000000        - Examine 16 words in hexadecimal from SRAM start
# print/x *GPIOA           - Print peripheral register struct contents
# bt                       - Backtrace call stack frames
# stepi                    - Single-step a single assembly instruction
Program 8.2: Automated GDB Remote Session Configuration Script

8.6 Buggy vs. Modern Safe Code Comparison

When a variable experiences random memory corruption, standard printfs fail to catch the culprit. GDB hardware watchpoints allow zero-overhead trapping the exact instant the memory location is written.

View Buggy/Legacy Code

In this code, an out-of-bounds array write in uart_driver.c silently corrupts the neighboring system_state variable in SRAM: 

/* IN uart_driver.c: Off-by-one buffer overflow */
uint8_t rx_buffer[16];
/* IN main.c: Located immediately adjacent to rx_buffer in SRAM */
volatile uint32_t system_state = 0x01; 

void bad_uart_isr(void) {
    /* Bug: Writes past index 15, corrupting system_state at index 16! */
    for (int i = 0; i <= 16; i++) {
        rx_buffer[i] = 0xFF; /* Overwrites system_state! */
    }
}
Program 8.3-A: Silent Adjacent Memory Corruption

Setting a GDB watchpoint watch system_state traps the exact assembly instruction and call stack that committed the invalid write: 

(gdb) watch system_state
Hardware watchpoint 1: system_state
(gdb) continue
Hardware watchpoint 1: system_state
Old value = 1
New value = 255
bad_uart_isr () at uart_driver.c:8
8           rx_buffer[i] = 0xFF;
(gdb) bt
#0  bad_uart_isr () at uart_driver.c:8
#1  <signal handler called>

Topic Quiz (10 Questions)

Test your ability to inspect binaries, audit memory sections, and debug with GDB.

1. When reviewing the output of 'size firmware.elf', how do you calculate total Flash memory consumption?
  • Flash = text + bss
  • Flash = text + data
  • Flash = data + bss
  • Flash = text + data + bss
Flash holds executable instructions (.text) and the non-volatile initial values for mutable variables (.data). .bss consumes zero Flash.
2. When reviewing the output of 'size firmware.elf', how do you calculate minimum SRAM memory consumption?
  • SRAM = text + data
  • SRAM = text + bss
  • SRAM = data + bss (+ stack and heap reserve)
  • SRAM = dec - hex
Static SRAM is consumed by initialized globals (.data) plus zero-initialized globals (.bss). The remaining SRAM hosts the stack and heap.
3. What does symbol type 'B' represent in the output of the 'nm' utility?
  • A function in the Bootloader.
  • A global variable residing in the uninitialized .bss section of SRAM.
  • A breakpoint.
  • A read-only binary constant.
In nm, 'B' indicates a global uninitialized symbol in the .bss section; lowercase 'b' indicates a static local variable in .bss.
4. Which flag passed to 'objdump' interleaves original C source code lines with the emitted disassembly?
  • -x
  • -t
  • -S (source interleave)
  • -r
-S displays source code intermixed with disassembly, provided the binary was compiled with debug information (-g).
5. What is the fundamental difference between a GDB breakpoint and a GDB watchpoint?
  • Breakpoints run in Flash; watchpoints run in RAM.
  • A breakpoint halts execution when an instruction address is reached; a watchpoint halts execution when a memory location is read or written.
  • Watchpoints only work on simulated CPUs.
  • Breakpoints require an oscilloscope.
Watchpoints monitor data access (reads/writes) using hardware comparator registers, while breakpoints monitor program counter instruction fetch addresses.
6. What GDB command examines 16 consecutive 32-bit words in hexadecimal starting at address 0x20000000?
  • show memory 16 0x20000000
  • x/16xw 0x20000000
  • print 16 words 0x20000000
  • dump ram 16
x/16xw stands for: eXamine / 16 count, in heXadecimal, Words (32-bit).
7. Why are hardware breakpoints limited in number (typically 4 to 8) on ARM Cortex-M microcontrollers?
  • GDB licenses restrict breakpoints.
  • They rely on dedicated physical hardware comparator registers inside the Flash Patch and Breakpoint (FPB) unit on the silicon.
  • Flash memory cannot hold more than 4 functions.
  • The SWD cable has only 4 wires.
Cortex-M FPB units implement a fixed number of silicon address comparator registers (e.g. 6 in Cortex-M4), bounding the number of simultaneous hardware breakpoints in Flash.
8. What GDB command single-steps a single assembly machine instruction rather than an entire C source line?
  • next
  • step
  • stepi (or nexti)
  • continue
stepi executes exactly one machine instruction, allowing precise stepping through assembly startup sequences and register updates.
9. What does the GDB command 'backtrace' (or 'bt') display?
  • The historical Git commit log.
  • The current chain of function call stack frames leading up to the active execution point.
  • The list of linker memory sections.
  • The Flash wear-leveling status.
backtrace unwinds stack frames using the Link Register (LR) and stack pointers to show which functions called the current function.
10. What GNU Binutils tool is used to extract a raw binary (.bin) or Intel Hex (.hex) file from an ELF binary for flashing?
  • arm-none-eabi-nm
  • arm-none-eabi-readelf
  • arm-none-eabi-objcopy
  • arm-none-eabi-ar
objcopy converts between object formats, stripping debug symbols and producing raw binary images ready to be written into Flash memory.

Hands-On Assignments

Execute these 5 laboratory assignments to master binary inspection and live silicon debugging.

Assignment 1: Largest Symbol Identification

Task: Run arm-none-eabi-nm --size-sort -C -r firmware.elf on your project binary. Identify the top 5 largest functions in .text and the top 5 largest data buffers in SRAM. Document their exact byte sizes.

Assignment 2: Disassembly Source Interleaving

Task: Compile a C file with -O2 -g. Run arm-none-eabi-objdump -d -S firmware.elf > disassembly.txt. Open the text file and locate a for-loop. Analyze how the compiler unrolled the loop and which CPU registers were allocated to loop index variables.

Assignment 3: Hardware Data Watchpoint Trap

Task: Connect to your target using GDB via OpenOCD. Set a hardware watchpoint on a global variable: watch g_counter. Run continue. When GDB halts, inspect the old and new value, print the active registers with info registers, and verify the line number.

Assignment 4: Raw Binary Extraction and Size Verification

Task: Use arm-none-eabi-objcopy -O binary firmware.elf firmware.bin. Check the exact file size on disk using ls -l firmware.bin. Compare this number to the sum of text + data from size and explain why they match identically.

Assignment 5: Live Peripheral Register Inspection via GDB

Task: In an active GDB session halted at a breakpoint, read the 32-bit hardware value of GPIOA Port Output Data Register (x/1xw 0x40020014). Then use GDB's set command to force a bit high (set *(uint32_t*)0x40020014 = 0x20) and verify that the physical LED illuminates immediately on the board.
