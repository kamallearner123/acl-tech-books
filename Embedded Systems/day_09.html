9.1 Beyond the Bare-Metal Superloop: The Need for an RTOS

As embedded applications grow in complexity, bare-metal superloops begin to collapse under their own architectural weight. Consider a modern medical infusion pump: it must simultaneously run a motor PID velocity loop at 1 kHz, poll keypad inputs, refresh an OLED UI, parse incoming hospital network packets over Wi-Fi, monitor optical bubble sensors, and kick a hardware watchdog. In a superloop, if the Wi-Fi network routine stalls for 50 milliseconds while resolving a TCP timeout, the motor PID loop drifts, causing severe dosing errors!

A Real-Time Operating System (RTOS) solves this by introducing Preemptive Multitasking. Instead of running one massive sequential loop, software is partitioned into independent, decoupled threads of execution called Tasks. A deterministic kernel scheduler rapidly switches the CPU between tasks based on strictly enforced priority levels, guaranteeing that safety-critical deadlines are met within microsecond tolerances.

Real World Example: In an automotive Gateway Electronic Control Unit (ECU), a FreeRTOS kernel manages dozens of concurrent tasks: high-priority CAN bus routing tasks preempt low-priority diagnostic logging and Bluetooth pairing routines instantly whenever safety-critical steering angle frames arrive.
Figure 2.0-1: FreeRTOS Task Finite State Machine Transition Diagram
Figure Parameters Explained:
  • Running State: The task currently possessing the CPU core; on a single-core MCU, exactly one task is Running.
  • Ready State: Tasks that are ready to execute but have equal or lower priority than the currently Running task.
  • Blocked State: Task is asleep waiting for either a time delay or an external resource (queue, semaphore, event group). Consumes 0% CPU cycles.
  • Suspended State: Task is frozen indefinitely via vTaskSuspend(); only wakes upon an explicit vTaskResume() call.

9.2 The Mechanics of a Real-Time Context Switch

How does a single microcontroller core give the illusion of running multiple C functions simultaneously? The answer lies in the Context Switch. Each task in FreeRTOS is allocated its own private stack in SRAM. When the scheduler decides to switch from Task A to Task B:

  1. The hardware and kernel save Task A's complete execution context (Core registers R0-R12, SP, LR, PC, and xPSR) onto Task A's private stack.
  2. Task A's current Stack Pointer is recorded into its Task Control Block (TCB).
  3. The scheduler identifies the highest-priority task in the Ready list (Task B).
  4. The CPU Stack Pointer is switched to point to Task B's stack.
  5. Task B's registers are popped from its stack into CPU hardware, and execution resumes exactly where Task B was previously interrupted.

On ARM Cortex-M microcontrollers, this context switch is executed inside the PendSV exception handler at the lowest priority level, ensuring that hardware ISRs are never blocked by operating system context switching overhead.

Figure 2.0-2: ARM Cortex-M Hardware Context Switch via PendSV Exception
Figure Parameters Explained:
  • Task Control Block (TCB): Kernel data structure storing task name, priority, private stack base, and current stack pointer.
  • Private Task Stack: Dedicated SRAM block holding function local variables, call return addresses, and saved registers.
  • PendSV Handler: ARM Cortex-M exception specifically architected to defer context switching until all hardware ISRs complete.
  • Switch Latency: Typically spans 80 to 150 clock cycles (approx 1 to 2 microseconds at 84-168 MHz).

9.3 FreeRTOS Dynamic Memory Allocation Models (Heap 1 through Heap 5)

Standard C library malloc() and free() are strictly forbidden in safety-critical embedded systems: they are non-deterministic, non-thread-safe, consume excessive code space, and cause catastrophic heap fragmentation over time. FreeRTOS provides 5 modular memory allocation implementations to suit different safety architectures:

  • heap_1.c: Simplest model. Only allocates memory; never frees. Completely immune to fragmentation. Ideal for safety-critical systems that allocate all tasks and queues at boot and run forever.
  • heap_2.c: Allows freeing memory using a best-fit algorithm, but does not coalesce adjacent free blocks. Obsolete; replaced by heap_4.
  • heap_3.c: Wraps standard C library malloc() and free() with thread-safe scheduler locks.
  • heap_4.c: Most widely used. Implements first-fit allocation and automatically coalesces adjacent free memory blocks into larger contiguous blocks to defeat fragmentation.
  • heap_5.c: Extends heap_4 to allow the heap to span multiple non-contiguous physical memory banks (e.g. internal SRAM + external SDRAM).
Figure 2.0-3: FreeRTOS Heap_4 Memory Allocation and Coalescing Engine
Figure Parameters Explained:
  • Block Header: Stores metadata containing the size of the block and a pointer to the next free block.
  • Coalescing: Merging neighboring freed blocks back together into larger unified memory segments.
  • xPortGetFreeHeapSize(): API function returning total unallocated heap memory remaining.
  • xPortGetMinimumEverFreeHeapSize(): Returns the historic lowest free heap watermark to verify memory headroom under peak load.

9.4 Deterministic Timekeeping: vTaskDelay vs. vTaskDelayUntil

FreeRTOS tracks time using periodic timer interrupts called Kernel Ticks (typically configured at 1000 Hz / 1 ms per tick via SysTick). When delaying a task, engineers must choose between two APIs:

  • vTaskDelay(ticks): Delays the task for a specified duration relative to the moment the function was invoked. If the task execution time varies or is preempted by higher-priority tasks, cumulative drift occurs!
  • vTaskDelayUntil(&previousWakeTime, period): Guarantees a strictly constant, jitter-free execution frequency. It calculates the sleep duration relative to the target period, automatically absorbing execution variations.
Figure 2.0-4: Cumulative Timing Drift: vTaskDelay vs. Jitter-Free vTaskDelayUntil
Figure Parameters Explained:
  • vTaskDelay Drift: Period = Task Execution Time + Delay Time. Execution variability accumulates continuously over time.
  • vTaskDelayUntil Precision: Calculates sleep relative to fixed absolute tick milestones: Next Wake = Previous Wake + Period.
  • Sensor Control Loops: Digital filters (Kalman filters, PID controllers) require strictly constant delta-t (dt) to remain stable.

9.5 Stack Sizing and Stack Overflow Detection Hooks

In an RTOS, every task has its own private stack. Under-sizing a task stack leads to memory corruption as the stack collides with neighboring TCBs. Over-sizing task stacks exhausts limited SRAM. FreeRTOS provides two complementary tools to achieve optimal sizing:

  • uxTaskGetStackHighWaterMark(task): Returns the minimum number of unused words that have remained on the task stack since the task started. An ideal high-water mark is between 20 and 50 words.
  • configCHECK_FOR_STACK_OVERFLOW: Kernel hook (Method 1 checks if SP exceeds boundary; Method 2 checks if the final 16 bytes of the stack canary pattern have been overwritten) that traps the CPU into vApplicationStackOverflowHook() upon violation.
Figure 2.0-5: Task Control Block (TCB) Layout and Stack Watermark Inspection
Figure Parameters Explained:
  • TCB (Task Control Block): Silicon structure maintaining kernel scheduling state for each independent thread.
  • High-Water Mark: Measures the closest the stack pointer ever got to overflowing its allocated SRAM boundary.
  • Stack Overflow Hook: Emergency trap function executed immediately if the canary zone at the end of stack is breached.

9.6 Hands-On Code Implementations


#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"

#define LED_PIN     5

/* Task Handles */
TaskHandle_t xLedTaskHandle = NULL;
TaskHandle_t xHeartbeatTaskHandle = NULL;

/* Task 1: Blink LED every 500 ms */
void vLedBlinkTask(void *pvParameters) {
    (void)pvParameters;
    
    for (;;) {
        /* Toggle LED hardware register */
        *(volatile uint32_t *)0x40020014UL ^= (1UL << LED_PIN);
        
        /* Block task for 500 ticks (500 ms) */
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

/* Task 2: Stream UART heartbeat counter every 1000 ms */
void vHeartbeatTask(void *pvParameters) {
    (void)pvParameters;
    uint32_t counter = 0;
    
    for (;;) {
        counter++;
        /* Non-blocking delay */
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void) {
    /* 1. Initialize hardware clocks and GPIO pins */

    /* 2. Create Task 1: 128 words stack, Priority 1 */
    xTaskCreate(vLedBlinkTask, "LED_Task", 128, NULL, 1, &xLedTaskHandle);

    /* 3. Create Task 2: 128 words stack, Priority 2 (Higher Priority) */
    xTaskCreate(vHeartbeatTask, "Heartbeat", 128, NULL, 2, &xHeartbeatTaskHandle);

    /* 4. Start the FreeRTOS Scheduler (Never Returns) */
    vTaskStartScheduler();

    /* Should never reach here unless heap memory was exhausted */
    for (;;);
    return 0;
}

    }
}

  • Because it stores the heap in external battery-backed SRAM
  • Because it replaces the C compiler linker script
In safety-critical systems governed by DO-178C or ISO 26262, dynamic deallocation is forbidden. heap_1 satisfies this rule by prohibiting frees.
