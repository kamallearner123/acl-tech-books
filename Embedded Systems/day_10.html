10.1 Real-Time Scheduling Paradigms: Preemptive vs. Cooperative

In real-time embedded systems, simply dividing code into tasks is insufficient: you must mathematically guarantee that critical tasks complete execution before their deadlines expire. The RTOS scheduler is the engine responsible for allocating CPU execution time. Schedulers operate under two primary disciplines:

  • Cooperative Scheduling: A task retains control of the CPU until it explicitly yields execution (via taskYIELD() or blocking). If a poorly written task enters an infinite calculation or fails to yield, every other task in the system is starved.
  • Preemptive Scheduling: The kernel scheduler can forcibly interrupt and suspend a running task at any instant if a higher-priority task transitions from Blocked to Ready. Preemption guarantees instantaneous response to real-time events.
  • Round-Robin Time-Slicing: When multiple Ready tasks share the exact same priority level, the scheduler shares CPU time equally among them, switching between them on each SysTick tick interrupt.
Real World Example: In an automotive electronic throttle control (drive-by-wire) system, the pedal position sensor task runs every 5 milliseconds with highest preemption priority. If a driver suddenly stomps on the accelerator pedal, the pedal task preempts background fuel economy logging and dashboard display rendering in under 5 microseconds, updating throttle valve PWM immediately.
Figure 2.1-1: Preemptive Scheduling and Priority Preemption Execution Timeline
Figure Parameters Explained:
  • Preemption Latency: The time elapsed between a high-priority task becoming ready and the first instruction of that task executing.
  • Time Slicing: Tasks of equal priority receive equal quantum slices of CPU execution time bounded by the SysTick tick interval.
  • Starvation Risk: If a high-priority task never enters the Blocked state, lower-priority tasks will never execute.

10.2 Rate-Monotonic Scheduling (RMS) Theory & Schedulability Bounds

How should an embedded engineer assign priority numbers across a dozen competing tasks? Guessing priorities leads to missed deadlines and mysterious system lockups. In 1973, Liu and Layland formulated Rate-Monotonic Scheduling (RMS), the mathematically optimal static priority assignment policy for periodic independent tasks:

The RMS Rule: Tasks with shorter periods (higher frequencies) MUST be assigned higher priorities.

Furthermore, Liu and Layland proved the RMS Utilization Upper Bound theorem. For a set of $n$ periodic tasks with computation times $C_i$ and periods $T_i$, the total CPU utilization $U$ is guaranteed to be schedulable if:

$$U = \sum_{i=1}^n \frac{C_i}{T_i} \le n\left(2^{1/n} - 1\right)$$

As $n \to \infty$, the utilization bound asymptotically approaches $\ln(2) \approx 69.3\%$. Any task set with total CPU utilization below 69.3% is mathematically proven to never miss a deadline under RMS.

Figure 2.1-2: Rate-Monotonic Scheduling Timeline and Task Execution Windows
Figure Parameters Explained:
  • Period (T): The regular interval at which a periodic task is re-triggered.
  • Worst-Case Execution Time (WCET, C): The maximum possible computation time the task consumes when executing uninterrupted.
  • Utilization (U = C/T): The fraction of total CPU bandwidth consumed by a specific task.
  • Deadline (D): The point in time by which a task execution cycle must finish (typically D = T).

10.3 Measuring Worst-Case Execution Time (WCET) via DWT Cycle Counters

To apply RMS mathematical theorems, an engineer must accurately measure each task's Worst-Case Execution Time (WCET). Simulators and averages are insufficient; firmware must capture peak execution cycles under maximum algorithmic workload. The ARM Cortex-M architecture provides the Data Watchpoint and Trace (DWT) Cycle Counter (CYCCNT), an internal 32-bit hardware register incrementing at the full CPU core clock frequency (e.g. 168 MHz = 5.95 nanoseconds per tick).

Figure 2.1-3: Profiling Code Execution using ARM DWT_CYCCNT Cycle Counter
Figure Parameters Explained:
  • DWT_CYCCNT Register: 32-bit free-running hardware counter incrementing every CPU clock cycle.
  • Zero Measurement Overhead: Reading DWT_CYCCNT takes 1 machine instruction (LDR), introducing negligible timing perturbation.
  • Cycle to Microsecond Conversion: Time in microseconds = (Cycles Elapsed) / (CPU Clock Frequency in MHz).

10.4 FreeRTOS Trace Hooks and Runtime Execution Statistics

To inspect real-time multi-tasking dynamics in production, FreeRTOS incorporates Trace Macros and Hooks. By defining traceTASK_SWITCHED_IN() and traceTASK_SWITCHED_OUT(), developers hook directly into the kernel context switcher. These hooks can toggle hardware pins for logic analyzer inspection or accumulate per-task runtime statistics to generate live CPU utilization dashboards.

Figure 2.1-4: FreeRTOS Kernel Trace Hooks and Logic Analyzer Task Profiling
Figure Parameters Explained:
  • traceTASK_SWITCHED_IN(): Macro invoked immediately after a task is swapped onto the CPU.
  • traceTASK_SWITCHED_OUT(): Macro invoked immediately before a task is suspended from the CPU.
  • vTaskGetRunTimeStats(): Kernel API generating an ASCII table of all tasks, their total runtime ticks, and their exact CPU% share.

10.5 Low-Power Tickless Idle Architecture

In standard RTOS configurations, the SysTick interrupt fires every 1 millisecond. Even when all tasks are Blocked and the system is completely idle, the CPU wakes up 1,000 times per second just to service the tick, draining battery power needlessly. Tickless Idle Mode eliminates this waste: when all tasks are asleep, the kernel calculates the sleep duration until the next earliest deadline, disables SysTick, and configures a low-power timer to sleep continuously for seconds or minutes.

Figure 2.1-5: Standard Periodic Tick vs. Low-Power Tickless Idle Sleep
Figure Parameters Explained:
  • configUSE_TICKLESS_IDLE: FreeRTOS configuration option enabling automated suppression of tick interrupts during idle intervals.
  • Suppressed Ticks: The kernel calculates the number of ticks skipped during deep sleep and steps the internal tick count forward upon wakeup.
  • Wakeup Sources: System can be awakened prematurely by any external hardware interrupt (GPIO, UART, CAN) without loss of timebase.

#include <stdint.h>
#include <stdbool.h>
#include <math.h>

typedef struct {
    const char *name;
    uint32_t period_ms;
    uint32_t wcet_ms;
    uint8_t  assigned_priority;
} TaskSpec_t;

/* Evaluate whether task set is mathematically guaranteed to meet deadlines under RMS */
bool verify_rms_schedulability(const TaskSpec_t *tasks, uint8_t num_tasks) {
    float total_utilization = 0.0f;

    for (int i = 0; i < num_tasks; i++) {
        total_utilization += (float)tasks[i].wcet_ms / (float)tasks[i].period_ms;
    }

    /* Liu & Layland Bound: U_bound = n * (2^(1/n) - 1) */
    float u_bound = (float)num_tasks * (powf(2.0f, 1.0f / (float)num_tasks) - 1.0f);

    return (total_utilization <= u_bound);
}

 * Task 1: Period 20 ms, WCET 4 ms   -> U = 20.0% -> Priority 3 (Highest)
 * Task 2: Period 50 ms, WCET 10 ms  -> U = 20.0% -> Priority 2 (Medium)
 * Task 3: Period 100 ms, WCET 20 ms -> U = 20.0% -> Priority 1 (Lowest)
 * Total Utilization = 60.0% <= U_bound(3) = 77.9% -> Schedulability Guaranteed!
 */

#include <stdint.h>

#define CoreDebug_DEMCR (*(volatile uint32_t *)0xE000EDFCUL)
#define DWT_CTRL        (*(volatile uint32_t *)0xE0001000UL)
#define DWT_CYCCNT      (*(volatile uint32_t *)0xE0001004UL)

void dwt_cycle_counter_init(void) {
    CoreDebug_DEMCR |= (1UL << 24); /* Enable Trace System (TRCENA) */
    DWT_CYCCNT = 0;                 /* Reset counter */
    DWT_CTRL |= (1UL << 0);          /* Enable CYCCNT */
}

typedef struct {
    uint32_t min_cycles;
    uint32_t max_cycles; /* WCET */
    uint32_t total_cycles;
    uint32_t run_count;
} TaskExecutionProfile_t;

static TaskExecutionProfile_t g_profile = {0xFFFFFFFF, 0, 0, 0};

void profile_workload(void (*func)(void)) {
    uint32_t start_cycles = DWT_CYCCNT;
    
    func(); /* Execute target workload */
    
    uint32_t elapsed = DWT_CYCCNT - start_cycles;
    
    if (elapsed > g_profile.max_cycles) g_profile.max_cycles = elapsed;
    if (elapsed < g_profile.min_cycles) g_profile.min_cycles = elapsed;
    g_profile.total_cycles += elapsed;
    g_profile.run_count++;
}

#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"

/* In FreeRTOSConfig.h:
 * #define traceTASK_SWITCHED_IN()   vTraceTaskSwitchedIn()
 * #define traceTASK_SWITCHED_OUT()  vTraceTaskSwitchedOut()
 */

#define GPIOA_BSRR (*(volatile uint32_t *)0x40020018UL)

void vTraceTaskSwitchedIn(void) {
    TaskHandle_t current = xTaskGetCurrentTaskHandle();
    
    /* Probe pins on Logic Analyzer based on active task handle */
    if (current == xTaskGetHandle("SensorTask")) {
        GPIOA_BSRR = (1UL << 0); /* PA0 HIGH */
    } else if (current == xTaskGetHandle("ControlTask")) {
        GPIOA_BSRR = (1UL << 1); /* PA1 HIGH */
    }
}

void vTraceTaskSwitchedOut(void) {
    /* Pull all profiling pins LOW upon context exit */
    GPIOA_BSRR = (0x03UL << 16); /* Reset PA0 and PA1 */
}

        }

  • Period must always be smaller than Execution time
  • There is no difference in real-time systems
Execution time is the computational duration of the task's algorithm. Period is the recurrence interval at which the task must repeat.
9. When two FreeRTOS tasks have identical priority levels and are both in the Ready state, how does the scheduler resolve them?
  • It deletes the task that was created second
  • It shares CPU time equally between them using round-robin time-slicing on each tick interrupt
  • It triggers a UsageFault exception
  • It executes them simultaneously on separate ALUs
Tasks of equal priority are executed in a round-robin circular queue, each receiving a 1 ms quantum slice before the scheduler switches to the next.
10. What is 'Scheduling Latency' in an RTOS?
  • The time required to compile the FreeRTOS source code
  • The delay between an event becoming ready and the scheduler actually dispatching the task to the CPU
  • The duration of an I2C transaction
  • The baud rate divided by clock frequency
Scheduling latency measures kernel responsiveness: the delay from an event occurring to the designated task acquiring CPU control.
