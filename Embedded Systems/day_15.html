15.1 Bootloader vs Application Architectural Separation

In production embedded engineering, deploying firmware to devices operating in remote field installations—such as automotive engine controllers, smart utility meters, or orbital satellites—demands the ability to update firmware without physical access via JTAG or SWD debuggers. This is achieved through a dedicated secondary program stored permanently in internal non-volatile memory: the In-System Programming (ISP) Bootloader.

The internal Flash memory is divided into distinct physical memory regions: a small, immutable Bootloader Partition located at the physical reset address (e.g., 0x08000000), an active Application Slot A, an update staging Application Slot B, and a persistent Metadata / NVM Configuration Sector.

Figure 15.0-1: Flash Memory Partitioning for Safe In-Field and OTA Firmware Updates
Figure Parameters Explained:
  • Bootloader Slot (0x08000000): Protected, non-volatile initial execution target executed upon every power-on reset (POR).
  • Metadata Partition (0x08004000): Contains boot state machines, firmware version numbers, execution counters, and 32-bit CRC signatures.
  • Dual-Bank Slots A & B: Permits atomic background download into inactive bank while the current bank continues real-time execution.
  • Golden Image Rollback: Allows immediate recovery to a known operational image if the newly flashed application crashes or fails watchdog health checks.

15.2 The Boot Decision Flow and Vector Relocation (VTOR)

Upon power-on reset, the microcontroller core executes the bootloader. The bootloader performs hardware sanity checks, samples a physical DFU recovery pin or UART command byte, and reads the metadata partition to determine which application slot is active and valid.

To transfer control to the user application, the bootloader must perform two low-level hardware procedures:

  1. Relocate the CPU Vector Table Offset Register (SCB->VTOR) to the base address of the application slot (e.g., 0x08008000).
  2. Load the Main Stack Pointer (MSP) from the first 32-bit word of the application's vector table, and jump to the function address specified in the second 32-bit word (the Application Reset Handler).

Figure 15.0-2: Bootloader Execution Flow and Application Branching State Machine
Figure Parameters Explained:
  • Hardware Pin Sampling: Samples a designated external switch or UART header within 50 ms of boot to permit emergency recovery.
  • CRC32 Integrity Validation: Computes polynomial checksum across application flash boundaries before permitting vector jump.
  • SCB->VTOR Relocation: Repoints CPU exception entry points to application interrupt handlers so peripherals fire correctly.
  • DFU Recovery Loop: Waits indefinitely for incoming firmware packets if application flash is corrupted or blank.

15.3 Vector Table Jump and Stack Pointer Initialization in C

Executing a jump to an embedded application requires direct assembly instructions or inline C function pointers. Because the ARM Cortex-M architecture places the initial stack pointer at address AppBase + 0x00 and the Reset Handler vector at AppBase + 0x04, the bootloader reads these memory words directly.


#include <stdint.h>

#define APP_START_ADDRESS   0x08008000U
#define SCB_VTOR            (*(volatile uint32_t *)0xE000ED08U)

typedef void (*pFunction)(void);

void jump_to_application(uint32_t app_address) {
    /* 1. Verify application stack pointer is located in valid internal SRAM */
    uint32_t app_stack = *(volatile uint32_t *)app_address;
    if ((app_stack & 0x2FFE0000U) != 0x20000000U) {
        /* Invalid stack pointer; abort jump to avoid HardFault */
        return;
    }

    /* 2. Disable all interrupts and clear pending flags */
    __asm volatile ("cpsid i" : : : "memory");
    for (int i = 0; i < 8; i++) {
        *(volatile uint32_t *)(0xE000E180U + (i * 4)) = 0xFFFFFFFFU; /* NVIC ICER */
        *(volatile uint32_t *)(0xE000E280U + (i * 4)) = 0xFFFFFFFFU; /* NVIC ICPR */
    }

    /* 3. Relocate Vector Table Offset Register (VTOR) */
    SCB_VTOR = app_address;

    /* 4. Extract application Reset Handler address (offset +4) */
    uint32_t reset_handler_addr = *(volatile uint32_t *)(app_address + 4U);
    pFunction app_entry = (pFunction)reset_handler_addr;

    /* 5. Set Main Stack Pointer (MSP) and branch to application */
    __asm volatile ("msr msp, %0" : : "r" (app_stack) : );
    __asm volatile ("cpsie i" : : : "memory");

    app_entry();

    /* Never reached */
    while (1);
}

15.4 Bare-Metal Flash Memory Driver: Sector Erasing and Word Programming

Embedded NOR Flash memory exhibits physical constraints fundamentally distinct from RAM: bits can only be cleared from 1 to 0 during a write operation. Transitioning bits back from 0 to 1 requires an erase operation, which can only be performed on entire multi-kilobyte flash sectors. Furthermore, the microcontroller Flash controller requires a strict cryptographic key unlock sequence to prevent spurious writes during power dips.


#include <stdint.h>

#define FLASH_BASE_ADDR     0x40023C00U
#define FLASH_KEYR          (*(volatile uint32_t *)(FLASH_BASE_ADDR + 0x04U))
#define FLASH_SR            (*(volatile uint32_t *)(FLASH_BASE_ADDR + 0x0CU))
#define FLASH_CR            (*(volatile uint32_t *)(FLASH_BASE_ADDR + 0x10U))

#define FLASH_KEY1          0x45670123U
#define FLASH_KEY2          0xCDEF89ABU
#define FLASH_SR_BSY        (1U << 16)
#define FLASH_CR_LOCK       (1U << 31)
#define FLASH_CR_PG         (1U << 0)
#define FLASH_CR_SER        (1U << 1)
#define FLASH_CR_STRT       (1U << 16)

void flash_unlock(void) {
    if (FLASH_CR & FLASH_CR_LOCK) {
        FLASH_KEYR = FLASH_KEY1;
        FLASH_KEYR = FLASH_KEY2;
    }
}

void flash_lock(void) {
    FLASH_CR |= FLASH_CR_LOCK;
}

void flash_wait_busy(void) {
    while (FLASH_SR & FLASH_SR_BSY);
}

void flash_erase_sector(uint8_t sector_num) {
    flash_wait_busy();
    flash_unlock();

    /* Configure Sector Erase and select sector (bits 3:6) */
    FLASH_CR &= ~(0x1FU << 3);
    FLASH_CR |= FLASH_CR_SER | ((uint32_t)sector_num << 3);
    FLASH_CR |= FLASH_CR_STRT;

    flash_wait_busy();
    FLASH_CR &= ~FLASH_CR_SER;
    flash_lock();
}

void flash_write_word(uint32_t address, uint32_t data) {
    flash_wait_busy();
    flash_unlock();

    /* Enable programming mode */
    FLASH_CR |= FLASH_CR_PG;

    /* Write 32-bit word */
    *(volatile uint32_t *)address = data;

    flash_wait_busy();
    FLASH_CR &= ~FLASH_CR_PG;
    flash_lock();
}

15.5 Hardware CRC32 Firmware Integrity Verification

Before launching a newly written application, firmware integrity must be verified mathematically to ensure transmission corruption or premature power loss during flashing does not execute invalid opcodes. Microcontrollers integrate a dedicated Hardware CRC Peripheral implementing the standard Ethernet / ISO 3309 CRC-32 polynomial (0x04C11DB7) to verify hundreds of kilobytes of Flash in under 5 milliseconds.


#include <stdint.h>
#include <stdbool.h>

#define CRC_BASE            0x40023000U
#define CRC_DR              (*(volatile uint32_t *)(CRC_BASE + 0x00U))
#define CRC_CR              (*(volatile uint32_t *)(CRC_BASE + 0x08U))
#define RCC_AHB1ENR         (*(volatile uint32_t *)(0x40023830U))

void crc_peripheral_init(void) {
    /* Enable CRC peripheral clock in RCC */
    RCC_AHB1ENR |= (1U << 12);
    /* Reset CRC computation unit */
    CRC_CR |= 1U;
}

uint32_t compute_firmware_crc(const uint32_t *p_data, uint32_t num_words) {
    CRC_CR |= 1U; /* Reset computation */
    for (uint32_t i = 0; i < num_words; i++) {
        CRC_DR = p_data[i];
    }
    return CRC_DR;
}

bool verify_application_integrity(uint32_t app_base_addr, uint32_t app_size_bytes, uint32_t expected_crc) {
    crc_peripheral_init();
    uint32_t num_words = app_size_bytes / 4U;
    uint32_t computed = compute_firmware_crc((const uint32_t *)app_base_addr, num_words);
    return (computed == expected_crc);
}

15.6 UART Packetized Device Firmware Upgrade (DFU) Protocol

When the bootloader detects an active update session, it runs a packetized transport protocol over UART, CAN, or USB. The protocol receives binary chunks, verifies frame checksums, writes words into Flash memory, and sends acknowledgments (ACK/NACK) back to the host programmer.


#include <stdint.h>
#include <stdbool.h>

#define DFU_PACKET_SIZE     128U
#define DFU_SOF             0x02U  /* Start of Frame */
#define DFU_ACK             0x06U  /* Acknowledge */
#define DFU_NACK            0x15U  /* Negative Acknowledge */

typedef struct {
    uint8_t  sof;
    uint16_t packet_id;
    uint8_t  payload[DFU_PACKET_SIZE];
    uint16_t checksum;
} __attribute__((packed)) DfuPacket_t;

extern void uart_send_byte(uint8_t b);
extern uint8_t uart_receive_byte(void);
extern void flash_erase_sector(uint8_t sec);
extern void flash_write_word(uint32_t addr, uint32_t data);

bool dfu_process_next_packet(uint32_t target_flash_addr) {
    DfuPacket_t packet;
    uint8_t *raw_ptr = (uint8_t *)&packet;

    /* Receive entire frame over UART */
    for (uint32_t i = 0; i < sizeof(DfuPacket_t); i++) {
        raw_ptr[i] = uart_receive_byte();
    }

    if (packet.sof != DFU_SOF) {
        uart_send_byte(DFU_NACK);
        return false;
    }

    /* Compute 16-bit additive checksum */
    uint16_t sum = 0;
    for (uint32_t i = 0; i < DFU_PACKET_SIZE; i++) {
        sum += packet.payload[i];
    }

    if (sum != packet.checksum) {
        uart_send_byte(DFU_NACK);
        return false;
    }

    /* Program verified 128 bytes (32 words) into Flash */
    uint32_t *p_data = (uint32_t *)packet.payload;
    for (uint32_t w = 0; w < (DFU_PACKET_SIZE / 4U); w++) {
        flash_write_word(target_flash_addr + (w * 4U), p_data[w]);
    }

    uart_send_byte(DFU_ACK);
    return true;
}

15.7 Non-Volatile A/B Dual-Bank Partitioning State Machine

To prevent bricking during over-the-air (OTA) updates, industrial systems implement an A/B Partitioning Scheme. While Slot A executes the active firmware, the network stack writes incoming packets into Slot B. Once verified, a persistent boot flag designates Slot B as pending trial. If Slot B fails to confirm successful startup within 3 reboots, the bootloader automatically rolls back to Slot A.


#include <stdint.h>
#include <stdbool.h>

#define NVM_METADATA_ADDR   0x08004000U
#define MAX_BOOT_ATTEMPTS   3U

typedef enum {
    SLOT_A = 0,
    SLOT_B = 1
} ActiveSlot_t;

typedef struct {
    uint32_t magic_header;       /* 0x55AA55AA */
    ActiveSlot_t active_slot;
    uint32_t boot_attempts;
    uint32_t slot_a_crc;
    uint32_t slot_b_crc;
    uint32_t slot_a_size;
    uint32_t slot_b_size;
} BootMetadata_t;

ActiveSlot_t bootloader_select_slot(BootMetadata_t *meta) {
    if (meta->magic_header != 0x55AA55AAU) {
        /* Default fallback */
        return SLOT_A;
    }

    if (meta->boot_attempts >= MAX_BOOT_ATTEMPTS) {
        /* Candidate failed to confirm operational status; rollback */
        meta->active_slot = (meta->active_slot == SLOT_A) ? SLOT_B : SLOT_A;
        meta->boot_attempts = 0;
        /* Note: Write updated metadata to NVM sector here */
    } else {
        meta->boot_attempts++;
    }

    return meta->active_slot;
}

  • To reduce power consumption during programming

Floating-gate NOR flash cells are charged to represent 0 and discharged to represent 1. Write operations only inject charge (1->0); removing charge (0->1) requires high-voltage sector bulk erasing.
3. What are the first two 32-bit words stored at the base address of any ARM Cortex-M application binary?
  • Initial Main Stack Pointer (MSP) value and Reset Handler function address
  • CRC32 checksum and firmware version string
  • UART baud rate register and clock divider settings
  • Heap pointer base and FreeRTOS task count
The ARM Cortex-M hardware vector table specification mandates that word 0 (offset 0x00) is loaded into the MSP register and word 1 (offset 0x04) is loaded into the Program Counter (PC).
4. In an A/B dual-partition update scheme, what is the purpose of the 'boot_attempts' counter in the metadata sector?
  • To limit how many times the user can plug in USB devices
  • To detect an application crash loop and automatically roll back to the previously operational image
  • To calculate the CPU clock cycle count
  • To verify the serial number of the microcontroller
If a newly flashed candidate image crashes or triggers a watchdog reset before marking itself as 'healthy', the boot_attempts counter increments. Exceeding the threshold triggers an automatic rollback to the known-good partition.
5. Which Intel HEX record type defines the upper 16 bits of a 32-bit linear memory address on ARM Cortex-M microcontrollers?
  • Record Type 0x00 (Data)
  • Record Type 0x01 (EOF)
  • Record Type 0x04 (Extended Linear Address Record)
  • Record Type 0x02 (Extended Segment Record)
Intel HEX record type 04 supplies the upper 16 address bits (base address), enabling addressing across the entire 4 GB 32-bit address space.
6. Why should interrupts be globally disabled before jumping from a bootloader to an application?
  • To prevent an in-flight peripheral interrupt from executing an ISR in the wrong memory context during vector table transition
  • To prevent flash memory from discharging
  • Because Cortex-M cores do not support interrupts in applications
  • To preserve battery power during the jump
If an interrupt fires during the transition between the bootloader stack pointer configuration and the application VTOR update, the core will branch using indeterminate vector table pointers, causing an immediate HardFault.
7. What is the primary vulnerability of updating firmware in-place in a single flash slot without an A/B dual bank or golden image?
  • SRAM becomes too fast for CPU execution
  • A sudden power outage or connection drop mid-write leaves the device permanently unbootable (bricked)
  • The serial baud rate doubles automatically
  • The compiler optimization flag drops from -O2 to -O0
Single-slot in-place updating erases the running application before writing the new image. If power fails mid-erase, no valid application exists on flash, requiring physical SWD/JTAG intervention.
8. How does the hardware CRC32 engine compare in throughput to a software bitwise CRC calculation?
  • Hardware CRC executes in 1 clock cycle per 32-bit word, outperforming software loops by 10x to 50x
  • Hardware CRC is slower because it requires network access
  • Hardware CRC consumes more Flash memory than software lookup tables
  • They operate at identical speeds
The integrated hardware CRC engine computes polynomial division in combinational hardware at 1 word per clock cycle, verifying multi-hundred-kilobyte images in milliseconds.
9. What does the Thumb instruction bit (bit 0) in an ARM function address indicate?
  • Whether the core operates in 16/32-bit Thumb state (must be 1 for Cortex-M processors)
  • Whether the memory is cached
  • Whether the function was compiled with -O3
  • Whether floating point hardware is present
Cortex-M microcontrollers exclusively execute the Thumb instruction set. Bit 0 of function pointer addresses must be set to 1; branching to an even address clears EPSR.T and triggers a UsageFault.
10. In automotive diagnostics, which protocol standard governs firmware reprogramming over the CAN bus?
  • ISO 14229 Unified Diagnostic Services (UDS)
  • Bluetooth SIG GAP Spec
  • IEEE 802.11 Wi-Fi
  • I2C Fast Mode Plus
ISO 14229 (UDS) specifies the diagnostic services (such as 0x34 RequestDownload, 0x36 TransferData, and 0x37 RequestTransferExit) used by automotive OEMs to flash ECUs over CAN.
