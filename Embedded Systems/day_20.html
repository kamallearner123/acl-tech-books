20.1 ARM CoreSight Hardware Debug Architecture and Debug Probes

In complex embedded systems, relying solely on printf() debugging is counterproductive: serial print statements add hundreds of microseconds of latency, altering thread scheduling, masking race conditions, and altering real-time interrupt timings (the Heisenbug phenomenon). Professional firmware engineers interface directly with silicon-level debugging hardware via the ARM CoreSight Debug Architecture.

The CoreSight framework decouples the external physical debug probe from the internal CPU core using a standard Debug Access Port (DAP). The DAP bridges external serial protocols (JTAG or SWD) to the internal high-speed system bus (AHB-AP), allowing the debugger to read and write registers and SRAM non-intrusively while the core is running at full speed.

Figure 20.0-1: ARM CoreSight Silicon Debug Architecture Block Diagram
Figure Parameters Explained:
  • Debug Access Port (DAP): Silicon interface translating external serial clock/data frames into internal AHB-Lite bus transactions.
  • Flash Patch & Breakpoint (FPB): Hardware comparators allowing setting hardware breakpoints in non-volatile Flash without modifying binary code.
  • Data Watchpoint & Trace (DWT): Monitors memory addresses and triggers execution halts when a variable is written or read.
  • Instrumentation Trace (ITM): Non-intrusive, ultra-high-speed hardware trace unit outputting printf data over a single SWO pin.

20.2 JTAG (IEEE 1149.1) vs. Serial Wire Debug (SWD)

Historically, microprocessors used the 5-wire JTAG (Joint Test Action Group / IEEE 1149.1) boundary-scan interface. While powerful for board-level continuity testing and daisy-chaining multiple chips, JTAG consumes precious microcontroller pins.

ARM introduced Serial Wire Debug (SWD), a bi-directional, high-speed 2-wire protocol replacing JTAG. Operating over a clock line (SWDCLK) and a bidirectional open-drain data line (SWDIO) with parity checking, SWD achieves speeds up to 10 MHz while freeing 3 physical pins for application peripherals. An optional single-wire output (SWO) transmits real-time telemetry.

Figure 20.0-2: Hardware Pinout Comparison: 5-Wire JTAG vs 2-Wire SWD + SWO
Figure Parameters Explained:
  • SWDIO (Bidirectional Data): Synchronous data transfer line with turnaround (TRN) cycles for bi-directional read/write transactions.
  • SWDCLK (Clock Input): Host-driven clock line driving the internal DAP state machine at rates up to 10-25 MHz.
  • SWO (Serial Wire Output): Asynchronous Manchester or UART packet stream transmitting ITM hardware trace data to the host.
  • JTAG Daisy-Chaining: JTAG connects TDI-to-TDO across multiple ICs on a PCB; SWD targets a single chip point-to-point.

20.3 Non-Intrusive Real-Time Tracing with ITM and SWO

The Instrumentation Trace Macrocell (ITM) provides a hardware-accelerated alternative to UART printf(). The firmware writes a 32-bit word directly to an ITM Stimulus Port register (ITM->PORT[0]). The internal CoreSight hardware serializes the word out the dedicated SWO (Serial Wire Output) pin in just 2 CPU clock cycles, consuming zero software execution overhead and zero CPU wait states.


#include <stdint.h>
#include <stdio.h>

#define ITM_PORT0_U32       (*(volatile uint32_t *)0xE0000000U)
#define ITM_PORT0_U8        (*(volatile uint8_t  *)0xE0000000U)
#define ITM_TER             (*(volatile uint32_t *)0xE0000E00U)
#define ITM_TCR             (*(volatile uint32_t *)0xE0000E80U)
#define DEMCR               (*(volatile uint32_t *)0xE000EDFCU)

#define DEMCR_TRCENA        (1U << 24)
#define ITM_TCR_ITMENA      (1U << 0)

void itm_trace_init(void) {
    /* 1. Enable Global Core Trace in Debug Exception and Monitor Control Register */
    DEMCR |= DEMCR_TRCENA;

    /* 2. Enable ITM Core */
    ITM_TCR |= ITM_TCR_ITMENA;

    /* 3. Enable Stimulus Port 0 in Trace Enable Register (TER) */
    ITM_TER |= (1U << 0);
}

void itm_send_char(char c) {
    /* Verify ITM is enabled and Port 0 is ready */
    if ((DEMCR & DEMCR_TRCENA) && (ITM_TCR & ITM_TCR_ITMENA) && (ITM_TER & (1U << 0))) {
        /* Wait until Stimulus Port 0 FIFO is not full */
        while (ITM_PORT0_U32 == 0U);
        /* Write byte to Port 0 hardware register */
        ITM_PORT0_U8 = (uint8_t)c;
    }
}

/* Retarget standard C library _write() syscall to ITM */
int _write(int file, char *ptr, int len) {
    for (int i = 0; i < len; i++) {
        itm_send_char(ptr[i]);
    }
    return len;
}

20.4 ARM Cortex-M Fault Architecture and Register Decoding

When an illegal memory access, unaligned load, divide-by-zero, or execution of an invalid opcode occurs, the Cortex-M processor triggers an exception. If sub-faults (MemManage, BusFault, UsageFault) are not explicitly enabled in the System Handler Control and State Register (SHCSR), they automatically escalate into a catastrophic HardFault.

Figure 20.0-3: ARM Cortex-M Fault Escalation and Status Register Decoding
Figure Parameters Explained:
  • MemManage Fault: Triggered by Memory Protection Unit (MPU) permission violations or executing from non-executable RAM.
  • BusFault: Triggered by physical bus errors (AHB error response, reading unmapped peripheral addresses).
  • UsageFault: Triggered by software defects: divide-by-zero, unaligned access, or executing undefined 16/32-bit instructions.
  • CFSR Register (0xE000ED28): 32-bit register combining MMFSR (bits 0:7), BFSR (bits 8:15), and UFSR (bits 16:31).

#include <stdint.h>
#include <stdio.h>

#define CFSR                (*(volatile uint32_t *)0xE000ED28U)
#define HFSR                (*(volatile uint32_t *)0xE000ED2CU)
#define MMFAR               (*(volatile uint32_t *)0xE000ED34U)
#define BFAR                (*(volatile uint32_t *)0xE000ED38U)

typedef struct {
    uint32_t r0;
    uint32_t r1;
    uint32_t r2;
    uint32_t r3;
    uint32_t r12;
    uint32_t lr;
    uint32_t pc;
    uint32_t psr;
} ExceptionStackFrame_t;

/* C diagnosis function called by assembly trampoline */
void hardfault_diagnose_c(ExceptionStackFrame_t *frame, uint32_t lr_val) {
    uint32_t cfsr_val = CFSR;
    uint32_t hfsr_val = HFSR;

    printf("
================ HARDFAULT EXCEPTION DETECTED ================
");
    printf("Faulting PC (Instruction): 0x%08lX
", frame->pc);
    printf("Caller LR (Return Address):0x%08lX
", frame->lr);
    printf("Stacked R0: 0x%08lX  R1: 0x%08lX
", frame->r0, frame->r1);
    printf("Stacked R2: 0x%08lX  R3: 0x%08lX
", frame->r2, frame->r3);
    printf("Stacked R12:0x%08lX  PSR:0x%08lX
", frame->r12, frame->psr);
    printf("EXC_RETURN (LR at fault):  0x%08lX
", lr_val);

    printf("CFSR Status: 0x%08lX  HFSR: 0x%08lX
", cfsr_val, hfsr_val);

    /* Check for BusFault Address Valid */
    if (cfsr_val & (1U << 15)) { /* BFARVALID bit */
        printf("BusFault Address (BFAR):   0x%08lX
", BFAR);
    }
    /* Check for MemManage Address Valid */
    if (cfsr_val & (1U << 7)) {  /* MMARVALID bit */
        printf("MemManage Address (MMFAR): 0x%08lX
", MMFAR);
    }
    /* Check for UsageFault bits */
    if (cfsr_val & (1U << 25)) printf("Fault Cause: DIVIDE BY ZERO
");
    if (cfsr_val & (1U << 24)) printf("Fault Cause: UNALIGNED ACCESS
");
    if (cfsr_val & (1U << 18)) printf("Fault Cause: INVALID STATE (Thumb bit cleared)
");
    if (cfsr_val & (1U << 16)) printf("Fault Cause: UNDEFINED INSTRUCTION
");

    /* Hang in infinite loop for JTAG debugger attachment */
    while (1);
}

/* Assembly entry trampoline: extracts active stack pointer (MSP or PSP) */
__attribute__((naked)) void HardFault_Handler(void) {
    __asm volatile (
        "tst lr, #4                
" /* Check bit 2 of EXC_RETURN */
        "ite eq                    
"
        "mrseq r0, msp             
" /* 0 = Main Stack Pointer */
        "mrsne r0, psp             
" /* 1 = Process Stack Pointer */
        "mov r1, lr                
" /* Pass EXC_RETURN as 2nd arg */
        "b hardfault_diagnose_c    
"
    );
}

20.5 OpenOCD and GDB Remote Scripting Automation

Modern embedded development integrates automated hardware debugging into continuous test systems. Using OpenOCD (Open On-Chip Debugger) coupled with the GNU Debugger (arm-none-eabi-gdb), engineers can automate flashing, set software and hardware breakpoints, inspect FreeRTOS task control blocks (TCBs), and evaluate memory without clicking through an IDE.


# GDB automation script: debug_session.gdb
# Run with: arm-none-eabi-gdb -x debug_session.gdb target_firmware.elf

target extended-remote localhost:3333
monitor reset halt

# Load symbols and flash binary
load

# Set hardware breakpoints on critical handlers
break main
break HardFault_Handler
break vApplicationStackOverflowHook

# Run until main()
continue

print "=== Target Initialized: Reading Clock Configuration ==="
x/4xw 0x40021000

# Inspect FreeRTOS task scheduler state
break vSensorTask
continue

print "=== Current Task Registers ==="
info registers
print "=== Backtrace ==="
bt

# Disconnect and let MCU run freely
detach
quit

20.6 Logic Analyzer Protocol Decoding (UART, SPI, I2C, CAN)

When firmware fails due to bus arbitration collisions, signal integrity ringing, or clock phase misconfigurations (CPOL/CPHA), software debuggers are blind. A hardware Logic Analyzer (e.g., Saleae Logic or Sigrok-compatible FX2) samples physical PCB traces at tens of megasamples per second, displaying protocol decodes directly synchronized to firmware execution pins.


import subprocess

def capture_and_decode_i2c(sample_rate_mhz=24, capture_time_s=2):
    """
    Automates sigrok-cli to capture I2C bus transactions and decode packets.
    Channel 0: SCL, Channel 1: SDA
    """
    cmd = [
        "sigrok-cli",
        "-d", "fx2lafw",
        "--config", f"samplerate={sample_rate_mhz}m",
        "--time", f"{capture_time_s}s",
        "-C", "0=SCL,1=SDA",
        "-P", "i2c:scl=SCL:sda=SDA",
        "-A", "i2c=address-read:address-write:data-read:data-write"
    ]

    print(f"Executing hardware logic capture: {' '.join(cmd)}")
    result = subprocess.run(cmd, capture_output=True, text=True)

    print("
--- Decoded I2C Protocol Output ---")
    for line in result.stdout.splitlines()[:20]:
        print(line)

    return result.returncode

1. Why is the ARM Instrumentation Trace Macrocell (ITM) vastly superior to UART printf() for debugging real-time firmware?

UART printf blocks CPU execution for hundreds of microseconds per string. Writing to ITM Stimulus Port 0 takes a single cycle, allowing non-intrusive logging without altering thread scheduling.

By default at reset, specific sub-faults (UsageFault, BusFault, MemManage) are disabled. Any sub-fault that fires immediately escalates to the HardFault_Handler.

  • The Link Register (LR)
  • The SysTick Current Value Register
Upon an exception, Cortex-M hardware pushes R0-R3, R12, LR, PC, and xPSR onto the active stack. The stacked PC points directly to the offending machine instruction.
5. What does the BFARVALID bit (bit 15) in the CFSR register signify?
  • The BusFault Address Register (BFAR) contains the exact physical address that triggered the bus error
  • The battery voltage is within valid limits
  • The Flash memory has completed programming
  • The breakpoint unit is currently disabled
If a precise BusFault occurs, the core writes the faulting address to BFAR and sets BFARVALID to 1. If BFARVALID is 0, the fault was imprecise (e.g., buffered write) and BFAR is invalid.
6. What is the role of OpenOCD in an embedded development environment?
  • It serves as a GDB server bridging the GDB remote protocol over TCP/IP to physical hardware debug probes (ST-Link, J-Link, FTDI)
  • It is a graphical text editor for writing C code
  • It is an optimizing cross-compiler replacing GCC
  • It is a real-time operating system
OpenOCD controls JTAG/SWD adapters, executes target initialization scripts, and exposes a GDB server on localhost:3333 so standard GDB can debug physical silicon.
7. What is the difference between a hardware breakpoint and a software breakpoint on ARM Cortex-M?
  • Hardware breakpoints use silicon comparator registers (FPB) and work in Flash; software breakpoints replace an instruction with a BKPT opcode in RAM
  • Hardware breakpoints consume battery power, software breakpoints do not
  • Software breakpoints can only be set from inside an ISR
  • Hardware breakpoints are only supported on 64-bit cores
You cannot easily patch an instruction in read-only Flash at runtime without an erase cycle. CoreSight Flash Patch and Breakpoint (FPB) comparators match PC addresses without modifying Flash.
8. Which tool is used to capture and decode multi-channel digital logic signals (e.g. SPI clock, MOSI, MISO, CS) synchronously?
  • A Digital Logic Analyzer
  • A digital multimeter
  • A function generator
  • A thermal imaging camera
Logic analyzers sample multiple digital channels at high sample rates, reconstructing waveforms and executing protocol decoding (UART, I2C, SPI, CAN) to diagnose bus-level timing faults.
9. What does an EXC_RETURN value of 0xFFFFFFFD in the Link Register (LR) inside an exception handler indicate?
  • The core was executing in Thread mode using the Process Stack Pointer (PSP) before the exception occurred
  • The microcontroller must immediately reboot
  • The floating-point unit was disabled
  • The core was running in Handler mode on MSP
ARM EXC_RETURN bit 2 indicates which stack held the exception frame: bit 2=1 indicates PSP (typical for FreeRTOS tasks), bit 2=0 indicates MSP (typical for bare-metal or ISRs).
10. What causes an 'imprecise' BusFault in ARM Cortex-M processors with write buffers?
  • A write buffer posts an asynchronous memory write to a peripheral bus; the bus returns an error several clock cycles after the CPU has moved on to subsequent instructions
  • A loose electrical wire on the PCB
  • The ADC clock frequency is drifting with temperature
  • A syntax error in the C source code
To maintain speed, Cortex-M writes to peripherals through a write buffer. If the peripheral returns an AHB error, the core has already advanced. The stacked PC points to a later instruction.
