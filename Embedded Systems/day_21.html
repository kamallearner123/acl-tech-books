21.1 The Embedded Testing Pyramid: Host Unit Tests, Mocks, and HIL

Developing embedded software exclusively on physical target hardware is a major bottleneck: physical boards are expensive, Flashing chips takes seconds per iteration, hardware components fail unpredictably, and setting up physical failure edge-cases (like an overheating lithium battery or a broken CAN bus) is dangerous or impossible. Leading embedded engineering organizations adopt the Embedded Test Pyramid:

  • Host-Based Unit Testing (Base of Pyramid, 80%): Pure C application and driver logic compiled natively for the host workstation (x86-64 Linux/macOS) using gcc/clang, executing thousands of automated unit tests in under 2 seconds.
  • Integration & Subsystem Testing (15%): Firmware components linked with software emulators (QEMU or native stubs) validating RTOS inter-task communication.
  • Hardware-in-the-Loop (HIL) Testing (Apex, 5%): Production firmware deployed onto real physical Device Under Test (DUT) hardware, connected to automated test benches simulating sensor voltages, load currents, and bus traffic.

Figure 21.0-1: Host-Based Native C Unit Testing vs Hardware-in-the-Loop (HIL)
Figure Parameters Explained:
  • Host Native Execution: C source files compile directly with host GCC; hardware registers are mocked by C structs and fake functions.
  • Deterministic Execution: Eliminates serial baud rate delays, probe dropouts, and flashing flash-wear during rapid unit test cycles.
  • Hardware-in-the-Loop (HIL): Validates real electrical impedances, crystal oscillator startup jitter, and silicon interrupt latency.
  • Continuous Integration (CI): Host unit tests run automatically inside GitHub Actions or GitLab CI runners upon every git commit.

21.2 The Unity Unit Testing Framework for Embedded C

The standard, industry-accepted unit test framework for embedded C is Unity (created by ThrowTheSwitch / Ceedling). Designed specifically for resource-constrained architectures, Unity requires zero dynamic memory allocation, compiles seamlessly with both native host and cross-compilers, and provides clear, descriptive assertion macros.

Figure 21.0-2: Embedded Test-Driven Development (TDD) Cycle
Figure Parameters Explained:
  • Red Phase (Failing Test): Forces specification of API contracts and error return codes before writing production code.
  • Green Phase (Minimal Code): Focuses strictly on passing tests without premature over-engineering.
  • Refactor Phase: Permits fearless restructuring of code because automated tests catch any unintended regression.

21.3 Decoupling Hardware Registers with Fake Function Framework (fff)

To unit test hardware drivers without silicon, we use Stubs and Mocks. The Fake Function Framework (fff) is a lightweight, single-header C mocking framework that creates mock functions for microcontroller peripheral calls (such as i2c_write() or flash_erase()), recording call histories, arguments, and return values.


#include <stdint.h>
#include <stdbool.h>
#include "unity.h"
#include "fff.h"

DEFINE_FFF_GLOBALS;

/* Define mock fakes for low-level Flash hardware drivers */
FAKE_VOID_FUNC(mock_flash_erase_sector, uint8_t);
FAKE_VOID_FUNC(mock_flash_write_word, uint32_t, uint32_t);
FAKE_VALUE_FUNC(uint32_t, mock_flash_read_word, uint32_t);

/* Production configuration manager under test */
typedef struct {
    uint16_t node_id;
    uint32_t baud_rate;
} Config_t;

bool config_save(const Config_t *cfg) {
    if (cfg == NULL || cfg->baud_rate == 0) {
        return false;
    }
    mock_flash_erase_sector(7);
    mock_flash_write_word(0x08060000U, (uint32_t)cfg->node_id);
    mock_flash_write_word(0x08060004U, cfg->baud_rate);
    return true;
}

/* Unity Setup and Teardown */
void setUp(void) {
    RESET_FAKE(mock_flash_erase_sector);
    RESET_FAKE(mock_flash_write_word);
    RESET_FAKE(mock_flash_read_word);
}

void tearDown(void) {}

/* Unit Test Cases */
void test_config_save_should_reject_null_pointer(void) {
    bool result = config_save(NULL);
    TEST_ASSERT_FALSE(result);
    TEST_ASSERT_EQUAL_INT(0, mock_flash_erase_sector_fake.call_count);
}

void test_config_save_should_erase_sector_and_write_words(void) {
    Config_t cfg = {.node_id = 42, .baud_rate = 115200};

    bool result = config_save(&cfg);

    TEST_ASSERT_TRUE(result);
    /* Verify flash sector 7 was erased once */
    TEST_ASSERT_EQUAL_INT(1, mock_flash_erase_sector_fake.call_count);
    TEST_ASSERT_EQUAL_UINT8(7, mock_flash_erase_sector_fake.arg0_val);

    /* Verify two 32-bit words were written to correct addresses */
    TEST_ASSERT_EQUAL_INT(2, mock_flash_write_word_fake.call_count);
    TEST_ASSERT_EQUAL_HEX32(0x08060000U, mock_flash_write_word_fake.arg0_history[0]);
    TEST_ASSERT_EQUAL_HEX32(42, mock_flash_write_word_fake.arg1_history[0]);
    TEST_ASSERT_EQUAL_HEX32(0x08060004U, mock_flash_write_word_fake.arg0_history[1]);
    TEST_ASSERT_EQUAL_HEX32(115200, mock_flash_write_word_fake.arg1_history[1]);
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_config_save_should_reject_null_pointer);
    RUN_TEST(test_config_save_should_erase_sector_and_write_words);
    return UNITY_END();
}

21.4 Test-Driven Development (TDD) of a Sensor Driver

In TDD, we write the unit test before implementing the driver logic. For a BMP280 temperature sensor, we define the expected conversion formulas and mock the underlying I2C register transaction. If the hardware returns an error code, the driver must handle it gracefully.


#include "unity.h"
#include "fff.h"

DEFINE_FFF_GLOBALS;

FAKE_VALUE_FUNC(int, mock_i2c_read_bytes, uint8_t, uint8_t, uint8_t *, uint16_t);

/* Function Under Test prototype */
int bmp280_read_temperature(int32_t *p_temp_centidegrees);

/* Custom fake implementation to simulate realistic sensor register data */
int fake_i2c_read_success(uint8_t dev_addr, uint8_t reg_addr, uint8_t *data, uint16_t len) {
    if (len >= 3) {
        /* Return raw sensor bytes for 25.0 C */
        data[0] = 0x80;
        data[1] = 0x00;
        data[2] = 0x00;
    }
    return 0; /* 0 = Success */
}

void test_sensor_should_return_error_if_i2c_bus_nacks(void) {
    mock_i2c_read_bytes_fake.return_val = -1; /* Bus error */
    int32_t temp = 0;

    int status = bmp280_read_temperature(&temp);

    TEST_ASSERT_EQUAL_INT(-1, status);
}

void test_sensor_should_calculate_correct_temperature(void) {
    mock_i2c_read_bytes_fake.custom_fake = fake_i2c_read_success;
    int32_t temp = 0;

    int status = bmp280_read_temperature(&temp);

    TEST_ASSERT_EQUAL_INT(0, status);
    TEST_ASSERT_EQUAL_INT(2500, temp); /* 25.00 deg C */
}

21.5 Host-Based Build Makefile with Code Coverage (gcov / lcov)

To verify test thoroughness, compilers provide Code Coverage Profiling using gcov. By passing -fprofile-arcs -ftest-coverage during compilation, GCC instruments the executable to record every branch and statement executed, producing visual HTML coverage reports via lcov.


# Host Testing Makefile: run natively on Linux/macOS
CC = gcc
CFLAGS = -Wall -Wextra -std=c99 -g -O0 --coverage -Iinclude -Iunity
LDFLAGS = --coverage

SRC_UNDER_TEST = src/config_mgr.c src/sensor_driver.c
TEST_SRCS = tests/test_runner.c tests/test_config.c unity/unity.c

all: run_tests coverage_report

run_tests: $(SRC_UNDER_TEST) $(TEST_SRCS)
	@mkdir -p build
	$(CC) $(CFLAGS) -o build/test_runner $^ $(LDFLAGS)
	@echo "=== Executing Host Unit Tests ==="
	./build/test_runner

coverage_report: run_tests
	@echo "=== Generating Code Coverage Report ==="
	lcov --capture --directory . --output-file build/coverage.info
	lcov --remove build/coverage.info '/usr/*' '*/unity/*' --output-file build/coverage_filtered.info
	genhtml build/coverage_filtered.info --output-directory build/coverage_html
	@echo "Coverage HTML report generated at: build/coverage_html/index.html"

clean:
	rm -rf build *.gcda *.gcno

21.6 Hardware-in-the-Loop (HIL) Automated Test Framework

At the apex of the testing pyramid, physical firmware is validated using an automated Hardware-in-the-Loop (HIL) harness. A host workstation running Python scripts commands external hardware (power supplies, waveform generators, CAN-USB adapters) to stimulate the real microcontroller and verify expected GPIO, UART, and CAN responses.


import time
import serial
import pytest

class HilFixture:
    def __init__(self, port="/dev/ttyUSB0", baud=115200):
        self.ser = serial.Serial(port, baud, timeout=2.0)

    def reset_dut(self):
        # Pulse DTR pin to reset STM32 via hardware reset circuit
        self.ser.dtr = True
        time.sleep(0.1)
        self.ser.dtr = False
        time.sleep(0.5)

    def send_command(self, cmd_str):
        self.ser.write((cmd_str + "
").encode("utf-8"))
        return self.ser.readline().decode("utf-8").strip()

@pytest.fixture(scope="module")
def dut():
    fixture = HilFixture()
    fixture.reset_dut()
    yield fixture
    fixture.ser.close()

def test_hil_dut_boot_banner(dut):
    """Verify device emits expected boot string within 1 second of reset"""
    line = dut.ser.readline().decode("utf-8").strip()
    assert "Sensor Hub Ready" in line

def test_hil_cli_ping_pong(dut):
    """Verify serial command shell responds correctly"""
    response = dut.send_command("ping")
    assert response == "PONG"

1. What is the primary advantage of host-based unit testing (running embedded C on x86 PC) over on-target testing?
  • Tests execute thousands of times faster without flash-wear or hardware dependency, enabling instant feedback during development
  • Host testing tests physical pin soldering quality
  • Host testing eliminates the need for compiling
  • Host testing measures actual battery current draw
Compiling and executing natively on the development workstation runs hundreds of tests in milliseconds, isolating pure algorithmic bugs long before hardware is available.
2. What is a 'Mock' in the context of embedded software testing?
  • A simulated function that replaces a hardware driver, recording how many times it was called and with which arguments, while returning controlled values
  • A software bug that laughs at the developer
  • A physical breakout board with LEDs
  • A compiler optimization flag that strips comments
Mocks (like those created by CMock or FFF) fake out real hardware interfaces (like SPI, I2C, or Flash), allowing developers to test higher-level logic against both nominal and faulted hardware responses.
3. What are the three distinct phases of Test-Driven Development (TDD)?
  • Red (write failing test) -> Green (write minimal code to pass) -> Refactor (clean up and optimize)
  • Compile -> Flash -> Debug
  • Plan -> Procrastinate -> Panic
  • Code -> Ship -> Patch
TDD follows the famous Red-Green-Refactor rhythm: first write a test that fails (proving the test is valid), then implement the smallest amount of code to make it green, then refactor safely.
4. Which tool is commonly used to generate visual HTML code coverage reports from gcov instrumented test binaries?
  • lcov (genhtml)
  • Wireshark
  • Valgrind
  • Photoshop
lcov aggregates execution counters produced by gcov and invokes genhtml to create color-coded HTML reports detailing line, branch, and function coverage percentages.
5. What is a Hardware-in-the-Loop (HIL) test system?
  • A test bench where the real physical microcontroller hardware is connected to automated test equipment that simulates physical sensors and loads
  • A program with an infinite while(1) loop
  • An automated JTAG cable manufacturing machine
  • A ring buffer stored in internal SRAM
HIL testing mounts the production ECU on a test rack with automated DACs, relays, and communication adapters simulating the vehicle or industrial machine around it.
6. Why is 100% statement coverage insufficient to guarantee software correctness?
  • Because executing every line does not test all combinations of conditions, boundary edge cases, or multi-branch decisions
  • Because statement coverage only works on assembly language
  • Because statement coverage causes the microcontroller to reset
  • Because statement coverage cannot detect syntax errors
A line like 'if (x > 0 && y > 0)' can have 100% statement coverage simply by testing x=1, y=1, leaving the behavior when x=0 or y=0 completely unverified. Branch and MC/DC coverage are required.
7. What does the Unity assertion TEST_ASSERT_EQUAL_HEX32(expected, actual) do when a test fails?
  • It prints the test file name, line number, and the exact hexadecimal difference between expected and actual values before halting the test
  • It automatically fixes the code error
  • It converts the test to Python
  • It flashes an error code on an LED
Unity assertion macros report human-readable failure diagnostics including file names, line numbers, and hexadecimal representations of mismatches, speeding up debugging.
8. How does the Fake Function Framework (fff) help in testing error paths that rarely occur in physical hardware?
  • It allows the test developer to configure the mock to return specific error codes (like bus timeouts or CRC faults) on demand to verify recovery logic
  • It automatically generates physical electrical noise on the PCB
  • It overrides the microcontroller crystal oscillator
  • It re-wires the circuit board traces via software
Simulating a hardware flash write error or an I2C NACK on physical hardware is difficult. With fff, setting 'mock_i2c_read_fake.return_val = -1;' instantly tests error handling.
9. In a continuous integration (CI) pipeline, why should host unit tests run before on-target or HIL tests?
  • Host unit tests run in seconds and catch 90% of regressions immediately, preventing costly and time-consuming HIL test runs on broken builds
  • Because host tests consume less network bandwidth
  • Because CI servers are not allowed to connect to physical USB devices
  • Because host tests can only be run once per day
Fast feedback is the core principle of CI: failing fast on host unit tests within 5 seconds saves engineering time and preserves expensive HIL test rack availability.
10. What is 'Mutation Testing' in embedded software verification?
  • A technique that deliberately injects artificial faults (e.g. changing > to <, or + to -) into source code to verify that the test suite detects and catches them
  • Testing biological sensors with bacterial cultures
  • Testing how microcontrollers survive cosmic radiation
  • Randomly overclocking the CPU to test silicon tolerances
Mutation testing tests the quality of your tests: if a mutated code change survives your entire test suite without triggering a test failure, your test coverage has blind spots.
