16.1 Industrial Multi-Tasking RTOS System Architecture

Modern embedded IoT gateways, automotive sensor nodes, and avionics flight computers require multi-rate, concurrent processing with microsecond determinism. Combining independent peripherals—such as I2C barometric sensors, ADC DMA converters, CAN-bus automotive transceivers, and CLI serial consoles—into a single bare-metal loop creates fragile coupling where any slow bus transaction stalls critical control loops.

By leveraging FreeRTOS, we partition system responsibilities into six decoupled, priority-driven tasks communicating strictly through thread-safe FreeRTOS Queues and protected by binary/mutex semaphores. A central Health Watchdog Monitor continuously tracks task heartbeats, enforcing system reliability and triggering graceful recovery if any thread deadlocks.

Figure 16.0-1: Industrial Multi-Tasking RTOS Sensor Hub Architecture
Figure Parameters Explained:
  • Sensor Task (Priority 4): Acquires I2C pressure/temperature and ADC DMA thermistor data every 100 ms; publishes to sensor_queue.
  • Control Task (Priority 4): Consumes sensor packets and computes PID heater control commands driving high-resolution PWM outputs.
  • CAN Telemetry Task (Priority 3): Packs sensor metrics into standard 8-byte CAN frames (ID 0x301) and pushes them onto the automotive bus.
  • CLI Command Task (Priority 2): Parses incoming ASCII commands over UART; accesses system parameters protected by a shared Mutex.
  • Health Watchdog (Priority 5): Highest priority supervisor; verifies all task heartbeat flags before resetting hardware Independent Watchdog (IWDG).

16.2 Task Configuration Table and Thread Allocation

In safety-conscious firmware development, task definitions, stack depths, and priorities should never be scattered across ad-hoc code blocks. Instead, they are consolidated into a centralized Task Configuration Descriptor Table. This allows compile-time stack allocation audits and systematic priority tuning to prevent priority inversion.


#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"

typedef struct {
    const char *task_name;
    TaskFunction_t task_func;
    configSTACK_DEPTH_TYPE stack_words;
    UBaseType_t priority;
    TaskHandle_t *task_handle;
} TaskDescriptor_t;

/* Task function declarations */
extern void vSensorTask(void *pvParams);
extern void vControlTask(void *pvParams);
extern void vCanTxTask(void *pvParams);
extern void vCliTask(void *pvParams);
extern void vHealthTask(void *pvParams);

/* Task handles */
TaskHandle_t hSensorTask;
TaskHandle_t hControlTask;
TaskHandle_t hCanTxTask;
TaskHandle_t hCliTask;
TaskHandle_t hHealthTask;

static const TaskDescriptor_t g_task_table[] = {
    {"HealthMon", vHealthTask,  configMINIMAL_STACK_SIZE * 2, 5, &hHealthTask},
    {"SensorAcq", vSensorTask,  configMINIMAL_STACK_SIZE * 3, 4, &hSensorTask},
    {"ControlPID",vControlTask, configMINIMAL_STACK_SIZE * 2, 4, &hControlTask},
    {"CanTelem",  vCanTxTask,   configMINIMAL_STACK_SIZE * 2, 3, &hCanTxTask},
    {"SerialCLI", vCliTask,     configMINIMAL_STACK_SIZE * 4, 2, &hCliTask},
};

#define NUM_TASKS (sizeof(g_task_table) / sizeof(TaskDescriptor_t))

void system_tasks_init(void) {
    for (size_t i = 0; i < NUM_TASKS; i++) {
        BaseType_t status = xTaskCreate(
            g_task_table[i].task_func,
            g_task_table[i].task_name,
            g_task_table[i].stack_words,
            NULL,
            g_task_table[i].priority,
            g_task_table[i].task_handle
        );
        configASSERT(status == pdPASS);
    }
}

16.3 High-Rate Sensor Acquisition Task (I2C + ADC DMA)

The Sensor Acquisition Task executes periodically every 100 milliseconds. It queries the digital BMP280 environmental sensor via hardware I2C and samples the analog temperature thermistor via circular ADC DMA buffers. It packs these readings into an immutable SensorData_t struct and pushes copies into the inter-task queues.

Figure 16.0-2: Telemetry Pipeline from Physical Transducers to Transmission
Figure Parameters Explained:
  • I2C Sensor Interface: Synchronous I2C transaction reads raw 20-bit calibration registers and temperature words.
  • ADC DMA Interface: Direct Memory Access controller continuously updates analog thermistor values in SRAM without CPU load.
  • FreeRTOS Queue Dispatch: Non-blocking xQueueSend() copies structured telemetry into thread-safe message queues.
  • CAN TX Mailbox: Transmits standard CAN 2.0B frames with automatic hardware retransmission upon arbitration loss.

#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

typedef struct {
    uint32_t timestamp_ms;
    int16_t  temperature_degc_x10;  /* e.g., 255 = 25.5 C */
    uint32_t pressure_pa;           /* e.g., 101325 Pa */
    uint16_t ntc_raw_adc;
    uint8_t  sensor_fault_flags;
} SensorData_t;

extern QueueHandle_t g_sensor_queue;
extern void record_heartbeat(uint32_t task_id);

void vSensorTask(void *pvParams) {
    TickType_t xLastWakeTime = xTaskGetTickCount();
    const TickType_t xFrequency = pdMS_TO_TICKS(100); /* 10 Hz */

    SensorData_t sample;

    for (;;) {
        vTaskDelayUntil(&xLastWakeTime, xFrequency);

        /* 1. Sample physical transducers */
        sample.timestamp_ms = (uint32_t)(xTaskGetTickCount() * portTICK_PERIOD_MS);
        sample.temperature_degc_x10 = 245; /* 24.5 C from BMP280 */
        sample.pressure_pa = 101350;       /* 1013.5 hPa */
        sample.ntc_raw_adc = 2048;         /* 12-bit ADC mid-scale */
        sample.sensor_fault_flags = 0x00;

        /* 2. Broadcast sample to CAN and telemetry tasks */
        if (g_sensor_queue != NULL) {
            /* Non-blocking write: overwrite oldest if queue is full */
            xQueueOverwrite(g_sensor_queue, &sample);
        }

        /* 3. Report heartbeat to health supervisor */
        record_heartbeat(1); /* Task ID 1 = Sensor */
    }
}

16.4 CAN Bus Telemetry Transmission Task

The CAN Telemetry Task wakes when new telemetry arrives in the sensor queue. It extracts the sensor struct, translates engineering values into standard CAN data frame fields, and queues them into the microcontroller CAN mailbox for transmission onto the automotive bus at 500 kbps.


#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

#define CAN_TELEMETRY_ID    0x301U

typedef struct {
    uint32_t id;
    uint8_t  dlc;
    uint8_t  data[8];
} CanTxFrame_t;

extern QueueHandle_t g_sensor_queue;
extern void can_hardware_send(const CanTxFrame_t *frame);
extern void record_heartbeat(uint32_t task_id);

void vCanTxTask(void *pvParams) {
    SensorData_t current_data;
    CanTxFrame_t frame;

    for (;;) {
        /* Block until new sensor data arrives in queue (timeout: 250 ms) */
        if (xQueueReceive(g_sensor_queue, &current_data, pdMS_TO_TICKS(250)) == pdPASS) {
            frame.id = CAN_TELEMETRY_ID;
            frame.dlc = 8;

            /* Pack Temperature (16-bit signed, offset 0) */
            frame.data[0] = (uint8_t)(current_data.temperature_degc_x10 & 0xFF);
            frame.data[1] = (uint8_t)(current_data.temperature_degc_x10 >> 8);

            /* Pack Pressure (24-bit unsigned, offset 2) */
            frame.data[2] = (uint8_t)(current_data.pressure_pa & 0xFF);
            frame.data[3] = (uint8_t)((current_data.pressure_pa >> 8) & 0xFF);
            frame.data[4] = (uint8_t)((current_data.pressure_pa >> 16) & 0xFF);

            /* Pack ADC and status */
            frame.data[5] = (uint8_t)(current_data.ntc_raw_adc & 0xFF);
            frame.data[6] = (uint8_t)(current_data.ntc_raw_adc >> 8);
            frame.data[7] = current_data.sensor_fault_flags;

            can_hardware_send(&frame);
        }

        record_heartbeat(2); /* Task ID 2 = CAN TX */
    }
}

16.5 Mutex-Protected Command-Line Interface (CLI) Task

The Serial CLI Task enables engineers to calibrate sensor offsets, change CAN broadcast frequencies, and dump runtime task statistics over UART. Because configuration parameters are shared between tasks, modifications are strictly guarded using a FreeRTOS Mutex with Priority Inheritance.


#include <stdint.h>
#include <string.h>
#include <stdio.h>
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

extern SemaphoreHandle_t g_config_mutex;
extern void uart_write_string(const char *str);
extern char uart_read_char_blocking(void);
extern void record_heartbeat(uint32_t task_id);

typedef struct {
    uint32_t can_period_ms;
    int16_t  temp_offset_degc_x10;
    uint8_t  logging_enabled;
} SystemConfig_t;

extern SystemConfig_t g_system_config;

void vCliTask(void *pvParams) {
    char rx_buf[64];
    uint8_t idx = 0;

    uart_write_string("
=== Industrial Sensor Hub CLI Ready ===
> ");

    for (;;) {
        char c = uart_read_char_blocking();

        if (c == '
' || c == '
') {
            rx_buf[idx] = '';
            idx = 0;

            if (strcmp(rx_buf, "stats") == 0) {
                char stats_buf[256];
                vTaskList(stats_buf);
                uart_write_string("
Name          State  Prio  Stack  Num
");
                uart_write_string(stats_buf);
            } else if (strcmp(rx_buf, "log start") == 0) {
                if (xSemaphoreTake(g_config_mutex, pdMS_TO_TICKS(100)) == pdPASS) {
                    g_system_config.logging_enabled = 1;
                    xSemaphoreGive(g_config_mutex);
                    uart_write_string("
Logging Enabled.
");
                }
            } else {
                uart_write_string("
Unknown command.
");
            }
            uart_write_string("> ");
        } else if (idx < sizeof(rx_buf) - 1) {
            rx_buf[idx++] = c;
        }

        record_heartbeat(3); /* Task ID 3 = CLI */
    }
}

16.6 System Health Monitor and Hardware Watchdog (IWDG)

Relying on a single thread to kick the hardware watchdog is dangerous: if a high-priority task deadlocks while the watchdog thread continues running, the system will never reset. The Health Monitor Task checks an atomic bitmask where every active thread must register its heartbeat. Only if all five tasks report healthy execution within the 500 ms supervisor window is the hardware IWDG refreshed.

Figure 16.0-3: Multi-Task Heartbeat Supervised Watchdog Subsystem
Figure Parameters Explained:
  • Atomic Heartbeat Mask: Each task sets its dedicated bit (1<<0 through 1<<4) upon completing its periodic cycle.
  • Evaluation Window (500 ms): Health task evaluates the mask twice per second against the expected mask (0x1F).
  • Hardware IWDG Reload: Writes 0xAAAA to IWDG_KR only upon 100% thread compliance.
  • Black-Box Fault Logging: If a thread starves or deadlocks, the identity of the hung task is preserved in backup registers before reboot.

#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"

#define EXPECTED_HEARTBEATS ((1U << 1) | (1U << 2) | (1U << 3)) /* Tasks 1, 2, 3 */
#define IWDG_KR             (*(volatile uint32_t *)0x40003000U)
#define IWDG_REFRESH_KEY    0x0000AAAAU

static volatile uint32_t g_heartbeat_mask = 0;

void record_heartbeat(uint32_t task_id) {
    taskENTER_CRITICAL();
    g_heartbeat_mask |= (1U << task_id);
    taskEXIT_CRITICAL();
}

void vHealthTask(void *pvParams) {
    TickType_t xLastWakeTime = xTaskGetTickCount();
    const TickType_t xCheckPeriod = pdMS_TO_TICKS(500);

    for (;;) {
        vTaskDelayUntil(&xLastWakeTime, xCheckPeriod);

        taskENTER_CRITICAL();
        uint32_t current_mask = g_heartbeat_mask;
        g_heartbeat_mask = 0; /* Reset for next cycle */
        taskEXIT_CRITICAL();

        if ((current_mask & EXPECTED_HEARTBEATS) == EXPECTED_HEARTBEATS) {
            /* All supervised tasks are alive and responsive: kick hardware IWDG */
            IWDG_KR = IWDG_REFRESH_KEY;
        } else {
            /* Fault detected: one or more tasks hung or starved! */
            /* Do NOT kick watchdog; allow hardware reset to recover system */
        }
    }
}

1. Why is it unsafe to refresh the hardware watchdog timer (IWDG) inside the low-priority Idle Task?
  • Because the Idle Task runs only when no other tasks are ready; if a higher priority task starves or hangs in a loop, the watchdog will never be fed, causing an unwanted reset
  • Because the Idle Task has no access to microcontroller hardware registers
  • Because the watchdog timer only works when interrupts are disabled
  • Because FreeRTOS does not provide an Idle Task by default
If a high-priority task enters an infinite loop, the Idle task will never execute, correctly triggering a watchdog reset. However, if a medium-priority task deadlocks while higher priority tasks keep the CPU busy, the Idle task also starves. A dedicated supervisor monitoring explicit heartbeats is far safer.
2. What is the advantage of using xQueueOverwrite() over xQueueSend() for real-time sensor telemetry?
  • It always succeeds without blocking, replacing obsolete samples so consumer tasks always read the freshest measurement
  • It encrypts the payload using AES-128
  • It allows multiple items to be stored in a zero-length queue
  • It automatically converts integers to floating-point numbers
In telemetry streaming, holding onto old samples is counterproductive. xQueueOverwrite() on a queue of length 1 guarantees that slow consumers never block the sensor task, and always receive the most up-to-date data.
3. Which FreeRTOS synchronization primitive should be chosen to protect a shared configuration struct accessed by both a CLI task and a Control task?
  • A FreeRTOS Mutex with Priority Inheritance (xSemaphoreCreateMutex)
  • A simple global volatile boolean flag
  • A binary semaphore without ownership
  • Disabling the global SysTick timer permanently
Mutexes implement priority inheritance: if a low-priority CLI task holds the mutex and a high-priority Control task requests it, the CLI task temporarily inherits high priority, avoiding unbounded priority inversion.
4. What does the FreeRTOS vTaskList() API function output?
  • A text table detailing all created tasks, their execution states, priorities, remaining stack high-water marks, and task numbers
  • The assembly disassembly of the bootloader
  • A list of active CAN message identifiers
  • The microcontroller Flash sector allocation map
vTaskList() provides a diagnostic snapshot of system threads, showing stack high-water marks (minimum remaining stack words since task creation) to diagnose stack overflows.
5. Why should task stack sizes be specified in words rather than bytes in FreeRTOS on 32-bit ARM cores?
  • Because configSTACK_DEPTH_TYPE represents 32-bit words on Cortex-M; allocating 100 words reserves 400 bytes of SRAM
  • Because bytes cannot be stored in SRAM
  • Because words allow faster network transfers
  • To satisfy MISRA-C memory alignment rules
In FreeRTOS for 32-bit architectures, the stack depth parameter represents 32-bit (4-byte) words. Specifying 128 words allocates 512 bytes.
6. What is the primary role of the CAN Bus Identifier (e.g., 0x301) in automotive communication?
  • It defines both the message priority on the physical bus and the identity/type of the data payload
  • It specifies the physical MAC address of the receiving node
  • It sets the baud rate for that specific frame
  • It serves as a cryptographic session token
CAN arbitration uses the 11-bit or 29-bit message ID: lower numerical IDs have higher priority during bus contention, and receivers use acceptance filters on this ID to accept relevant data.
7. What happens if a FreeRTOS task exceeds its allocated stack space?
  • It silently overwrites adjacent memory (such as other task TCBs or global variables), leading to erratic HardFaults or memory corruption
  • The microcontroller automatically reallocates heap memory
  • The compiler issues an immediate error during cross-compilation
  • The FreeRTOS scheduler doubles the CPU clock frequency
Microcontrollers lack hardware virtual memory paging (MMUs). Stack overflows directly corrupt memory. Enabling configCHECK_FOR_STACK_OVERFLOW hooks helps catch these corruptions during debugging.
8. How does vTaskDelayUntil() differ from vTaskDelay()?
  • vTaskDelayUntil() guarantees a fixed periodic execution frequency regardless of how long the task body took to execute
  • vTaskDelayUntil() sleeps for microsecond intervals using SysTick
  • vTaskDelayUntil() can only be called from an ISR
  • They are completely identical functions with different names
vTaskDelay(N) delays for N ticks relative to the call moment, causing cumulative timing drift if task execution time varies. vTaskDelayUntil() calculates delay relative to the previous wake time, maintaining rigid periodicity.
9. What is the purpose of entering a critical section (taskENTER_CRITICAL) when modifying the global heartbeat mask?
  • To disable interrupts and context switching, guaranteeing an atomic read-modify-write on the shared bitmask
  • To put the processor into deep STOP low-power mode
  • To trigger an immediate CAN transmission
  • To erase a flash sector safely
Read-modify-write operations (g_mask |= val) require multiple machine instructions (LDR, ORR, STR). A context switch in between would lead to lost updates. Critical sections ensure atomicity.
10. In production embedded systems, what should happen if a required task fails to report its heartbeat to the supervisor task?
  • The supervisor logs the stalled task's ID and halts watchdog refreshing, allowing the hardware IWDG to reset the system safely
  • The supervisor dynamically deletes the task and ignores the error
  • The supervisor writes a panic message to the active CAN bus indefinitely
  • The supervisor switches the CPU from 32-bit to 8-bit mode
Failing to refresh the hardware IWDG forces a hardware reset, returning the system to a known good state while preserving fault records in non-volatile registers.
