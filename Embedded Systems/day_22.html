22.1 When Bare-Metal and RTOS Are Not Enough: The Embedded Linux Paradigm

While microcontrollers (ARM Cortex-M) excel at deterministic, sub-microsecond control loops with minimal power draw, modern connected embedded systems—such as industrial automation gateways, high-speed edge AI cameras, automotive infotainment displays, and smart grid routers—demand complex capabilities:

  • Full dual-stack IPv4/IPv6 networking with TLS 1.3 encryption and WebSockets.
  • Complex multi-gigabyte filesystems (ext4, UBIFS) on eMMC or NVMe SSDs.
  • Hardware accelerated graphics (OpenGL/Wayland) and video decoding (V4L2).
  • True virtual memory management with hardware MMUs isolating user-space processes.
These systems transition to Application Processors (ARM Cortex-A, RISC-V 64) running Embedded Linux.

Figure 22.0-1: Embedded Linux Multi-Stage Boot Sequence
Figure Parameters Explained:
  • ROM Bootloader (PBL): Hard-coded silicon boot code; reads boot mode pins and loads SPL from SD/eMMC into internal SRAM.
  • U-Boot SPL: Initializes external DDR3/DDR4 SDRAM controllers and power management ICs (PMICs).
  • U-Boot Proper: Provides an interactive bootloader shell, network TFTP booting, and kernel execution handover.
  • Linux Kernel & DTB: Initializes MMU, schedules processes, configures drivers using Device Tree bindings, and mounts rootfs.

22.2 The Linux Device Tree (DTS / DTB) Hardware Abstraction

Unlike x86 personal computers with ACPI and PCI buses that dynamically enumerate attached hardware, embedded ARM application processors feature System-on-Chips (SoCs) with hardwired internal buses. To avoid compiling hardcoded register addresses into the kernel binary, Linux uses a Device Tree: a hierarchical data structure describing physical memory addresses, interrupts, clocks, and pin multiplexing.

Figure 22.0-2: Device Tree Source (DTS) Compilation to Flattened Device Tree (DTB)
Figure Parameters Explained:
  • Device Tree Source (.dts): C-like hierarchical text file describing peripherals, base addresses, and pin configurations.
  • Compatible String: Matching key (e.g., 'bosch,bmp280') linking device tree hardware nodes to specific kernel driver C code.
  • Pin Control (pinctrl): Configures electrical pull-ups, drive strength, and internal multiplexer pin routing.
  • Device Tree Overlays (.dtbo): Dynamically modifies hardware descriptions at runtime (e.g. plugging in a Raspberry Pi HAT).

22.3 User-Space GPIO Control using modern libgpiod

Historically, Linux accessed GPIO pins via the legacy /sys/class/gpio sysfs interface. This interface is deprecated due to high context-switch overhead and lack of atomic multi-pin updates. Modern embedded Linux utilizes libgpiod, interacting with the Linux character device /dev/gpiochipN via ioctl syscalls.


#include <gpiod.h>
#include <stdio.h>
#include <unistd.h>

#define CHIP_NAME   "gpiochip0"
#define LED_PIN     17  /* GPIO 17 */

int main(void) {
    struct gpiod_chip *chip = NULL;
    struct gpiod_line *line = NULL;
    int ret;

    /* 1. Open the GPIO controller chip device */
    chip = gpiod_chip_open_by_name(CHIP_NAME);
    if (!chip) {
        perror("Failed to open gpiochip");
        return 1;
    }

    /* 2. Acquire handle to the specific GPIO line */
    line = gpiod_chip_get_line(chip, LED_PIN);
    if (!line) {
        perror("Failed to get line");
        gpiod_chip_close(chip);
        return 1;
    }

    /* 3. Request line as output with consumer label */
    ret = gpiod_line_request_output(line, "led_blinker", 0);
    if (ret < 0) {
        perror("Failed to request line output");
        gpiod_chip_close(chip);
        return 1;
    }

    printf("Toggling GPIO %d via libgpiod...
", LED_PIN);

    /* 4. High-speed toggle loop */
    for (int i = 0; i < 10; i++) {
        gpiod_line_set_value(line, 1);
        usleep(100000); /* 100 ms */
        gpiod_line_set_value(line, 0);
        usleep(100000);
    }

    /* 5. Release line and close chip */
    gpiod_line_release(line);
    gpiod_chip_close(chip);
    return 0;
}

22.4 User-Space SPI Communication with /dev/spidev

Linux provides the spidev generic character driver to interface SPI peripherals (such as Flash chips or LCD displays) directly from user-space applications without writing custom kernel modules. Configuration (mode, bits-per-word, clock speed) and full-duplex transfers are performed via ioctl() syscalls.


#include <stdint.h>
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/spi/spidev.h>

#define SPIDEV_PATH "/dev/spidev0.0"

int main(void) {
    int fd = open(SPIDEV_PATH, O_RDWR);
    if (fd < 0) {
        perror("Failed to open spidev");
        return 1;
    }

    uint8_t mode = SPI_MODE_0;
    uint8_t bits = 8;
    uint32_t speed_hz = 10000000; /* 10 MHz */

    /* Configure SPI parameters */
    ioctl(fd, SPI_IOC_WR_MODE, &mode);
    ioctl(fd, SPI_IOC_WR_BITS_PER_WORD, &bits);
    ioctl(fd, SPI_IOC_WR_MAX_SPEED_HZ, &speed_hz);

    /* Read JEDEC ID Command (0x9F) followed by 3 dummy response bytes */
    uint8_t tx_buf[4] = {0x9F, 0x00, 0x00, 0x00};
    uint8_t rx_buf[4] = {0x00, 0x00, 0x00, 0x00};

    struct spi_ioc_transfer tr = {
        .tx_buf = (unsigned long)tx_buf,
        .rx_buf = (unsigned long)rx_buf,
        .len = 4,
        .speed_hz = speed_hz,
        .bits_per_word = bits,
    };

    /* Execute full-duplex synchronous SPI transaction */
    if (ioctl(fd, SPI_IOC_MESSAGE(1), &tr) < 0) {
        perror("SPI transfer failed");
        close(fd);
        return 1;
    }

    printf("W25Q32 JEDEC Manufacturer ID: 0x%02X
", rx_buf[1]);
    printf("Memory Type:                0x%02X
", rx_buf[2]);
    printf("Capacity Code:              0x%02X
", rx_buf[3]);

    close(fd);
    return 0;
}

22.5 User-Space I2C Communication via /dev/i2c-dev

Interfacing digital sensors over I2C in Linux uses the i2c-dev driver, exposing devices as /dev/i2c-1. The user-space program binds to the target 7-bit slave address using ioctl(fd, I2C_SLAVE, addr), after which standard POSIX read() and write() syscalls interact directly with hardware registers.


#include <stdint.h>
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/i2c-dev.h>

#define I2C_DEV_PATH    "/dev/i2c-1"
#define BMP280_ADDR     0x76U
#define REG_CHIP_ID     0xD0U

int main(void) {
    int fd = open(I2C_DEV_PATH, O_RDWR);
    if (fd < 0) {
        perror("Failed to open I2C bus device");
        return 1;
    }

    /* Bind file descriptor to slave address 0x76 */
    if (ioctl(fd, I2C_SLAVE, BMP280_ADDR) < 0) {
        perror("Failed to acquire I2C bus access for slave");
        close(fd);
        return 1;
    }

    /* 1. Write register pointer (0xD0) */
    uint8_t reg = REG_CHIP_ID;
    if (write(fd, &reg, 1) != 1) {
        perror("Failed to write register address");
        close(fd);
        return 1;
    }

    /* 2. Read 1 byte response */
    uint8_t chip_id = 0;
    if (read(fd, &chip_id, 1) != 1) {
        perror("Failed to read chip ID");
        close(fd);
        return 1;
    }

    printf("BMP280 Chip ID Read: 0x%02X (Expected: 0x58)
", chip_id);
    close(fd);
    return 0;
}

22.6 Writing a Minimal Linux Kernel Character Device Driver

When sub-millisecond interrupt latency or direct hardware register mapping is required in Linux, user-space tools are insufficient; an engineer must write a Linux Kernel Module (LKM). A character driver implements the file_operations structure, mapping user-space syscalls (open, read, write) to kernel C routines registered under a major/minor device number.

Figure 22.0-3: Linux Kernel Character Driver Architecture and Syscall Flow
Figure Parameters Explained:
  • Virtual Filesystem (VFS): Unified kernel abstraction providing identical file semantics to physical disks, pipes, and device nodes.
  • struct file_operations: C function pointer table implementing driver callbacks for user syscalls.
  • copy_to_user(): Safely transfers kernel memory buffers across the hardware MMU barrier into user-space memory.
  • udev / mknod: Creates physical filesystem device node in /dev (e.g. /dev/my_sensor) matching allocated major/minor numbers.

#include <linux/init.h>
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/uaccess.h>

#define DEVICE_NAME "simple_char_dev"
#define BUFFER_SIZE 256

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Embedded Systems Engineer");
MODULE_DESCRIPTION("Minimal Linux Character Driver");

static int major_number;
static char kernel_buffer[BUFFER_SIZE] = "Hello from Linux Kernel Space!
";
static int open_count = 0;

static int dev_open(struct inode *inodep, struct file *filep) {
    open_count++;
    printk(KERN_INFO "simple_char_dev: Device opened %d times
", open_count);
    return 0;
}

static ssize_t dev_read(struct file *filep, char __user *buffer, size_t len, loff_t *offset) {
    size_t bytes_to_copy;
    size_t not_copied;

    if (*offset >= BUFFER_SIZE) return 0; /* EOF */

    bytes_to_copy = min(len, (size_t)(BUFFER_SIZE - *offset));

    /* Safely transfer data from kernel space to user space */
    not_copied = copy_to_user(buffer, kernel_buffer + *offset, bytes_to_copy);
    if (not_copied != 0) {
        return -EFAULT;
    }

    *offset += bytes_to_copy;
    return bytes_to_copy;
}

static struct file_operations fops = {
    .owner = THIS_MODULE,
    .open = dev_open,
    .read = dev_read,
};

static int __init simple_driver_init(void) {
    major_number = register_chrdev(0, DEVICE_NAME, &fops);
    if (major_number < 0) {
        printk(KERN_ALERT "Failed to register major number
");
        return major_number;
    }
    printk(KERN_INFO "simple_char_dev: Registered successfully with Major %d
", major_number);
    return 0;
}

static void __exit simple_driver_exit(void) {
    unregister_chrdev(major_number, DEVICE_NAME);
    printk(KERN_INFO "simple_char_dev: Unregistered successfully
");
}

module_init(simple_driver_init);
module_exit(simple_driver_exit);

22.7 Building Custom Linux Distributions with the Yocto Project

Desktop distributions (like Ubuntu) are bloat-heavy and non-deterministic for commercial embedded products. Professional embedded Linux developers build minimal, hardened operating systems using The Yocto Project / OpenEmbedded. Yocto uses BitBake recipes (.bb files) organized in metadata layers to compile the cross-toolchain, U-Boot, Linux kernel, and tailored root filesystem from source.

1. What is the primary architectural purpose of the Linux Device Tree (DTS/DTB)?
  • To describe the physical hardware topology (base addresses, IRQs, pin muxing) in a separate binary so the same kernel image can run on different boards without recompilation
  • To plant virtual trees inside the Linux filesystem to reduce carbon emissions
  • To replace the need for writing C driver source code
  • To increase the clock speed of external DDR SDRAM
Before Device Trees, every ARM board required hardcoded C board files in the kernel. Device Trees cleanly decouple the kernel binary from board-specific hardware address descriptions.
2. Why is the legacy /sys/class/gpio sysfs interface deprecated in modern Linux in favor of libgpiod?
  • sysfs causes excessive string-parsing context switches, lacks atomic multi-pin manipulation, and does not support kernel timestamping of input events
  • sysfs only works on 32-bit processors
  • sysfs requires root permissions on every machine instruction
  • libgpiod eliminates the physical GPIO hardware pins
sysfs requires opening and writing ASCII strings to separate virtual files for every pin toggle. libgpiod uses efficient ioctl() calls on /dev/gpiochip, allowing atomic updates of pin groups.
3. What is the role of copy_to_user() inside a Linux kernel device driver read() callback?
  • To safely transfer data from kernel memory across the hardware MMU virtual address space boundary into user-space process memory
  • To send files over the network via SSH
  • To copy files between two USB flash drives
  • To bypass the Linux filesystem permissions checks
User space and kernel space occupy completely separate MMU page tables. Dereferencing a user pointer directly in kernel space causes crashes or security vulnerabilities; copy_to_user() handles page validation.
4. Which bootloader component is responsible for training external DDR SDRAM and loading the main U-Boot binary on modern SoCs?
  • U-Boot Secondary Program Loader (SPL)
  • The Linux init process (systemd)
  • The BusyBox shell
  • The FreeRTOS scheduler
At power-on, external DDR RAM is unconfigured and unusable. The on-chip ROM loads the small U-Boot SPL into internal on-chip SRAM, which initializes the DDR memory controller and loads full U-Boot into RAM.
5. What syscall is used in C to execute full-duplex synchronous SPI transactions using /dev/spidev?
  • ioctl(fd, SPI_IOC_MESSAGE(1), &tr)
  • write(fd, buf, len)
  • read(fd, buf, len)
  • printf(buf)
SPI is fundamentally a full-duplex bus where shifting a byte out simultaneously clocks a byte in. Standard read() and write() are half-duplex; the SPI_IOC_MESSAGE ioctl performs atomic full-duplex transfers.
6. What is BitBake in the context of the Yocto Project?
  • A build engine that executes task recipes (.bb files) to cross-compile toolchains, kernels, and root filesystems from source code
  • A hardware chip for baking circuit boards
  • A replacement for the standard C preprocessor
  • A Python package for rendering 3D graphics
BitBake reads recipe metadata, calculates package dependency graphs, fetches upstream source tarballs, applies patches, and cross-compiles complete customized Linux operating system images.
7. Why is standard desktop Linux unsuitable for hard real-time control (such as high-speed motor commutations) without patches?
  • Linux is a general-purpose time-sharing OS optimized for high throughput rather than bounded, deterministic sub-millisecond interrupt latency
  • Linux does not support the C programming language
  • Linux cannot access physical hardware registers
  • Linux CPUs only run at 100 Hz
Standard Linux kernel locks, paging mechanisms, and process scheduling can cause unpredictable latency spikes up to several milliseconds. Real-time requires the PREEMPT_RT patch or a co-processor.
8. What does a 'compatible' string like 'bosch,bmp280' indicate in a Device Tree node?
  • It specifies the exact hardware model name that the Linux kernel matches against registered driver ID tables to bind the appropriate driver
  • It specifies the price of the sensor in euros
  • It sets the serial baud rate to Bosch standard
  • It requires the board to be manufactured in Germany
The 'compatible' string format ('manufacturer,model') serves as the global hardware identifier. When the kernel scans the device tree, it instantiates the driver declaring that exact compatible string.
9. What is an advantage of an asymmetric multiprocessing SoC like the STM32MP157 (Dual Cortex-A7 + Cortex-M4)?
  • The Cortex-A cores run Linux for cloud networking, GUI, and storage, while the Cortex-M4 runs bare-metal or RTOS for hard real-time sensor loops
  • It allows the device to run Windows and Linux simultaneously
  • It halves the required battery capacity
  • It eliminates the need for circuit board traces
Heterogeneous dual-core SoCs give embedded engineers the best of both worlds: full Linux networking and storage on Cortex-A without sacrificing sub-microsecond determinism on the Cortex-M core.
10. What device file is created to interface with I2C bus 1 directly from user space?
  • /dev/i2c-1
  • /dev/ttyS0
  • /dev/null
  • /dev/sda1
When the i2c-dev kernel module is loaded, each physical I2C adapter registered in the kernel exposes a corresponding character device file named /dev/i2c-N.
