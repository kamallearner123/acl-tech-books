14.1 Connectivity Beyond the Circuit Board

While I2C, SPI, and CAN interconnect chips on a single board or vehicle harness, modern IoT and embedded systems must bridge to the wider digital world. They must connect directly to host PCs via USB (Universal Serial Bus), interface with industrial local area networks via Ethernet, communicate with consumer smartphones via Bluetooth Low Energy (BLE), and stream telemetry to cloud databases via Wi-Fi and MQTT.

Integrating these complex protocol stacks on resource-constrained microcontrollers without a desktop operating system requires understanding descriptor hierarchies, lightweight TCP/IP stacks (lwIP), and asynchronous AT command state machines.

Real World Application: Modern hospital patient monitors communicate simultaneously across these layers: a USB CDC port provides local technician diagnostics; an isolated Ethernet port streams vital signs over hospital LANs via lwIP; and a BLE transceiver links to wearable pulse oximeter finger rings.
Figure 2.5-1: USB 2.0 Descriptor Tree Hierarchy
Figure Parameters Explained:
  • Device Descriptor: Root metadata identifying the device VID (Vendor ID) and PID (Product ID).
  • Configuration Descriptor: Specifies bus-powered vs self-powered status and maximum current draw (in 2mA units).
  • Interface Descriptor: Declares functional class (e.g. Class 0x02 = CDC Communications, Class 0x03 = HID).
  • Endpoint Descriptors: Configure hardware FIFOs for Control (EP0), Bulk, Interrupt, or Isochronous transfers.

14.2 USB Device Classes: Communication Device Class (CDC) vs. Human Interface Device (HID)

To avoid writing custom operating system kernel drivers, embedded engineers design USB firmware conforming to standard USB Classes recognized natively by Windows, macOS, and Linux:

  • USB CDC (Communications Device Class): Emulates an RS-232 serial COM port over high-speed USB bulk endpoints. The host OS automatically assigns a virtual serial port (e.g. /dev/ttyACM0 or COM3), allowing standard terminal programs to communicate at over 1 Megabyte/sec.
  • USB HID (Human Interface Device): Used for keyboards, mice, and gamepads. Transmits structured HID Reports over low-latency Interrupt endpoints. Requires zero host driver installation and works in BIOS pre-boot environments.
Figure 2.5-2: USB CDC Virtual COM Port Architecture and Data Flow
Figure Parameters Explained:
  • Bulk Transfer Endpoints: Guarantees error-free data delivery with hardware CRC and retries; utilizes spare bus bandwidth.
  • Control Endpoint (EP0): Handles standard USB enumeration, descriptor requests, and line coding parameters (baud rate, parity).
  • Throughput Advantage: Bypasses physical UART baud rate dividers; USB Full-Speed transmits at up to 12 Mbps wire speed.

14.3 Embedded TCP/IP Networking: The lwIP Architecture

Connecting a microcontroller to an Ethernet LAN requires an operating system networking stack. Because standard Linux socket stacks require megabytes of virtual memory, microcontrollers utilize lwIP (Lightweight IP), an open-source TCP/IP stack designed by Adam Dunkels. lwIP implements full IPv4/IPv6, TCP, UDP, DHCP, and ARP protocols while fitting inside less than 40 KB of ROM and a few kilobytes of RAM through zero-copy packet buffer (pbuf) chaining.

Figure 2.5-3: lwIP Lightweight Embedded TCP/IP Stack Protocol Layers
Figure Parameters Explained:
  • Ethernet PHY (Physical Layer): Transceiver chip (e.g. LAN8742) converting differential cable voltages to digital RMII signals.
  • RMII (Reduced Media Independent Interface): High-speed 50 MHz 7-wire digital interface connecting MAC to PHY.
  • pbuf (Packet Buffer): lwIP memory structure chaining fragmented network packets without copying data.
  • Zero-Copy Architecture: DMA transfers Ethernet frames directly into lwIP pbufs, avoiding multiple CPU memory copies.

14.4 Bluetooth Low Energy (BLE): GAP Advertising & GATT Data Hierarchy

Unlike classic Bluetooth designed for continuous audio streaming, Bluetooth Low Energy (BLE) is engineered for extreme power conservation, allowing sensor nodes to operate for years on a single coin cell. BLE software architecture is divided into two operational models:

  • GAP (Generic Access Profile): Controls device discovery, advertising, and connection establishment. A Broadcaster / Peripheral sends periodic 31-byte Advertising Packets; an Observer / Central (e.g. a smartphone) scans for advertisements.
  • GATT (Generic Attribute Profile): Organizes data once a connection is formed. Data is structured hierarchically into Services (logical functional groups identified by 16-bit or 128-bit UUIDs) containing Characteristics (individual data values supporting Read, Write, and Notify operations).
Figure 2.5-4: BLE GATT Data Structure and Smartphone Notification Flow
Figure Parameters Explained:
  • UUID (Universally Unique Identifier): 16-bit numbers for standard Bluetooth SIG profiles; 128-bit UUIDs for custom vendor profiles.
  • Notify Operation: The peripheral pushes data to the central smartphone asynchronously without waiting for host polling.
  • Connection Interval: Configurable period (e.g. 50 ms to 4000 ms) controlling how frequently radio transceivers exchange synchronization pulses.

14.5 Wireless IoT via Cellular & Wi-Fi: The AT Command State Machine

Many industrial embedded systems pair a host microcontroller with an external co-processor modem (such as an Espressif ESP32 or a Quectel 4G LTE module) over a high-speed UART interface. Communication is managed via standardized Haynes AT Commands. Firmware must implement an asynchronous, non-blocking Parser State Machine to transmit AT strings, handle variable-latency responses (OK, ERROR), and stream telemetry over MQTT.

Figure 2.5-5: STM32 to ESP32 AT Command Flow for Cloud MQTT Publishing
Figure Parameters Explained:
  • Asynchronous AT Parser: Parses incoming ASCII response lines in real-time without blocking the CPU in delay loops.
  • MQTT (Message Queuing Telemetry Transport): Lightweight publish-subscribe protocol ideal for high-latency, low-bandwidth wireless links.
  • Unsolicited Result Codes (URCs): Spontaneous notifications from modem (e.g. '+MQTTRCV') handled by interrupt ring buffers.

int8_t CDC_Receive_FS(uint8_t* Buf, uint32_t *Len);
uint8_t CDC_Transmit_FS(uint8_t* Buf, uint16_t Len);

/* Called by USB interrupt when a packet arrives from host PC */
int8_t CDC_Receive_FS(uint8_t* Buf, uint32_t *Len) {
    uint32_t rx_bytes = *Len;

    /* Echo received bytes back to host PC immediately */
    CDC_Transmit_FS(Buf, (uint16_t)rx_bytes);

    return 0; /* USBD_OK */
}

/* Transmit log string over USB CDC at native 12 Mbps wire speed */
void usb_cdc_print_string(const char *str) {
    uint16_t len = (uint16_t)strlen(str);
    CDC_Transmit_FS((uint8_t *)str, len);
}

#include <stdint.h>

/* Standard USB HID Keyboard Report Format (8 bytes) */
typedef struct __attribute__((packed)) {
    uint8_t modifiers;      /* Bit 0=LCTRL, 1=LSHIFT, 2=LALT, 3=LGUI */
    uint8_t reserved;       /* 0x00 */
    uint8_t keycodes[6];    /* Up to 6 simultaneous pressed keys */
} USB_HID_KeyboardReport_t;

extern void USBD_HID_SendReport(uint8_t *report, uint16_t len);

#define HID_KEY_A           0x04
#define HID_KEY_RETURN      0x28

void send_keystroke_a(void) {
    USB_HID_KeyboardReport_t report = {0};

    /* Step 1: Press 'A' */
    report.keycodes[0] = HID_KEY_A;
    USBD_HID_SendReport((uint8_t *)&report, sizeof(report));

    /* Simple delay before releasing key */
    for (volatile int i = 0; i < 100000; i++);

    /* Step 2: Release all keys (all zeroes report) */
    report.keycodes[0] = 0x00;
    USBD_HID_SendReport((uint8_t *)&report, sizeof(report));
}

#include <stdint.h>
#include <stdbool.h>
#include <stdio.h>

typedef enum {
    AT_STATE_TEST,
    AT_STATE_JOIN_WIFI,
    AT_STATE_CONNECT_MQTT,
    AT_STATE_PUBLISH,
    AT_STATE_IDLE
} AT_ClientState_t;

static AT_ClientState_t g_at_state = AT_STATE_TEST;

void send_uart_command(const char *cmd);

void at_modem_state_machine_step(void) {
    switch (g_at_state) {
        case AT_STATE_TEST:
            send_uart_command("AT\r\n");
            g_at_state = AT_STATE_JOIN_WIFI;
            break;

        case AT_STATE_JOIN_WIFI:
            /* Connect to Access Point */
            send_uart_command("AT+CWJAP=\"LabNetwork\",\"SecurePassword\"\r\n");
            g_at_state = AT_STATE_CONNECT_MQTT;
            break;

        case AT_STATE_CONNECT_MQTT:
            /* Connect to Cloud Broker */
            send_uart_command("AT+MQTTCONN=0,\"broker.hivemq.com\",1883,1\r\n");
            g_at_state = AT_STATE_PUBLISH;
            break;

        case AT_STATE_PUBLISH:
            /* Publish telemetry payload */
            send_uart_command("AT+MQTTPUB=0,\"sensors/telemetry\",\"{\\"status\\":\\"OK\\"}\",0,0\r\n");
            g_at_state = AT_STATE_IDLE;
            break;

        case AT_STATE_IDLE:
            break;
    }
}

1. What is the primary role of the USB Device Descriptor?
  • To configure PWM frequencies
  • To define root device metadata including Vendor ID (VID), Product ID (PID), and supported USB revision
  • To establish Wi-Fi credentials
  • To allocate dynamic heap memory
The Device Descriptor is the initial 18-byte structure read by the host upon plug-in to identify the hardware vendor and product class.
2. Why is the USB Human Interface Device (HID) class widely used for custom embedded PC communication?
  • It supports multi-gigabit throughput
  • Standard OS kernels (Windows, Linux, macOS) include built-in generic HID drivers, eliminating the need to write custom kernel drivers
  • It requires zero RAM on the microcontroller
  • It can only transmit text strings
HID devices require no custom host driver installation. Operating systems natively provide user-space APIs to read/write HID reports.
3. In the lwIP embedded TCP/IP stack, what is a `pbuf`?
  • A hardware register inside the Ethernet PHY
  • A packet buffer data structure that chains network memory blocks without copying data, enabling zero-copy network processing
  • A floating point math coprocessor
  • A persistent configuration sector in Flash
pbufs (packet buffers) allow network layers to add headers and route frames by linking memory pointers rather than allocating and copying buffers.
4. What is the difference between BLE GAP and BLE GATT?
  • GAP manages broadcast advertising and connections; GATT structures data into services and characteristics once connected
  • GAP is used for audio; GATT is used for sensors
  • GAP requires 5V power; GATT operates at 3.3V
  • GATT operates over Wi-Fi only
GAP (Generic Access Profile) governs discovery and pairing. GATT (Generic Attribute Profile) organizes application data into readable/notifiable characteristics.
5. What property must a BLE GATT Characteristic possess to push data asynchronously to a smartphone without being polled?
  • Read Property
  • Write Property
  • Notify (or Indicate) Property
  • Broadcast Property
The Notify property enables the peripheral server to push value updates to the client central device immediately upon data change.
6. What physical interface is commonly used to connect a microcontroller Ethernet MAC to an external Ethernet PHY chip using only 7 digital pins?
  • I2C
  • RMII (Reduced Media Independent Interface)
  • UART
  • 1-Wire
RMII reduces the pin count from 16 (in classical MII) down to 7 lines while clocking at 50 MHz to achieve 100 Mbps data throughput.
7. What does the USB CDC class emulate when connected to a host computer?
  • A SCSI Hard Disk Drive
  • A Virtual COM (Serial) Port
  • An HDMI Display Monitor
  • An Audio Microphone
CDC ACM (Abstract Control Model) presents itself to the operating system as a standard virtual RS-232 serial port.
8. Why is MQTT preferred over HTTP for battery-powered wireless IoT sensor telemetry?
  • MQTT packets have minimal overhead (as small as 2 bytes), reducing radio transmit time and power consumption
  • MQTT requires gigabit Ethernet
  • MQTT cannot be encrypted
  • MQTT requires full web browsers
HTTP headers consume hundreds of bytes per request. MQTT uses compact binary headers, minimizing active radio duration and conserving battery life.
9. In an AT command parser, what are 'Unsolicited Result Codes' (URCs)?
  • Hardware syntax errors
  • Spontaneous messages transmitted by the modem without a prior request (e.g. incoming call, network disconnect, or received MQTT message)
  • Compiler linker errors
  • Parity bit mismatch flags
URCs are sent asynchronously by modems to notify the host MCU of external network events (e.g. '+RECEIVE: 10 bytes').
